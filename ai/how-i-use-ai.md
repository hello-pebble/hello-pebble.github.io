# AI를 어떻게 사용하고 있는가

> AI를 **생산성 증폭기**로 사용합니다. 코드 작성과 반복 작업은 적극적으로 위임하되, 결과물을 검증하고 최종 판단을 내리는 책임은 항상 개발자인 저에게 있다는 원칙을 지킵니다.

---

## 활용 원칙

1. **위임하되, 검증한다**: AI가 생성한 코드는 반드시 직접 읽고, 테스트하고, 동작을 확인한 뒤에만 반영합니다. "AI가 그렇게 했다"는 장애의 변명이 될 수 없기 때문입니다.
2. **질문을 명세처럼 작성한다**: 모호한 요청은 모호한 결과를 낳습니다. 제약 조건, 기대 동작, 예외 상황을 명시한 프롬프트가 곧 좋은 요구사항 정의 훈련이 된다고 생각합니다.
3. **AI가 잘하는 일과 내가 해야 하는 일을 구분한다**: 보일러플레이트, 반복 리팩토링, 문서 초안은 AI가 빠릅니다. 반면 아키텍처 트레이드오프 결정, 도메인 이해, 코드에 대한 책임은 사람의 몫으로 남깁니다.

## 개발 워크플로우에서의 AI

### 설계와 학습 — ChatGPT · Gemini

- 새로운 기술을 학습할 때 **개념 간 비교와 트레이드오프를 토론하는 상대**로 활용합니다. 예를 들어 세션 기반 인증과 JWT 무상태 인증의 장단점을 여러 각도에서 검증하며 [통합 인증 프로젝트](/portfolio/oauth-sso/)의 설계 방향을 다듬었습니다.
- 공식 문서나 RFC처럼 밀도 높은 자료를 읽을 때 요약과 반문(反問)을 병행하여, 이해했다고 착각하는 부분을 드러내는 용도로 사용합니다.
- 서로 다른 모델에 같은 질문을 던져 **답변이 갈리는 지점**을 찾고, 그 지점을 공식 문서로 재확인하는 교차 검증 습관을 유지합니다.

### 구현과 자동화 — Claude Code

- 이 이력서·포트폴리오 사이트의 구조 개편, 스타일링, 다이어그램 제작을 **Claude Code와 협업**으로 진행했습니다. 원하는 결과물의 의도를 정의하고, 결과를 리뷰하고, 방향을 교정하는 역할에 집중했습니다.
- 반복적인 리팩토링, 형식 변환, 테스트 코드 초안처럼 **패턴이 명확한 작업을 위임**하여, 설계와 검증에 쓸 시간을 확보합니다.
- 커밋 단위로 결과를 확인하며 작업 이력을 남겨, AI와의 협업 과정 자체를 추적 가능하게 관리합니다. 협업 방식은 각 저장소에 그대로 공개돼 있습니다 — [DelayNoMore의 릴리스 규칙(CLAUDE.md)](https://github.com/hello-pebble/DelayNoMore_Release/blob/main/CLAUDE.md), [oauth2 프로젝트의 워크플로우 기록](https://github.com/hello-pebble/oauth2-authorization/blob/main/docs/how-i-work/claude-code-workflow.md), [AdminCore의 단계별 계획서·보고서](https://github.com/hello-pebble/AdminCore/tree/main/docs).

### 검증과 책임 — 개발자

- AI가 만든 코드도 제 코드와 동일한 기준으로 리뷰합니다. 특히 **경계 조건, 예외 처리, 보안 관련 코드**는 반드시 직접 검증합니다.
- AI의 답변이 그럴듯하지만 틀린 경우(할루시네이션)를 여러 번 경험했기 때문에, 근거가 되는 공식 문서나 실제 실행 결과로 확인하기 전까지는 사실로 취급하지 않습니다.

## 제품에 AI를 통합한 경험 — DelayNoMore

AI를 개발 도구로 쓰는 것과 **제품의 핵심 기능으로 통합하는 것**은 전혀 다른 문제라는 것을 [DelayNoMore 프로젝트](/portfolio/delaynomore/)에서 배웠습니다.

- **프롬프트를 제품 로직으로 설계**: 목표, 기간, 가용 시간 등 필수 정보(슬롯)가 채워질 때까지 AI 코치가 대화를 유도하도록, 프롬프트를 일회성 질문이 아닌 **상태를 가진 인터뷰 플로우**로 설계했습니다.
- **AI의 지연 시간을 UX로 해결**: 대형 모델의 20~30초 추론 시간을 모델 다운그레이드 없이 스트리밍 응답(`for await...of`)으로 풀어, 대기 시간을 "계획이 조립되는 과정"으로 바꿨습니다.
- **AI의 행동을 데이터로 관리**: 계획 생성·수정을 감사 이력으로 적재하고(프로토타입은 Firestore, 릴리스판은 PostgreSQL), 에이전트의 도구 선택 정확도를 평가 하네스로 실측해 프롬프트 변경의 효과를 숫자로 판단했습니다.

## AI 시대의 백엔드 개발자로서

코드를 생성하는 비용은 빠르게 낮아지고 있습니다. 그래서 저는 **무엇을 만들지 정의하는 능력, 만들어진 것을 검증하는 능력, 시스템 전체의 트레이드오프를 판단하는 능력**이 개발자의 핵심 역량이 된다고 믿습니다. AI를 잘 쓰는 개발자란 결국, AI에게 좋은 질문을 던질 만큼 문제를 깊이 이해하고 있는 개발자라고 생각합니다.
