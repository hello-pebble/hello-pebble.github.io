# 항만 시설 사용료 관리 시스템 — 매년 바뀌는 세율을 다루기

- **서비스** 여수광양항만공사의 GIS 기반 항만 시설 사용료 관리 시스템입니다. 지도 위 시설과 사용 업체를 연결해 사용료를 산정합니다.
- **담당** 연도별·임시 세율 관리, 업체 관리, 사용료 산정 기능을 개발하고 운영을 지원했습니다.
- **이 페이지** 첫 회사에서 15개월간 개발과 운영을 함께 맡으며 무엇을 배웠는지 적었습니다.

## 세율 — 임시 예외를 기존 흐름 옆에 붙이기

| 구분 | 내용 |
| :--- | :--- |
| **기존 구조** | 적용 세율은 해마다 고시되는 기준에서 셀렉박스로 골라 넣고, 그 값으로 전 업체 사용료가 일괄 계산됩니다. |
| **요청** | 코로나 시기 비상 감면으로, 담당자가 **원할 때만** 업체별 적용 세율을 수기로 넣을 수 있게 해 달라는 요구가 왔습니다. |
| **구현** | 기존 화면에 버튼 하나를 더해 **수기 입력 모드로 전환**하도록 했습니다. 전환하면 셀렉박스 대신 직접 입력한 세율이 적용되고, 전환하지 않은 업체는 기존 경로 그대로 계산됩니다. |
| **건드리지 않은 것** | 기준 세율을 고르는 셀렉박스와 일괄 계산 코드는 수정하지 않고, 필요한 기능만 옆에 덧붙였습니다. |

- **왜 덧붙이는 방식이었나** 감면은 한시적이고, 코로나가 끝나면 모든 업체가 다시 기준 세율 셀렉박스로 돌아갈 것이 분명했습니다. 정상 경로를 고쳐 예외를 녹이면 나중에 되돌릴 때 또 손을 대야 합니다. 예외는 켜고 끌 수 있는 모드로 두고, 정상 경로는 그대로 두는 쪽이 되돌리기 쉬웠습니다.
- **여기서 배운 것** 예외를 코드 분기로 넣지 않고 **담당자가 켜고 끄는 모드**로 두면, 예외가 생기거나 사라질 때 개발 요청이 필요 없습니다. 이후 개방DB API관리에서 조회 API를 메타데이터로 옮긴 것도 같은 판단의 연장입니다.

## 운영 — 월 1회 현장 방문

- **점검** 매월 현장을 방문해 서버 상태를 점검했습니다. 원격 접근이 제한된 환경이라 정기 방문이 유일한 확인 수단이었습니다.
- **대응** 담당자 문의와 개선 요청을 직접 받아 반영했습니다. 사용자와 개발자 사이에 중간 단계가 없어, 요청이 실제로 무엇을 해결하려는 것인지 그 자리에서 확인할 수 있었습니다.

## 도로 점검 모듈 — 전 계층을 처음 혼자 맡은 기능

입사 직후인 2019.06에 생성된 모듈로, 당시 코드를 보관하고 있어 아래는 그 코드 기준으로 적었습니다. 항만 도로 시설의 연도별 점검 결과를 등록·수정·조회·인쇄하는 기능이며 컨트롤러·서비스·DAO·iBATIS SQL 맵·JSP를 모두 작성했습니다.

| 구분 | 내용 |
| :--- | :--- |
| **데이터 구조** | 점검 헤더 1건(연도·시설·순번) 아래에 점검 항목을 **1종·2종·기타 세 묶음**으로 나눠 세부 행으로 저장 |
| **등록** | 헤더를 먼저 넣어 순번을 받고, 세 묶음의 세부 행에 그 순번을 붙여 저장 |
| **수정** | 세부 행을 비교하지 않고 **헤더 기준으로 전부 지운 뒤 요청대로 다시 저장** |
| **삭제** | 세부 행을 먼저 지우고 헤더를 지워 참조 순서를 지킴 |
| **부가 기능** | 공통 업로드 유틸과 ID 생성기를 이용한 첨부 파일, 세 묶음을 한 장에 담는 인쇄 페이지 |
| **보고서** | 점검 결과 보고서는 Crystal Reports로 연동해 출력 |
| **DB 작업** | 자산 관리용 공통코드(건물 용도·건물 구조) 등록 SQL 작성 |

- **세부 행을 교체한 이유** 세 묶음 각각에서 어떤 행이 바뀌었는지 계산하는 것보다, 화면에 보이는 상태를 그대로 저장하는 쪽이 단순했습니다. 요청 본문이 곧 최종 상태가 됩니다. 이후 [LMS 역할 변경](/portfolio/lms/#roles)에서도 같은 선택을 했습니다.
- **반복 코딩을 줄인 시트** 테이블 컬럼 목록을 붙여 넣으면 VO 필드 선언, SQL 바인딩, JSP 입력 폼 조각이 수식으로 만들어지는 엑셀 시트를 만들어 썼습니다. 화면 하나에 수십 개 컬럼을 손으로 옮기던 작업을 줄이려는 것이었고, 같은 문제를 나중에 개방DB에서는 메타데이터 엔진으로 풀었습니다.
- **지금 보면 틀린 것** 인쇄 페이지에서 시설 종류 코드를 `==`로 비교해, 어떤 값이 와도 "기타"로 표시됐습니다. Java 문자열 비교를 몰라서 생긴 버그이고 당시에는 발견하지 못했습니다. 세부 행도 건별로 `INSERT`해서 항목이 많으면 왕복이 그만큼 늘어납니다.

## 한계

- **수치 기록이 없습니다** 첫 회사 프로젝트라 장애 원인 분석이나 개선 전후 지표를 문서로 남기지 않았습니다. 이 페이지에 숫자를 적지 않은 이유입니다.
- **테스트가 없었습니다** 자동 테스트 없이 수동 확인에 의존했습니다. 세율처럼 기간에 따라 결과가 갈리는 로직일수록 테스트가 필요하다는 것은 이후 프로젝트에서 알았습니다.
