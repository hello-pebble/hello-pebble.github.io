# 사내 교육 플랫폼(LMS) — 회원·운영관리 백엔드

- **서비스** 기업 고객이 쓰는 화상 교육 플랫폼의 LMS 백엔드입니다. 과정·강의 모듈은 다른 팀원이, 회원과 운영관리 모듈은 제가 맡았습니다.
- **담당** 회원 등록·수정·삭제와 역할 부여, 공지사항·FAQ·Q&A 운영관리, 공통코드 유형, 업체 관리 연동. 4개월 동안 커밋 33건, 약 4,200줄.
- **이 페이지** 보관 중인 저장소 사본의 제 커밋을 기준으로 적었습니다. 설계한 것과 당시에는 몰랐던 문제를 나눠 썼습니다.

| 기능 | 처리 |
| :--- | :--- |
| **회원** | 등록·수정·삭제, 이메일 중복 확인, 이름·사번·이메일·업체명 조건 검색과 페이징 |
| **역할** | 사용자-역할 매핑(`T_USER_ROLE`), 강사 역할에 딸린 강사 정보 |
| **공지사항** | 등록·수정·노출 여부 변경, 팝업 이미지 업로드 |
| **FAQ · Q&A** | 유형별 조회, 관리자 답변 등록, 답변 순번 |
| **공통코드** | 코드 유형 등록·조회 |

## 01. 역할 변경은 차집합이 아니라 교체로 처리 {#roles}

사용자는 역할을 여러 개 가질 수 있고(관리자·강사·수강생), 역할은 `(ROLE_ID, USER_ID)` 복합키 엔티티로 둡니다. 수정 요청이 오면 기존 역할 목록과 비교해 추가·삭제를 계산하지 않고, **기존 매핑을 비우고 요청에 담긴 역할로 다시 채웁니다.**

- 요청 본문이 곧 최종 상태라서, 화면과 서버가 "지금 역할이 무엇인가"를 두고 어긋날 여지가 없습니다.
- 대가로 수정 때마다 삭제·삽입이 생깁니다. 역할이 서너 개인 서비스라 감수했습니다.
- 강사 정보는 역할 엔티티에 `cascade`로 매달아, 강사 역할이 빠지면 강사 정보도 같이 정리됩니다.

## 02. 유형은 이름이 아니라 코드 ID로 저장 {#type-id}

FAQ와 Q&A의 유형을 처음에는 표시용 이름 문자열로 들고 있었습니다. 유형 이름이 바뀌면 기존 글이 그 유형에서 떨어져 나가는 구조라, 마지막 주에 **공통코드 ID를 저장하고 이름은 조회 시 붙이는 방식**으로 바꿨습니다. 저장 값과 표시 값을 분리하는 첫 경험이었습니다.

## 03. 검색은 조건이 있을 때만 붙는 동적 쿼리 {#search}

회원·공지·FAQ 목록은 QueryDSL `BooleanBuilder`로 입력된 조건만 `where`에 더하고, 페이징은 `Pageable`로 받습니다. 조건 조합마다 쿼리 메서드를 늘리지 않기 위해서입니다.

## 04. 파일 업로드 — 지금 보면 아쉬운 것 {#files}

공지사항 팝업 이미지는 Azure Blob Storage에 올리고 파일 메타데이터를 별도 테이블에 저장합니다. 당시 구현은 업로드 예외를 `catch`로 삼키고 공지 저장을 계속해, 파일은 없는데 공지는 등록된 상태가 생길 수 있었습니다.

- **외부 저장과 DB 저장은 하나의 트랜잭션으로 묶이지 않는다**는 것을 이때는 몰랐습니다. 이후 PMS의 저장 유실 분석과 AdminCore의 "상태 변경과 통지를 한 트랜잭션으로" 판단은 이 경험에서 출발했습니다.

## 결과와 한계

- 회원·운영관리 API를 `develop`에 병합해 사내 배포했습니다. 프리랜서 선임의 코드 리뷰와 페어 프로그래밍으로 JPA를 실무에 처음 적용했습니다.
- 인증(JWT)과 Spring Security 설정은 다른 팀원 담당이었습니다. 제 몫은 역할 데이터 모델링까지였고, 엔드포인트 인가 규칙은 제가 설계하지 않았습니다.
- 자동 테스트가 없었고, 4개월 계약이라 위 문제를 고칠 기회가 없었습니다. 보관 중인 코드로 확인한 범위만 적었고, 그 밖의 세부는 기억이 정확하지 않아 적지 않았습니다.
