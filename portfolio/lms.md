# 사내 교육 플랫폼(LMS) — 권한과 파일 정합성

- **서비스** 다수 부서·직군이 함께 쓰는 사내 교육 플랫폼입니다.
- **담당** SSO 연동 권한 인가와 파일 저장 구현을 맡았습니다.
- **이 페이지** 직접 구조를 바꾼 것(권한 인가)과, 제약이 주어진 상태에서 구현한 것(파일 저장)을 나눠 적었습니다.

## 트러블슈팅 1 — 화면 분기만으로는 못 막는 비인가 접근

| 구분 | 내용 |
| :--- | :--- |
| **증상** | 부서·직군이 섞인 사용자의 비인가 기능 접근을 차단할 수단이 없었습니다. |
| **원인** | 세분화된 권한 체계가 없고 검증이 화면 단위 분기로 흩어져 있어, API 직접 호출을 막지 못했습니다. |
| **조치** | SSO 세션 정보를 RBAC로 구조화하고, Spring Security 계층에 공통 권한 검증 인터셉터를 두었습니다. |
| **결과** | API 엔드포인트 레벨에서 비인가 요청을 차단했습니다. |

- **핵심** 검증 로직을 기능마다 복제하지 않고 한 곳에 모았습니다. 권한 검사가 흩어져 있으면 누락된 한 곳이 곧 구멍이 되기 때문입니다.

## 파일 저장 — 주어진 제약 안에서 구현하기

**저장 위치는 제가 고른 것이 아니라 요구사항이었습니다.** 자사 시스템과 연동되는 사내 서비스였고, 사내 정보가 담긴 자료라 외부 스토리지가 아닌 자체 서버 안에 보관해야 했습니다. 그래서 Oracle BLOB 저장이 전제로 주어졌고, 제 몫은 그 전제 위에서 구현하는 일이었습니다.

| 구분 | 내용 |
| :--- | :--- |
| **주어진 제약** | 사내 정보가 담긴 자료 → 자체 서버 보관 · 자사 시스템 연동 → Oracle BLOB 저장 |
| **구현** | 파일 생성·수정·삭제를 비즈니스 데이터와 같은 트랜잭션(`@Transactional`)에 묶어, 한쪽만 반영되는 상태가 생기지 않게 했습니다. |
| **따라온 이점** | 백업·복구 단위가 DB 하나로 통일돼, 게시글은 있는데 첨부파일이 없는 불일치가 구조적으로 생기지 않습니다. |
| **따라온 비용** | DB 용량과 I/O 부하가 늘고, 파일이 크거나 많아지면 맞지 않는 방식입니다. |

- **여기서 배운 것** 저장 위치가 정해져 있어도 **트랜잭션 경계를 어디에 두느냐는 여전히 구현자의 선택**이었습니다. 파일을 DB에 넣는 것만으로 정합성이 보장되지는 않고, 같은 트랜잭션에 묶어야 의미가 생깁니다.
- **제약을 읽는 법** 당시에는 "이렇게 하라"는 요구로만 받았지만, 사내 정보라는 성격과 연동 조건에서 나온 제약이었습니다. 요구사항 뒤의 이유를 먼저 묻는 편이 낫다는 것을 이후에 알았습니다.

![파일 저장 방식 비교 - 로컬 디스크 vs Oracle BLOB](/assets/images/portfolio/lms-blob.svg)

## 결과

- 엔드포인트 레벨 권한 제어와 트랜잭션으로 묶인 파일 저장으로 사내 배포를 완료했습니다.
- JPA를 실무에 처음 적용하며, 프리랜서 선임 개발자의 코드 리뷰와 페어 프로그래밍으로 ORM 기반 설계를 익혔습니다.
