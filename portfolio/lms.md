# 사내 교육 플랫폼(LMS) — 권한과 파일 정합성

- **서비스** 다수 부서·직군이 함께 쓰는 사내 교육 플랫폼입니다.
- **담당** SSO 연동 권한 인가와 파일 저장 구조를 맡았습니다.
- **다룬 위험** 비인가 접근과 첨부파일 유실, 두 가지를 각각 구조로 해결했습니다.

## 트러블슈팅 1 — 화면 분기만으로는 못 막는 비인가 접근

| 구분 | 내용 |
| :--- | :--- |
| **증상** | 부서·직군이 섞인 사용자의 비인가 기능 접근을 차단할 수단이 없었습니다. |
| **원인** | 세분화된 권한 체계가 없고 검증이 화면 단위 분기로 흩어져 있어, API 직접 호출을 막지 못했습니다. |
| **조치** | SSO 세션 정보를 RBAC로 구조화하고, Spring Security 계층에 공통 권한 검증 인터셉터를 두었습니다. |
| **결과** | API 엔드포인트 레벨에서 비인가 요청을 차단했습니다. |

- **핵심** 검증 로직을 기능마다 복제하지 않고 한 곳에 모았습니다. 권한 검사가 흩어져 있으면 누락된 한 곳이 곧 구멍이 되기 때문입니다.

![SSO 연동 RBAC 권한 검증 흐름](/assets/images/portfolio/lms-rbac.svg)

## 트러블슈팅 2 — 복구했더니 게시글은 있는데 파일이 없다

| 구분 | 내용 |
| :--- | :--- |
| **증상** | 복구 시 게시글은 있는데 첨부파일이 없는 정합성 불일치가 생길 수 있었습니다. |
| **원인** | 첨부파일을 웹 서버 로컬 디스크에 두어 DB 백업과 파일 백업의 시점이 어긋났습니다. |
| **조치** | 파일을 Oracle BLOB으로 DB에 직접 저장해, 파일 생성·수정·삭제를 비즈니스 데이터와 단일 트랜잭션(`@Transactional`)으로 묶었습니다. |
| **결과** | 백업·복구 단위가 DB 하나로 통일됐습니다. |

**감수한 비용**

- **비용** DB 용량과 I/O 부하가 늘고, 대용량·대량 파일 환경에는 적합하지 않습니다.
- **판단 근거** 사내 교육 자료라는 파일 규모와 "복구 시 정합성이 최우선"이라는 요구에서는 트랜잭션 정합성이 저장 효율보다 중요하다고 판단했습니다.
- **다른 조건이라면** 파일 규모가 큰 시스템이었다면 외부 스토리지와 보상 트랜잭션을 검토했을 것입니다.

![파일 저장 방식 비교 - 로컬 디스크 vs Oracle BLOB](/assets/images/portfolio/lms-blob.svg)

## 결과

- 엔드포인트 레벨 권한 제어와 트랜잭션으로 묶인 파일 저장 구조로 사내 배포를 완료했습니다.
- JPA를 실무에 처음 적용하며 ORM 기반 설계를 익혔습니다.
