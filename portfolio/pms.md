# 공정 관리 솔루션(PMS) — 라벨링 작업을 멈추지 않게 하는 운영

AI 학습데이터 라벨링(2D·3D 이미지, PDF) 작업을 관리자·매니저·기간별 작업자 최대 100명이 원격으로 수행하는 웹 시스템입니다. 프로젝트별 툴 커스터마이징과 Java REST API·관리 페이지 개발, 그리고 **배포와 장애 대응을 재현 가능한 절차로 만드는 일**을 담당했습니다.

## 무엇이 문제였나

초기에는 프로젝트 매니저가 로컬 프로그램을 작업자 PC에 설치하고 엑셀 파일명 기준으로 작업물을 배분·회수했습니다. 웹 전환 후에도 Java WAR, Nginx, Docker, DB가 분리돼 있어 포트·방화벽·컨테이너 연결 설정이 하나만 어긋나도 작업자 전체가 접속하지 못했습니다. 배포가 담당자 개인의 기억에 묶여 있는 것이 실제 리스크였습니다 — 접속 불가는 곧 라벨링·검수·납품 일정 전체의 정지였기 때문입니다.

## 어떻게 풀었나

**실행 환경을 컨테이너로 정리했습니다.** Java REST API·관리 페이지는 WAR로, FastAPI 기반 라벨링 툴 화면은 Nginx로 실행하도록 구성하고, 구현이 안정화된 뒤 Docker Compose로 애플리케이션 구성 요소를 묶었습니다. DB 서버는 분리해 점검 지점을 줄였습니다.

**배포를 절차로 만들었습니다.** develop의 변경이 검토를 거쳐 main에 병합되면 GitLab CI가 이미지를 빌드하고, 빌드 성공 확인 후 수동 배포합니다. 완전 자동 배포 대신 수동 단계를 남긴 것은 기간제 인력이 몰리는 작업 시간대를 피해 배포 시점을 통제하기 위해서였고, 대신 배포 전 확인 항목(포트 포워딩·방화벽·컨테이너 포트 연결)을 문서로 고정해 누가 해도 같은 결과가 나오게 했습니다.

![GitLab CI/CD 배포 파이프라인](/assets/images/portfolio/pms-pipeline.svg)

**장애 대응을 기록으로 만들었습니다.** Nginx·Docker 로그에서 증상과 원인을 확인해 수정하고, 화면 캡처·코드 위치·조치 순서를 오류 문서로 남겨 같은 장애가 다시 왔을 때 걸리는 시간을 줄였습니다. 기능별 PDF 매뉴얼을 만들어 관리 화면에 버튼으로 제공했고, 분기별 시연과 전사 워크숍으로 운영 방법을 전달했습니다.

![장애 대응 표준화 프로세스](/assets/images/portfolio/pms-ops.svg)

## 남긴 것과 한계

기간별 작업자가 원격으로 배분·라벨링·저장·검수를 수행하는 운영 환경과, 담당자가 바뀌어도 반복 가능한 배포·장애 대응 절차를 남겼습니다. 다만 100명 이하 규모라 배포 시간 전후 수치 같은 지표는 수집하지 못했고, 자동 롤백과 중앙화된 모니터링 없이 로그 확인 → 수정 → 재배포로 대응했습니다. 장애 매뉴얼은 시스템 변경과 함께 갱신되지 않으면 빠르게 낡는다는 것도 배웠습니다 — 갱신 책임과 주기를 정하는 것까지가 문서화라는 것이 이 프로젝트의 교훈입니다.
