# 공정 관리 솔루션(PMS) — 라벨링 작업을 멈추지 않게 하는 운영

AI 학습데이터 라벨링(3D 포인트 클라우드·2D 이미지·PDF)을 기간별 작업자 최대 100명이 원격 수행하는 웹 시스템입니다. Java REST API·관리 페이지 개발, 프로젝트별 툴 커스터마이징, 그리고 배포·장애 대응을 담당했습니다. 업무 흐름은 아래 그림 한 장이 전부입니다 — 이 페이지의 나머지는 이 시스템에서 실제로 겪은 장애 두 건의 기록입니다.

![PMS 업무 흐름 — 매니저 배분, 작업자 라벨링, 검수 반려 루프, 검수 통과분만 JSON 납품](/assets/images/portfolio/pms-workflow.svg)

## 트러블슈팅 ① — "앞부분만 저장되고 뒤가 사라졌어요"

가장 많은 문의는 저장에서 나왔습니다. 뒷부분 파일이 저장에 실패하고, 같은 작업이 두 번 저장돼 보인다는 문의가 반복됐습니다.

**원인은 자동 라벨링과 저장 단위가 맞물린 것이었습니다.** 툴에는 한 프레임에서 객체 하나를 지정하면 폴더 안의 나머지 프레임에서 같은 객체를 추적해 자동 생성하는 기능이 있는데, 기반 오픈소스의 저장은 **로드된 프레임 전체의 모든 객체를 요청 하나로 전송**하는 구조였습니다. 클릭 한 번으로 불어난 결과가 그대로 한 요청에 실리면서 요청이 서버의 저장 처리에 도달하지 못하고 끊겼습니다.

서버까지 도달해도 문제가 남았습니다. 서버는 객체 단위 INSERT를 반복하는데 요청 전체를 감싸는 트랜잭션 없이 **한 건마다 개별 커밋**했습니다. 도중에 끊기면 앞부분은 커밋되고 뒷부분은 사라집니다 — 작업자가 본 "앞은 저장, 뒤는 유실"은 부분 저장이 아니라 **부분 커밋**이었습니다.

**조치는 한 번에 보내는 양을 줄이는 방향이었습니다.** 저장을 프레임 단위로 나눠 요청 크기가 폴더 전체에 비례하지 않게 했고, 파일 이동 시점 저장과 창 닫기 확인 안내로 마지막 파일이 저장 없이 빠져나가는 경로를 막았습니다. 증상·원인·코드 위치·조치 순서는 오류 문서로 남겨 같은 장애에 문서만 보고 대응하게 했습니다.

![자동 라벨링과 저장 단위가 맞물린 지점](/assets/images/portfolio/pms-auto-save.svg)

**한계도 그대로 남깁니다.** 요청 하나를 한 트랜잭션으로 묶는 구조 변경은 도입하지 못했습니다 — 운영 중인 툴이라 저장 경로 전체를 건드리면 회귀 범위가 라벨링 작업 전체가 되기 때문에, 유실을 즉시 줄이는 조치를 먼저 넣고 구조 변경은 미뤘습니다. 지금 다시 한다면 실패 시 전부 되돌아가는 트랜잭션 경계를 먼저 만들고 그 위에서 전송량을 줄였을 것입니다. 부분 커밋은 데이터가 절반만 맞는 상태를 남기고, 그건 저장이 아예 안 되는 것보다 발견이 늦습니다.

## 트러블슈팅 ② — 같은 객체가 둘로 보이는 3D 중복

중복은 다른 경로였습니다. 3D 저장은 중복 키를 갱신하는 방식이었지만 유니크 키가 프레임·배분 번호에 더해 **객체의 클래스와 순서 번호까지** 묶여 있어, 클래스나 번호가 달라지면 갱신이 아니라 새 행으로 들어갑니다. 2D 저장 경로에는 기존 행을 지우고 다시 넣는 처리가 있는 반면 **3D 경로에는 그 정리 호출이 빠져 있어** 새 행이 들어와도 이전 행이 남았습니다.

즉 "저장이 두 번 실행된 것"이 아니라 **갱신과 삭제 중 삭제 쪽이 없어서** 생긴 증상이었습니다. 두 저장 경로를 나란히 놓고 비교해 누락된 정리 호출을 찾았고, 3D 경로에 동일한 삭제-재삽입 처리를 맞춰 넣어 해소했습니다. 증상이 같아 보여도(중복 저장) 원인 경로는 전혀 다를 수 있다는 것 — 재현 조건을 먼저 좁히고 두 경로의 차이를 비교하는 것이 가장 빠른 길이었습니다.

## 운영은 짧게

배포는 GitLab CI 이미지 빌드 후 수동 배포로 운영했습니다 — 작업자 전원의 작업 종료 확인 후에만 배포 가능하고 배포 직후 동작 확인까지 사람이 해야 하는 조건이라, 시점은 사람이 정하되 배포 전 확인 항목(포트·방화벽·컨테이너 연결)을 문서로 고정해 누가 해도 같은 결과가 나오게 했습니다. 화면별 PDF 매뉴얼과 서비스 내 매뉴얼 버튼, 분기별 신규 담당자 시연, 팀별 서버 세팅 인계로 운영을 넘길 수 있는 형태로 만들었고, 서버 용량 제약은 납품 검수가 끝난 회차 파일을 삭제하는 운영 규칙으로 풀었습니다. 100명 이하 규모라 배포 지표 수집·자동 롤백·중앙 모니터링 없이 로그 확인 → 수정 → 재배포로 대응한 것이 한계입니다.
