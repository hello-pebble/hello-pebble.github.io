# 공정 관리 솔루션(PMS) — 라벨링 작업을 멈추지 않게 하는 운영

AI 학습데이터 라벨링 작업을 관리자·매니저·기간별 작업자 최대 100명이 원격으로 수행하는 웹 시스템입니다. 3D 라벨링(PCD 포인트 클라우드를 큐보이드로 지정하고 대응하는 2D 이미지에 좌표를 투영), 2D 이미지 라벨링, PDF 라벨링 세 종류의 툴을 다뤘습니다. 프로젝트별 툴 커스터마이징과 Java REST API·관리 페이지 개발, 그리고 **배포와 장애 대응을 재현 가능한 절차로 만드는 일**을 담당했습니다.

## 무엇이 문제였나

초기에는 프로젝트 매니저가 로컬 프로그램을 작업자 PC에 설치하고 엑셀 파일명 기준으로 작업물을 배분·회수했습니다. 설치 파일을 가진 사람이 자리에 없으면 그 시간만큼 작업이 멈췄고, 이 반복이 웹 전환의 출발점이었습니다. 웹 전환 후에도 Java WAR, Nginx, Docker, DB가 분리돼 있어 포트·방화벽·컨테이너 연결 설정이 하나만 어긋나도 작업자 전체가 접속하지 못했습니다. 배포가 담당자 개인의 기억에 묶여 있는 것이 실제 리스크였습니다 — 접속 불가는 곧 라벨링·검수·납품 일정 전체의 정지였기 때문입니다.

## 시스템이 다루는 업무

**권한을 편의가 아니라 결과물 보호 기준으로 나눴습니다.** 매니저는 자료 등록·배분, 작업 현황과 근태 조회, 1:1 문의 답변, 공지 등록, 휴가 승인을 할 수 있지만 **작업자가 만든 라벨링 결과는 열람만 가능하고 직접 수정할 수 없습니다.** 결과물이 그대로 납품 데이터가 되기 때문에, 작업자–검수 경로 밖에서 값이 바뀌는 통로를 만들지 않았습니다. 수정과 삭제 권한은 관리자에게만 두었습니다.

**근태와 급여를 시스템 안에 넣은 이유는 무급휴가였습니다.** 작업자는 서비스 로그인 시점에 출근이 기록되고, 휴가는 유급·무급을 구분해 신청한 뒤 매니저 승인으로 확정됩니다. 기간별 작업자는 무급휴가 사용에 따라 매달 실지급액이 달라지므로, 본인이 근무일과 급여를 직접 확인할 수 있어야 문의가 줄어듭니다. 급여 화면은 복지 기능이 아니라 이 계산의 근거를 공개하는 화면이었습니다.

**작업의 끝은 납품이었습니다.** 상태는 `배분 완료 → 작업중 → 완료 → 검수 → 반려 → 수정`으로 흐르고, 반려–수정은 오류가 0이 될 때까지 반복합니다. 최종 승인으로 완료 처리된 건에 한해 프로젝트별 규격의 JSON 다운로드가 열리도록 해, 검수를 통과하지 않은 데이터가 납품 경로로 나갈 수 없게 했습니다. 프로젝트마다 중점 항목이 달라 툴 커스터마이징과 확인용 통계 화면도 함께 맞췄습니다.

**배분은 자동 분배 대신 매니저의 폴더 단위 수동 배분으로 두었습니다.** 작업자마다 속도 차이가 크기 때문에, 처음에 균등하게 나누면 빨리 끝낸 사람이 놀고 늦은 사람에게 물량이 남습니다. 매니저가 진행 현황을 보고 여유가 생긴 작업자에게 폴더를 추가로 배분하는 방식이 실제 소진 속도에 더 맞았습니다.

## 어떻게 풀었나

**실행 환경을 컨테이너로 정리했습니다.** Java REST API·관리 페이지는 WAR로, FastAPI 기반 라벨링 툴 화면은 Nginx로 실행하도록 구성하고, 구현이 안정화된 뒤 Docker Compose로 애플리케이션 구성 요소를 묶었습니다. DB 서버는 분리해 점검 지점을 줄였습니다.

**배포를 절차로 만들었습니다.** develop의 변경이 검토를 거쳐 main에 병합되면 GitLab CI가 이미지를 빌드하고, 빌드 성공을 확인한 뒤 수동으로 배포합니다. 배포까지 자동화하지 않은 것은 운영 조건 때문입니다 — 배포는 작업자들의 작업 종료 확인을 받은 뒤에만 가능했고, 배포 직후 동작 확인까지 사람이 해야 했습니다. 자동 배포로 시점이 심야·이른 새벽에 잡히면 이 확인을 실제로 수행할 수 없었습니다. 대신 배포 전 확인 항목(포트 포워딩·방화벽·컨테이너 포트 연결)을 문서로 고정해, 시점은 사람이 정하되 절차는 누가 해도 같은 결과가 나오게 했습니다.

![GitLab CI/CD 배포 파이프라인](/assets/images/portfolio/pms-pipeline.svg)

**가장 많은 문의는 배포가 아니라 저장에서 나왔습니다.** 같은 작업이 두 번 저장되고, 뒷부분 파일은 저장에 실패하며, 저장하지 않고 창을 닫아 작업분이 사라졌다는 문의가 반복됐습니다.

원인은 **툴의 자동 라벨링 기능과 저장 단위가 맞물린 것**이었습니다. 툴에는 한 프레임에서 객체 하나를 지정하면 폴더 안의 나머지 프레임에서 같은 객체를 추적해 자동으로 라벨링하는 기능이 있습니다. 작업 효율을 위한 핵심 기능이지만, 클릭 한 번으로 폴더 전체에 객체가 생성됩니다. 그런데 기반이 된 오픈소스의 저장은 현재 프레임이 아니라 **로드된 프레임 전체의 모든 객체를 모아 요청 하나로 전송**하는 구조였습니다. 자동 라벨링으로 불어난 결과가 그대로 한 요청에 실리면서, **요청이 서버의 저장 처리에 도달하지 못하고 끊겼습니다.**

서버까지 도달한 경우에도 문제가 남았습니다. 서버는 객체 단위로 INSERT를 반복하는데, 요청 전체를 감싸는 트랜잭션 없이 **INSERT 한 건마다 개별 커밋**하는 구조였습니다. 그래서 처리 도중 끊기면 **이미 커밋된 앞부분은 남고 뒷부분은 통째로 사라졌습니다.** 작업자가 본 "앞은 저장됐는데 뒤는 날아갔다"는 부분 저장이 아니라 부분 커밋이었습니다.

중복은 다른 경로였습니다. 3D 저장은 중복 키를 갱신하는 방식이었지만, 유니크 키가 프레임·배분 번호에 더해 **객체의 클래스와 순서 번호**까지 묶여 있었습니다. 그래서 클래스나 번호가 달라지면 갱신이 아니라 새 행으로 들어갑니다. 2D 저장 경로에는 기존 행을 지우고 다시 넣는 처리가 있는 반면 3D 경로에는 **그 정리 호출이 빠져 있어**, 새 행이 들어와도 이전 행이 그대로 남았습니다. 같은 객체가 둘로 보이는 증상은 저장이 두 번 실행돼서가 아니라, 갱신과 삭제 중 삭제 쪽이 없어서 생긴 것이었습니다.

조치는 한 번에 보내는 양을 줄이는 방향이었습니다. 저장을 **프레임 단위로 각각 처리**하도록 바꿔, 자동 라벨링으로 결과가 아무리 늘어나도 요청 하나의 크기가 폴더 전체에 비례하지 않게 했습니다. 파일 이동 시점에 해당 파일이 저장되도록 하고, 창을 닫을 때는 저장 여부를 확인하는 안내를 띄워 마지막 파일이 저장 없이 빠져나가는 경로를 막았습니다. 라벨링 결과가 곧 납품물이라 한 건의 유실도 재작업으로 이어지므로, 이후에도 Nginx·Docker 로그에서 증상과 원인을 확인해 수정하고 화면 캡처·코드 위치·조치 순서를 오류 문서로 남겼습니다. 같은 장애가 다시 왔을 때 문서만 보고 바로 위치를 찾게 하는 것이 목적이었습니다.

**운영을 넘길 수 있는 형태로 만들었습니다.** 서비스 동작 순서대로 화면마다 기능과 조작 방법을 번호로 설명한 PDF 매뉴얼을 만들고, 기능이 몰린 자료 등록·배분 화면에는 서비스 안에 매뉴얼 버튼을 두어 작업하면서 볼 수 있게 했습니다. 분기별로 새로 프로젝트를 맡은 담당자에게 실제 동작을 시연했고, 워크숍에서는 전 사원 대상으로 유튜브 라이브로 공유했습니다. 프로젝트 시작마다 팀별 서버 세팅을 맡아 그 팀이 이후 서버를 직접 관리할 수 있도록 사용법을 인계했습니다. 특히 서버 용량이 넉넉하지 않아 **납품이 여러 차례로 나뉘는 특성을 이용해, 납품 검수가 끝난 회차의 파일은 서버에서 삭제하도록 운영 규칙으로 정했습니다.**

## 남긴 것과 한계

기간별 작업자가 원격으로 배분·라벨링·저장·검수를 수행하는 운영 환경과, 담당자가 바뀌어도 반복 가능한 배포·장애 대응 절차를 남겼습니다. 다만 100명 이하 규모라 배포 시간 전후 수치 같은 지표는 수집하지 못했고, 자동 롤백과 중앙화된 모니터링 없이 로그 확인 → 수정 → 재배포로 대응했습니다.

저장 장애도 끝까지 가지는 못했습니다. 한 번에 보내는 양을 줄여 실패 자체를 드물게 만들었을 뿐, **요청 하나를 한 트랜잭션으로 묶는 작업은 도입하지 못했습니다.** 운영 중인 툴이라 저장 경로 전체를 건드리면 회귀 범위가 라벨링 작업 전체가 되기 때문에, 유실을 즉시 줄이는 조치를 먼저 넣고 구조 변경은 뒤로 미뤘습니다. 지금 다시 한다면 실패 시 전부 되돌아가는 경계를 먼저 만들고, 그 위에서 전송량을 줄였을 것입니다 — 부분 커밋은 데이터가 절반만 맞는 상태를 남기고, 그건 저장이 아예 안 되는 것보다 발견이 늦습니다. 장애 매뉴얼은 시스템 변경과 함께 갱신되지 않으면 빠르게 낡는다는 것도 배웠습니다 — 갱신 책임과 주기를 정하는 것까지가 문서화라는 것이 이 프로젝트의 교훈입니다.
