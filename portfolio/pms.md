<span class="badge outline">회사 프로젝트</span>

## Project Overview {#overview}

- **구분**: 회사 프로젝트
- **기간**: 2022.11 ~ 2024.12 (2년 1개월)
- **기술 스택**: Java, Spring Boot, FastAPI, JavaScript, MyBatis, Docker, Docker Compose, Nginx, GitLab CI, MariaDB
- **사용자**: 관리자·매니저·기간별 라벨링 작업자 — 최대 100명 이하
- **서비스**: 2D·3D(PCD) 이미지와 PDF의 AI 학습데이터 라벨링, 작업 배분·검수·근태·휴가·급여 조회 지원
- **핵심 역할**: 프로젝트별 툴 커스터마이징, Java REST API·관리 페이지 및 FastAPI 기반 툴 운영, Docker 배포·서버 초기 설정, 로그 기반 장애 대응과 사용자 매뉴얼 작성

---

## Intent (설계 의도) {#intent}

작업자는 배분받은 라벨링 결과물을 서비스에서 저장·검수받아야 합니다. 배포 오류로 서비스에 접속하지 못하면 작업 배분부터 라벨링·저장·검수까지 모두 멈추므로, 작업 시작 전 안정적으로 접속 가능한 환경을 준비하고 배포·장애 대응 절차를 재현 가능하게 만드는 것을 우선했습니다.

---

## Problem (문제 정의 및 원인 분석) {#problem}

- **기존 방식**: 초기에는 프로젝트 매니저가 로컬 프로그램을 작업자 PC에 설치하고, 엑셀 파일명 기준으로 작업물을 배분·회수했습니다. 설치 파일을 가진 담당자를 기다려야 하는 경우도 있었습니다.
- **문제**: 웹 서비스 전환 후에도 Java WAR, Nginx, Docker, DB가 분리돼 있어 포트·방화벽·컨테이너 연결 설정이 어긋나면 작업자가 접속할 수 없었습니다.
- **운영 영향**: 저장 중복·저장 실패·저장하지 않은 채 창을 닫아 작업이 유실되는 문의는 라벨링 결과물의 품질과 납품 일정에 직접 영향을 줬습니다.

---

## Solution (해결 과정) {#solution}

1. **컨테이너 기반 실행 환경 정리**
   - Java REST API·관리 페이지는 WAR로, FastAPI 기반 라벨링 툴 화면은 Nginx로 실행되도록 구성했습니다.
   - 초기에는 서비스를 각각 확인했지만, 구현이 안정화된 뒤에는 Docker Compose로 애플리케이션 구성 요소를 묶고 DB 서버는 분리해 점검 지점을 줄였습니다.
2. **GitLab CI 이미지 빌드와 수동 배포 절차**
   - develop 브랜치의 변경이 검토를 거쳐 main에 병합되면 이미지를 빌드하도록 구성했습니다.
   - 이미지 빌드 성공을 확인한 뒤 수동으로 배포를 진행했습니다. 빌드부터 이미지 생성·서버 배포까지 담당했고, 배포 전 포트 포워딩·방화벽·컨테이너 포트 연결을 확인했습니다.

![GitLab CI/CD 배포 파이프라인](/assets/images/portfolio/pms-pipeline.svg)
3. **로그 기반 장애 대응과 운영 문서화**
   - Nginx·Docker 로그에서 증상과 원인을 확인하고, 코드 수정 후 화면 캡처와 코드 위치, 조치 순서를 오류 문서에 남겼습니다.
   - 서비스 기능별 PDF 매뉴얼을 만들고, 작업 중에도 확인할 수 있도록 관리 화면에 매뉴얼 버튼을 제공했습니다.
   - 프로젝트 담당자 대상 분기별 시연과 전사 워크숍 라이브 공유로 운영 방법을 전달했습니다.

![장애 대응 표준화 프로세스](/assets/images/portfolio/pms-ops.svg)

## Implementation Evidence (구현 근거) {#evidence}

- 배포 다이어그램에 `main 병합 → 이미지 빌드 → 확인 후 수동 배포` 흐름과 실행 구성 요소를 표시했습니다.
- 장애 대응 다이어그램에 `로그 확인 → 증상·원인 파악 → 코드 수정 → 화면·코드 위치 기록` 흐름을 정리했습니다.
- 프로젝트별 서버 초기 설정, 툴 커스터마이징, 통계 조회와 납품용 JSON 결과 다운로드 기능을 지원했습니다.

---

## Results (확인 가능한 변화) {#results}

- 기간별 라벨링 작업자가 원격으로 접속해 작업 배분·라벨링·저장·검수 흐름을 수행할 수 있는 웹 운영 환경을 구성했습니다.
- GitLab CI로 이미지 빌드 조건을 정리하고, 배포 전 확인 항목을 통해 수동 배포 절차를 반복할 수 있게 했습니다.
- 서비스 기능 매뉴얼과 오류 대응 문서를 만들어, 각 팀 매니저가 기능·운영 문의를 전달하고 확인할 수 있는 기준을 마련했습니다.

---

## Limitations (한계 및 후속 과제) {#limitations}

- 최대 사용 인원이 100명 이하인 기간제 업무 시스템이어서 대규모 트래픽 지표나 배포 시간의 전후 수치를 수집하지 못했습니다.
- 자동 롤백과 중앙화된 실시간 모니터링은 구축하지 않았습니다. 서비스 중단 시 이전 버전을 자동 복구하는 대신, 로그를 확인해 원인을 수정하고 재배포하는 방식으로 대응했습니다.
- 파일 용량이 큰 환경이므로 프로젝트 종료·납품 확인 뒤 서버의 완료 파일을 정리하도록 안내했습니다. 파일 보관 정책과 용량 알림을 자동화하는 것은 후속 과제입니다.
- 장애 매뉴얼은 시스템 변경과 함께 갱신되지 않으면 빠르게 오래된 정보가 되므로, 정기 점검 책임과 갱신 주기를 정해야 합니다.
