# 공정 관리 솔루션 — 중복 작업 배분과 저장 유실 방지

![PMS 업무 흐름 — 매니저 배분, 작업자 라벨링, 검수 반려, 검수 통과 데이터 납품](/assets/images/portfolio/pms-workflow.svg)

## 만든 것과 담당 범위

기간별 최대 약 100명의 작업자가 3D 포인트 클라우드, 2D 이미지, PDF에서 AI 학습데이터를 만드는 웹 시스템입니다. 매니저의 자료 배분부터 작업, 검수, 반려, 납품까지 한 서비스에서 처리합니다.

Java REST API와 관리 페이지를 개발하고 프로젝트별 라벨링 툴 연동, 배포, 장애 대응, 사용자 교육을 담당했습니다. 아래 내용은 그중 직접 문제를 확인하고 수정한 범위입니다.

**이 경험으로 바로 맡을 수 있는 업무** — Java·Spring 기반 기존 시스템 분석, 관리자 화면과 API 수정, 역할별 데이터 검증, 저장 오류 재현, 배포와 운영 대응

## 해결 사례 1 — 동일 자료의 작업자 중복 배분 차단

### 문제 원인

매니저가 한 사람에게 자료를 배분하고 바로 다른 사람에게 연속 배분하면, 첫 번째 배분 결과가 화면에 반영되기 전에 같은 자료가 다시 선택될 수 있었습니다. 실제 라벨링이 시작되면 두 작업자가 같은 자료를 각각 처리하게 됩니다. 작업자별 결과 데이터는 분리돼도 사용자는 중복 배분을 시스템 오류로 인식할 수 있고, 불필요한 작업이 생기는 흐름이었습니다.

배분 완료 뒤 목록과 선택 상태를 다시 읽는 순서가 빠져 있었습니다. 백엔드에도 같은 자료가 동일한 작업자 권한에 이미 배분됐는지 확인하는 조건이 없어, 화면에서 오래된 상태를 보내면 그대로 처리될 수 있었습니다.

### 해결 과정

1. 배분 완료 뒤 서비스 목록을 다시 읽고 선택 상태를 갱신하도록 화면의 처리 순서를 수정했습니다.
2. 화면 상태와 관계없이 백엔드가 자료의 기존 배분 상태를 다시 확인하도록 검사를 추가했습니다.
3. 자료가 이미 배분됐다는 이유로 모든 역할을 막으면 검수가 불가능해지므로 권한을 함께 비교했습니다.
4. 동일한 작업자 권한에는 중복 배분하지 않고, 작업 결과를 확인하는 검수자는 같은 자료를 받을 수 있게 했습니다.

### 테스트·확인

현재 확인된 사실은 수정 후 운영 서버에 배포했다는 것까지입니다. 제출 전에 아래 테스트를 당시 실제로 수행했는지 기억과 기록을 확인해야 합니다.

- 같은 자료를 같은 작업자 권한의 두 사용자에게 연속 배분했을 때 두 번째 배분이 거부되는지
- 먼저 작업자에게 배분한 자료를 검수자에게 배분할 수 있는지
- 갱신 전 화면에서 배분 요청을 보내도 백엔드 검사가 막는지

수행 여부를 확인하지 못하면 포트폴리오에는 테스트했다고 쓰지 않고, 면접에서 구현 조건만 설명합니다.

### 결과

화면 갱신과 백엔드 검증을 함께 적용해 같은 작업자 역할 사이의 중복 배분 경로를 차단했습니다. 작업자와 검수자가 같은 자료를 다뤄야 하는 정상 흐름은 유지했습니다. 당시 중복 배분 발생 건수를 별도로 집계하지 않아 감소율은 적지 않습니다.

## 해결 사례 2 — 저장 유실처럼 보인 증상을 네 경로로 분리

### 문제 원인

작업자가 저장했는데 뒷부분이 사라지거나, 저장되지 않은 채 종료되거나, 3D 객체가 중복으로 보인다는 문의가 발생했습니다.

| 구분 | 확인한 원인 |
| :--- | :--- |
| 요청 크기 | 자동 라벨링 결과가 늘어날수록 로드된 전체 프레임의 객체를 한 요청에 전송했습니다. |
| 저장 경계 | 객체 단위 INSERT가 요청 전체 트랜잭션 없이 건별로 반영돼 중간 실패 시 앞부분만 남았습니다. |
| 종료 흐름 | 저장하지 않고 파일을 이동하거나 창을 닫는 경로가 열려 있었습니다. |
| 3D 중복 | 2D 저장 경로에 있던 기존 행 정리 호출이 3D 경로에 빠져 이전 행이 남았습니다. |

### 해결 과정

- 자동 저장이 불러온 전체 객체를 누적 전송하던 것을 선택된 객체만 보내도록 줄였습니다.
- 그러자 같은 객체 재저장 시 키 충돌이 드러나, 무조건 INSERT를 `ON DUPLICATE KEY UPDATE`로 바꿔 재저장이 반복돼도 결과가 같아지게 했습니다.
- 파일 이동 시 자동 저장을 실행하고 창을 닫을 때 확인 안내를 추가했습니다.
- 증상, 재현 조건, 원인, 코드 위치와 조치 순서를 오류 문서로 남겼습니다.

### 테스트·확인

- 자동 라벨링 후 저장되는 요청의 데이터 범위를 확인해 전체 폴더 객체가 함께 전송되는 지점을 찾았습니다.
- 중간 실패 뒤 DB에 앞부분만 남는 상태를 건별 커밋 흐름과 대조했습니다.
- 2D와 3D 저장 코드를 나란히 비교해 3D 경로에만 빠진 기존 행 정리 호출을 확인했습니다.
- 파일 이동과 창 종료 경로를 각각 확인해 자동 저장과 종료 안내가 실행되는 위치를 분리했습니다.

자동 회귀 테스트를 남겼다는 기록은 없어 수동 확인 이상의 검증은 주장하지 않습니다.

### 결과

요청 하나의 데이터량이 폴더 전체가 아니라 프레임 한 개의 객체 수에 비례하도록 바뀌었습니다. 미저장 종료와 3D 이전 행 잔존 경로도 각각 막았습니다. 운영 중인 라벨링 저장 경로 전체의 회귀 범위가 커 요청 전체 트랜잭션으로 재구성하지는 못했습니다.

## 해결 사례 3 — 서버 설정 누락과 반복 문의를 운영 절차로 전환

### 문제 원인

서버별 포트·경로·런타임 설정이 담당자 기억에 있어 설정 하나가 다르면 전원이 접속하지 못했습니다. Docker Compose로 실행 환경을 고정하고 포트, 방화벽, 컨테이너 연결을 배포 전 체크리스트로 만들었습니다. 작업 종료 확인과 배포 직후 점검이 필요해 이미지 빌드까지만 자동화하고 실제 배포는 수동 승인으로 남겼습니다.

사용자 조작 방법도 담당자의 구두 설명에 의존해 같은 문의가 반복됐습니다.

### 해결 과정

- Docker Compose로 애플리케이션 실행 환경을 고정했습니다.
- 포트 포워딩, 방화벽, 컨테이너 포트를 배포 전 확인 항목으로 만들었습니다.
- 작업자가 모두 종료한 뒤 배포하고 즉시 확인해야 하는 업무 조건을 반영해 빌드는 자동화하되 배포 실행은 수동 승인으로 남겼습니다.
- 화면별 PDF 매뉴얼과 서비스 안의 매뉴얼 버튼을 만들고, 문의가 들어오면 해당 항목을 보완했습니다.

### 테스트·확인

프로젝트별 서버 구성과 배포 시 체크리스트를 사용했고, 분기별 신규 담당자 시연과 팀별 서버 설정 인계를 진행했습니다. 배포 시간과 장애 복구 시간은 측정하지 않았습니다.

### 결과

당시 집계한 사용 문의는 초기 월평균 20건에서 1년 후 월 1~2건으로 줄었습니다. 설정 누락은 배포 전에 확인할 대상으로 바뀌었지만 발생 건수는 별도로 집계하지 않아 감소율을 적지 않습니다.

## 이 프로젝트 전후의 경력 흐름

2021.04~2022.10은 공무원 시험 준비 기간이 아니라 사내 서비스를 보유한 회사의 개발 직무로 이동하기 위한 Java 웹 개발 교육과 구직 기간이었습니다. 이후 미디어그룹사람과숲에 입사해 이 사내 공정 관리 솔루션을 개발·운영했습니다.

2025.02부터는 상향 지원 과정의 최종·임원면접과 기술면접에서 드러난 부족한 영역을 보완하고 있습니다. 인증·인가, 동시성, 테스트, 배포를 개인 프로젝트로 구현하고, AI 결과를 코드와 테스트로 검토하는 사용법을 익히고 있습니다.

## 공개 범위

회사 소스 코드와 운영 데이터는 공개하지 않습니다. 측정 기록이 있는 문의 건수와 구조상 확인 가능한 요청 단위만 수치로 적었으며, 중복 배분 감소율·배포 시간·장애 복구 시간처럼 당시 측정하지 않은 값은 주장하지 않습니다.
