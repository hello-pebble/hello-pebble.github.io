# 지원 문서 작성 규칙

지원 문서의 목적은 지원자를 멋있게 설명하는 것이 아니라, 채용 담당자가 다음 세 가지를 빠르게 판단하게 만드는 것이다.

1. 무엇을 만들었는가
2. 그 경험이 우리 팀의 일과 겹치는가
3. 지원자가 직접 판단하고 구현한 부분은 무엇인가

문서마다 같은 사실을 반복하더라도 상세 수준은 다르게 한다. 이력서는 선택하게 만들고, 경력기술서는 담당 범위를 확인하게 하며, 포트폴리오는 문제 해결 과정을 검증하게 한다.

---

# 모든 문서에 적용하는 공통 규칙

## 사실과 담당 범위를 먼저 쓴다

- `시스템 안정성을 높였다`보다 무엇을 막거나 바꿨는지 쓴다.
- 팀 전체 결과와 본인이 한 일을 구분한다.
- `참여`, `담당`만 쓰지 않고 수정한 화면, API, 데이터 처리, 배포 범위를 적는다.
- 회사 프로젝트와 개인 프로젝트를 구분한다.
- 사용한 시스템과 직접 개발한 기능을 구분한다. GIS 시스템에서 사용료 기능을 개발했다면 지도 기능을 개발했다고 쓰지 않는다.

## 문장은 본인이 설명할 수 있어야 한다

다음 질문에 자기 말로 답하지 못하는 문장은 제출하지 않는다.

- 왜 문제라고 판단했는가
- 실제 원인은 무엇이었는가
- 어느 계층이나 흐름을 수정했는가
- 다른 방법 대신 그 방법을 선택한 이유는 무엇인가
- 수정 후 무엇을 확인했는가
- 해결하지 못하고 남긴 부분은 무엇인가

AI는 구조 정리와 문장 다듬기에 사용한다. 기술적 사실, 판단 이유, 테스트 결과는 지원자가 제공하고 최종 문장은 본인이 다시 읽어 표현을 확정한다.

## 증거 수준에 맞춰 표현한다

| 증거 수준 | 사용할 수 있는 표현 | 예시 |
| :--- | :--- | :--- |
| 측정값이나 기록이 있음 | 전후 수치와 기간을 표시 | 문의 월평균 20건 → 1~2건 |
| 코드·테스트·구조로 확인 가능 | 차단된 경로나 달라진 처리 단위를 표시 | 동일 작업자 권한의 중복 배분 차단 |
| 당시 수행했지만 기록이 없음 | 구현 사실과 확인 범위만 표시 | 화면 갱신 순서와 백엔드 검사를 수정 |
| 기억이나 추정만 있음 | 확인 전에는 삭제하거나 검토 표시 | 안정성이 크게 향상됨 |

`향상`, `최적화`, `효율화`, `유연성 확보`, `안정성 강화`는 그 뒤에 무엇이 얼마나 달라졌는지 붙일 수 있을 때만 사용한다.

## 하나의 수치는 하나의 기준을 가진다

- 측정 기간과 단위를 함께 확인한다.
- 추정치를 정확한 값처럼 쓰지 않는다.
- 팀 전체 수치를 본인의 성과로 단정하지 않는다.
- 전후 값을 측정하지 않았다면 작업 단계, 검증 지점, 요청 단위처럼 구조적 변화를 쓴다.
- 하나의 수치에는 하나의 원인 설명을 붙인다. 원인이 여럿이면 여럿이라고 쓰고, 문서마다 다른 원인을 앞세우지 않는다.

## 문서 사이의 값이 어긋나지 않게 한다

이력서·경력기술서·자기소개서·포트폴리오는 함께 읽힌다. 한 문서에서만 맞는 문장은 나머지 문서가 반증한다.

- 같은 프로젝트의 기술 스택, 기간, 인원, 역할, 수치는 모든 문서에서 같은 값을 쓴다.
- 원본 자료끼리 값이 충돌하면 추정해서 고르지 않는다. 확인 전까지 그 항목을 빼고 확인할 것에 남긴다.
- 개발 환경과 운영 환경이 달랐다면 어느 쪽인지 함께 적는다. 한쪽만 적으면 다른 문서의 값과 충돌한다.
- 검증 범위는 모든 문서에서 같은 강도로 쓴다. 회사 운영 환경에서 확인한 것과 개인 프로젝트에서 확인한 것은 문서마다 같은 방식으로 구분한다. 한 문서에서 `검증했다`, 다른 문서에서 `하지 못했다`가 되면 둘 다 신뢰를 잃는다.
- 결과의 강도(줄었다 / 멈췄다 / 없앴다)를 문서마다 다르게 쓰지 않는다. 확인 가능한 범위에서 가장 약한 표현으로 맞춘다.
- 한 항목 안에서 앞뒤 문장이 서로를 부정하지 않는지 확인한다. `DB·App·Web을 컨테이너화했다`와 `DB는 컨테이너 밖에 뒀다`는 함께 설 수 없다. 구성요소별로 무엇이 어디에 있었는지 적는다.
- 지난 공고의 제출본을 복사해 출발점으로 삼지 않는다. 출발점은 언제나 원본이다. 이전 문서를 복사하면 그 문서의 오류까지 함께 복사된다.

## 요건 충족은 기술 단위로 따진다

- 공고가 특정 기술의 실무 연수를 요구하면(예: Spring Boot 3년 이상) 총 경력으로 충족한다고 적지 않는다.
- 총 경력과 특정 스택의 사용 기간을 나눠 적는다. 나눌 수 없으면 총 경력만 적고 그 스택의 기간은 면접에서 설명한다.
- 유사 경험을 요구 기술로 바꿔 적지 않는다. 셸 스크립트 스케줄링은 Python 배치가 아니고, 개인 데모 배포는 클라우드 운영 경험이 아니다.

# 이력서 작성 규칙

## 목적

채용 담당자가 짧은 시간 안에 면접 검토 여부를 결정하게 한다.

## 순서

1. 이름과 지원 직무
2. 어떤 시스템을 만들어 왔는지 설명하는 2~3문장
3. 바로 맡을 수 있는 업무
4. 최신순 경력과 프로젝트별 대표 결과
5. 실제 사용 기술
6. 개인 프로젝트와 공백기
7. 학력과 자격

## 작성 기준

- 첫 문단에 Java 개발자라는 말만 쓰지 않고 라벨링 공정 관리, 공공데이터 API, 사내 교육 시스템처럼 만든 대상을 쓴다.
- 공고와 겹치는 경력을 위로 올린다.
- 회사 하나당 대표 문제 해결 1~3개만 남긴다.
- 각 항목은 `만든 것 → 직접 한 일 → 확인된 결과` 순으로 쓴다.
- 기술 스택에는 실제 업무에서 사용한 기술과 개인 프로젝트 기술을 구분한다.
- 이력서만 읽어도 총경력과 재직기간을 계산할 수 있게 한다.
- 상세 설계와 긴 회고는 포트폴리오로 보낸다.
- 공고의 필수요건 중 경험이 얕은 항목은 그대로 두지 않는다. 지금 가진 가장 가까운 구현 사례를 한 가지 연결한다. 실무가 얕으면 개인 프로젝트에서 실제로 구현하고 테스트한 사례를 적는다.
- 근거로 드는 개인 프로젝트에는 기간과 저장소 링크를 함께 적는다. 공백기 설명의 근거도 된다.

## 쓰지 않는 내용

- 성격을 증명하지 않는 추상적인 자기평가
- 프로젝트의 모든 기능 목록
- 긴 기술 선택 비교
- 측정하지 않은 효과
- 면접용 단점 설명

# 경력기술서 작성 규칙

## 목적

실제 투입 가능한 업무와 프로젝트별 담당 범위를 확인하게 한다.

## 순서

1. 총경력과 핵심 직무
2. 바로 맡을 수 있는 업무
3. 전체 경력 흐름
4. 최신순 회사와 프로젝트
5. 프로젝트별 서비스, 역할, 기술, 문제 해결, 결과
6. 공백기의 준비 내용과 산출물
7. 개인 프로젝트로 보완한 기술
8. 전체 기술 목록

## 프로젝트 작성 기준

- 서비스가 무엇인지 1~2문장으로 설명한다.
- 팀 구성과 본인의 담당 범위를 적는다.
- 가장 강한 문제 해결 사례를 먼저 배치한다.
- 결과가 회사 전체 성과인지 본인 수정 결과인지 구분한다.
- 운영 반영, 개발 서버 적용, 개인 재구현을 구분한다.
- 공개할 수 없는 회사 코드 대신 요청 흐름, 데이터 조건, 역할 규칙처럼 면접에서 설명할 수 있는 기술적 사실을 적는다.
- 같은 회사의 서로 다른 시스템은 프로젝트를 나눠 적는다. 사용자 역할·업무 용어가 어느 시스템의 것인지 원본에서 확인되지 않으면 싣지 않는다.

## 공백기 작성 규칙

공백기는 변명이 아니라 `기간 → 목표 → 행동 → 결과`로 쓴다.

- **2021.04~2022.10** — 사내 서비스를 보유한 회사의 개발 직무로 이동하기 위해 Java 웹 개발 교육과 구직 준비를 진행했고, 이후 미디어그룹사람과숲의 사내 공정 관리 솔루션 담당으로 입사했다.
- **2025.02~현재** — 2025년 상향 지원 과정의 최종·임원면접과 기술면접에서 부족한 기술 설명과 검증 역량을 확인했다. 이후 인증·인가, 동시성, 테스트, 배포를 개인 프로젝트로 구현하고 AI 결과를 코드와 테스트로 검토하는 작업 방식을 익히고 있다.

두 번째 공백은 아직 취업이라는 결과가 없으므로 `공부 중`으로 끝내지 않는다. 저장소, 테스트, 배포, 기술 문서처럼 현재 확인 가능한 산출물을 함께 제시한다.

# 포트폴리오 목록 페이지 작성 규칙

## 목적

채용 담당자가 지원 직무와 겹치는 문제 해결 사례를 선택해 들어가게 한다.

## 프로젝트 카드에 넣을 내용

1. 만든 시스템의 이름
2. 기간과 회사·개인 프로젝트 구분
3. 대표 문제 한 가지
4. 해결로 달라진 구체적인 상태
5. 실제 핵심 기술

카드는 발표 슬라이드의 요약 문구가 아니다. 상세 페이지에서 증명할 수 있는 내용만 예고한다.

## 정렬 기준

- 지원 공고와 가장 겹치는 프로젝트를 먼저 둔다.
- Java·JSP 유지관리 공고라면 PMS, 개방DB, LMS, 항만 시스템을 먼저 둔다.
- 인증 플랫폼 공고라면 OAuth2, AdminCore 같은 개인 프로젝트를 위로 올릴 수 있다.
- 최신 프로젝트라는 이유만으로 관련성이 낮은 프로젝트를 앞에 두지 않는다.

# 프로젝트 상세 포트폴리오 작성 규칙

## 목적

지원자가 어떤 문제를 자기 방식으로 이해하고 해결했는지 상세하게 보여준다. 프로젝트 전체 소개서나 발표자료로 만들지 않는다.

## 페이지 순서

1. **제목** — 만든 시스템과 대표 문제를 함께 표시
2. **대표 그림** — 사용자 흐름, 데이터 흐름 또는 문제 발생 지점
3. **서비스와 담당 범위** — 이해에 필요한 만큼만 설명
4. **문제 해결 사례 나열**
5. **기술과 공개 가능한 근거**
6. **한계와 해결하지 못한 부분**
7. **경력 흐름** — 공백기 설명이 필요한 제출본에서만 간단히 표시

## 문제 해결 사례의 고정 순서

### 문제 원인

- 어떤 사용 순서나 데이터 상태에서 발생했는가
- 사용자나 운영에 어떤 영향을 줄 수 있었는가
- 처음 보인 증상과 실제 원인은 무엇이었는가

### 해결 과정

- 문제를 어떻게 재현하고 범위를 좁혔는가
- 어느 화면, API, 서비스, 쿼리 또는 배포 흐름을 수정했는가
- 어떤 업무 규칙을 코드 조건으로 옮겼는가
- 다른 해결책을 선택하지 않은 이유는 무엇인가

### 테스트·확인

- 수정 전 문제를 어떤 순서로 재현했는가
- 정상, 실패, 권한별, 동시 요청 등 어떤 시나리오를 확인했는가
- 자동 테스트인지 수동 확인인지 구분한다.
- 테스트하지 않은 시나리오는 테스트했다고 쓰지 않는다.

### 결과

- 차단된 오류 경로
- 줄어든 문의나 작업 단계
- 달라진 요청·저장 단위
- 정상적으로 유지된 예외 흐름
- 남은 한계

결과에는 `그래서 무엇이 달라졌는가`가 보여야 한다. 수치가 없다면 변경 전후의 처리 흐름을 비교한다.

## 한계를 쓰는 분량

한계는 반드시 적되, 읽고 남는 것이 미완료 보고가 되지 않게 한다.

- 순서는 `적용한 조치 → 확인한 결과 → 남은 한계`다. 한계를 조치보다 먼저 쓰지 않는다.
- 남은 한계 설명이 조치와 결과보다 길면 줄인다. 솔직함이 목적이고 자기 감점이 목적이 아니다.
- 사례마다 어느 시스템·회사·기간의 것인지 제목과 메타에 적는다. 원본에서 소속이 확인되지 않는 사례는 싣지 않고, 확인된 다른 사례로 교체한다.

## 그림 사용 규칙

- 페이지 처음에는 서비스 전체 흐름 그림 하나를 둔다.
- 추가 그림은 원인이나 해결 구조를 글보다 명확히 설명할 때만 사용한다.
- 장식용 이미지, 기술 로고 모음, 의미 없는 화면 캡처는 넣지 않는다.
- 그림의 화살표와 명칭은 본문 용어와 일치시킨다.

# 공고별 수정 규칙

공고마다 새로운 이력서를 처음부터 만들지 않는다. 사실은 유지하고 순서와 강조점만 바꾼다.

| 공고 | 먼저 보여줄 경험 |
| :--- | :--- |
| Java·JSP·공공 SI 유지관리 | PMS 운영, 공공데이터 API, LMS, 항만 시스템 |
| 사내 서비스 백엔드 | PMS 문제 해결, 개방DB 엔진, 지속적인 운영 개선 |
| 솔루션 개발·기술지원 | 장애 원인 분석, 사용자 문의 감소, 배포 체크리스트 |
| 인증·플랫폼 | LMS RBAC, AdminCore, OAuth2 Gateway |
| 데이터·API 플랫폼 | 개방DB 엔진, api-forge, 정부 공문서 처리 |

공고에 없는 기술을 억지로 추가하지 않는다. 직접 일치하는 경험, 옮겨 쓸 수 있는 경험, 없는 필수 경험을 구분한다.

# 제출 전 확인표

- [ ] 첫 세 문장에서 만든 시스템과 담당 업무가 보인다.
- [ ] 공고와 가장 겹치는 경험이 먼저 나온다.
- [ ] `우리`, `팀`의 결과를 본인 단독 성과처럼 쓰지 않았다.
- [ ] 본인이 직접 한 동사로 문장이 시작된다.
- [ ] 모든 수치의 기준과 기간을 설명할 수 있다.
- [ ] 문제 원인과 해결 방법 사이의 논리가 이어진다.
- [ ] 테스트 방식과 확인 결과를 구분했다.
- [ ] 측정하지 않은 효과를 삭제했다.
- [ ] 회사 프로젝트와 개인 프로젝트의 범위를 구분했다.
- [ ] 공백기를 기간·행동·결과로 설명했다.
- [ ] 모든 문장을 면접에서 자기 말로 다시 설명할 수 있다.

네 문서를 나란히 놓고 대조한다.

- [ ] 같은 프로젝트의 기술 스택·기간·인원이 네 문서에서 같다.
- [ ] 같은 수치의 원인 설명이 네 문서에서 같다.
- [ ] 검증 범위(회사 운영 / 개발 서버 / 개인 프로젝트)를 네 문서에서 같은 강도로 적었다.
- [ ] 같은 결과를 문서마다 다른 강도로 쓰지 않았다.
- [ ] 한 항목 안에서 앞뒤 문장이 서로를 부정하지 않는다.
- [ ] 공고가 요구한 특정 스택의 사용 기간을 총 경력으로 대체하지 않았다.
- [ ] 포트폴리오의 모든 사례가 원본에서 소속이 확인되는 것이다.
