# A. 주요 프로젝트 3. MatchSimulation — 교체 가능한 경계를 먼저 설계한 매칭 서비스 백엔드 (개인)

| | |
| :--- | :--- |
| **역할** | 요구사항 정의 · 도메인 경계 설계 · API 구현 · 인증/스키마 교체 · 채팅 수신 구조 진화 · 동시성 검증 (단독) |
| **기간** | 2026.06 ~ 진행 중 · phase마다 계획서와 완료 보고서를 쌍으로 |
| **핵심 성과** | 인증·스키마 **2개 접점 실교체 후 회귀 테스트 51건 통과** · 채팅 수신 4단계 실측(빈 응답 **90% → 0**, push 지연 **9ms**) · 계획서·보고서 **29건 공개** |
| **기술** | Java 21, Spring Boot 4.1, JPA, Flyway, Spring Security/JWT, WebSocket, Gradle 9 |

[github.com/hello-pebble/MatchSimulation](https://github.com/hello-pebble/MatchSimulation)

AI 소개팅 서비스를 가정한 매칭 백엔드. 가입·추천·수락·1:1 채팅·관리자 흐름을 구현하면서, **"나중에 반드시 바뀔 부분"의 경계를 먼저 긋고 실제로 그 경계를 따라 교체하며** 설계가 통하는지 확인해 왔다.

## 핵심 문제

실무에서 인증 방식이나 스키마 관리 도구를 바꿀 때 그 변경이 어디까지 번지는지 예측하기 어려웠다. **"잘 분리했다"는 설계 문서만으로는 확인되지 않는다.** 실시간 기능도 마찬가지로, 처음부터 WebSocket을 쓰는 것이 맞는지 판단할 근거가 없었다.

## 핵심 의사결정

**1. 경계를 먼저 긋고 실제로 교체해서 검증했다.** 처음부터 Spring Security를 깔지 않고 더미 토큰으로 시작한 것은, 핵심 매칭 흐름을 먼저 완성해 회귀 테스트를 갖춘 뒤 갈아타야 교체가 검증이 되기 때문이다. **테스트 없이 교체하면 그건 검증이 아니라 재작성이다.**

| 교체 접점 | 이전 | 이후 |
| :--- | :--- | :--- |
| **인증** | UUID 더미 토큰 + 평문 비밀번호 | Spring Security + JWT(HS256) + BCrypt. 인증 헤더와 에러 응답 포맷을 유지해 **API 계약 무변경**, 위조·만료·정지 계정 엣지케이스를 계획서에 먼저 정의한 뒤 교체 |
| **스키마 소유권** | Hibernate `ddl-auto: create-drop` | Flyway `V1__init.sql`. Hibernate는 `validate`로 강등해 **엔티티–스키마 불일치 시 기동 실패**가 안전장치가 되도록 |
| **추천 엔진** | 규칙 기반 구현체 | 인터페이스 유지, 설정만으로 구현체 전환 확인(서비스 코드 무변경) |

**2. 채팅 수신은 측정한 뒤 다음 단계로 넘어갔다.** 가장 단순한 구조부터 시작해 각 단계의 비용을 숫자로 확인했고, 서버 API 계약(`afterId` 증분 조회)은 1단계에서 고정해 전 단계가 재사용했다.

| 단계 | 실측 |
| :--- | :--- |
| Short Polling(3초) | 30초에 1건 수신하는 동안 요청 10회·빈 응답 9회(**90%**)·전달 지연 최대 3초 |
| Long Polling(`DeferredResult`) | 같은 조건에서 요청 2회·빈 응답 0~1회·전달 지연 ≈ 0 |
| WebSocket | push 지연 **9ms**·핸드셰이크 13ms |

**3. 알림은 트랜잭션 커밋 이후에.** Long Polling 대기자에게 메시지 저장 트랜잭션 **안에서** 알리면, 대기자가 커밋 전 데이터를 조회해 새 메시지를 놓친다. 대기자는 `ConcurrentHashMap` 레지스트리가 보관하다 `onTimeout`·`onCompletion` 콜백으로 제거해 누수를 막았다.

## 대표 구현 — WebSocket 단계

**STOMP를 쓰지 않기로 결정했다.** 구독 대상이 matchId 하나뿐이라 브로커·구독 프로토콜 계층이 과했고, 핸드셰이크·세션 관리·브로드캐스트를 직접 다루는 쪽이 목적에 맞았다. 인증은 `HandshakeInterceptor`에서 연결 수립 전에 JWT·정지 계정·매칭 참여자를 검증해 **실패한 연결은 열리지도 않는다.** "매칭이 ACCEPTED인 경우에만 연결 허용" 같은 규칙은 앞서 만든 상태 전이 지점을 그대로 재사용했다.

검증은 목이 아니라 **실제 연결**로 했다 — 롱폴링은 MockMvc `asyncDispatch`로 비동기 응답 사이클을, WebSocket은 `StandardWebSocketClient`로 랜덤 포트 서버에 직접 접속해 핸드셰이크 거부·세션 누수·REST 전송 → WebSocket 수신 교차까지 확인한다.

## 검증 결과

| 검증 항목 | 확인 결과 |
| :--- | :--- |
| 인증 교체 | JWT·BCrypt 전환 후 전체 회귀 통과 · 위조/만료/정지 계정 엣지케이스 확인 |
| 스키마 이전 | Flyway 적용 이력 검증 · `validate` 모드에서 전체 테스트 통과 |
| 매칭 동시성 | 동시 수락·거절 시 `@Version` 낙관적 락으로 1건만 성공(409) · 알림 저장 실패 시 상태 변경도 롤백 |
| API 회귀 | JUnit 5 `@SpringBootTest` 기반 **51건**을 phase마다 green 유지 |

phase마다 **계획 문서**로 배경·설계·엣지케이스·테스트 계획을 고정하고 **완료 보고서**에 회귀 결과와 curl 실측을 기록했다. Short Polling 계획서의 목표였던 "구조적 비용을 실측으로 남긴다"가 실제로 다음 phase의 근거가 됐고, 이렇게 쌓인 plan→report 쌍 29건이 저장소에 공개돼 있다.

## 회고

**교체 가능성은 설계로 주장할 수 없고 실제 교체로만 증명된다.** 경계를 그어두는 것과 그 경계가 실제로 버티는 것은 다른 문제였고, 인증 교체에서 API 계약을 유지한 채 내부만 바꿀 수 있었던 것이 그 증명이었다. 실시간 기능도 처음부터 WebSocket으로 갔다면 Long Polling으로 충분한 구간이 있었는지 영영 몰랐을 것이다.

**한계** — H2 인메모리 기반이라 대규모 트래픽·다중 인스턴스는 검증 범위 밖이다. 규칙 기반 추천 점수(지역·나이·직군)는 실제 선호를 설명하기에 얕고, 외부 AI 엔진은 어댑터 구조까지만 준비된 상태다. 다음 단계는 PostgreSQL 전환(Flyway 이전이 그 포석)과 운영 관측성이다.

# B. 주요 프로젝트 3. Gateway 기반 인증·인가 검증 (개인)

| | |
| :--- | :--- |
| **역할** | 인증 구조 설계 · JWT/Refresh Token 발급 · JWKS 기반 검증 · Gateway 라우팅 · 동시성 락 설계 · Compose 통합 구성 (단독) |
| **기간** | 2026.01 ~ 2026.03 · 기술 검증 프로젝트 |
| **핵심 성과** | 접근 제어 **4개 시나리오 실요청 검증** · Ordered Lock 적용 후 **10스레드 동시 상호 선택에서 매칭 정확히 1건** · **6개 모듈** Compose 통합 기동 · TDR·Decision Log 등 **문서 56건** 공개 |
| **기술** | Kotlin, Spring Boot, Spring Security, OAuth2/JWT, Spring Cloud Gateway(WebFlux), PostgreSQL, Docker Compose |

[github.com/hello-pebble/oauth2-authorization](https://github.com/hello-pebble/oauth2-authorization)

인증 서버가 JWT를 중앙 발급하고 Gateway·Resource Server가 각자 검증하는 구조를 6개 모듈(Auth·Gateway·Matching·Task·Preview·Admin)로 직접 구성한 실험이다. 각 모듈의 업무 기능이 아니라 "공개 라우트를 가진 서비스 · 보호 API를 가진 서비스 · 내부 API만 가진 서비스"라는 역할 구분이 핵심이다.

## 핵심 문제

Gateway를 단일 진입점으로 구성했을 때 공개·보호·내부 경로의 접근 제어가 의도대로 동작하는지 확인할 방법이 필요했다. **인증은 설정 한 줄이 통째로 방어를 무력화할 수 있는 영역이라**, 동작한다는 느낌이 아니라 실제 요청과 응답 코드로 확인해야 한다고 봤다.

## 핵심 의사결정

**1. 인증 상태는 Stateless JWT로.** Redis 세션은 즉시 무효화가 가능하지만 **Redis가 단일 장애점**이 되고, Opaque Token은 매 요청 introspection으로 레이턴시가 늘어난다. Auth가 RSA 개인키로 서명하고 공개키를 JWKS로 제공해, 각 서비스가 공개키로 서명·만료를 직접 검증하도록 했다. **감수한 것도 같은 문서에 적었다** — 발급된 토큰의 중앙 회수 어려움, 권한 변경의 즉시 미반영, 키 보관·순환이 새로운 핵심 과제가 된다는 점. 선택하지 않은 것은 코드에서도 걷어냈다(미사용 Redis 의존성 −60줄).

**2. Gateway는 통과, 서비스는 재검증.** 호스트에 공개한 포트는 Gateway의 8000 하나이고, Gateway는 라우팅과 Cookie→Bearer 변환만 담당한다. JWT 서명과 역할 정책은 각 Resource Server가 자신의 규칙으로 다시 판단한다 — **Gateway만 검사하고 내부를 신뢰하는 구조는 진입점이 뚫리는 순간 전부 뚫리기 때문이다.**

**3. 락은 항상 작은 ID부터.** 두 사용자가 서로를 동시에 선택하면 매칭이 누락되거나 중복 생성될 수 있고, 쌍마다 락을 잡으면 반대 순서로 획득하다 데드락이 된다. 구현 전에 **Ordered Locking** 원칙을 설계 문서로 먼저 세웠다 — 락 순서가 전역적으로 일정하면 순환 대기가 성립하지 않아 데드락이 구조적으로 불가능해진다.

## 대표 구현 — 경계별 책임을 실제 요청으로 검증

| 시나리오 | 보장해야 하는 동작 | 확인 결과 |
| :--- | :--- | :--- |
| 1. 공개 경로 | 로그인 화면·JWKS·OIDC metadata는 토큰 없이 접근 | Gateway 경유 접근 확인 |
| 2. 보호 경로 · 토큰 없음 | 보호 API 호출 시 401 | Task·Admin API에서 확인 |
| 3. Admin 경유 인가 | Admin → Matching 호출에서 **양쪽 서비스가 각각** JWT와 관리자 권한 검증 | 양측 검증 확인 |
| 4. 내부 경로 직접 접근 | Gateway에 `/internal/**` 라우트가 없어 외부에서는 404 | `/internal/admin/users` 404 확인 |

이 과정에서 **버그 하나가 비대칭 키 모델을 이해시켰다.** 초기 스모크 테스트에서 정상 JWT가 보호 API에서 401을 받았는데, 추적하니 `JwtProvider`가 토큰 **검증에도 RSA 개인키**를 쓰고 있었다 — 발급자와 검증자가 같은 코드였을 때는 드러나지 않다가 검증을 각 서비스로 분산하자 바로 깨진 것이다. "개인키는 발급 주체만, 공개키는 검증 주체 누구나"가 설정 문법이 아니라 실제 요청 흐름으로 이해된 순간이었다.

## 검증 결과

| 검증 항목 | 확인 결과 |
| :--- | :--- |
| 시나리오 1~4 | 실제 요청으로 전부 확인 |
| 모듈별 빌드 | 6개 애플리케이션 모듈 빌드와 전체 테스트 통과 |
| 통합 실행 | 6개 애플리케이션 + PostgreSQL을 Compose로 기동하고 health 확인 |
| 동시 매칭 경쟁 | Ordered Lock 적용 후 10스레드 동시 상호 선택에서 매칭 정확히 1건 생성 |

기능 하나를 만드는 순서를 **문제 정의 → 접근법 A/B/C 비교 → 설계 문서 → TDD → 버그 리포트 → 시나리오 정리**로 고정했고, 이 사이클이 남긴 문서 56건(TDR 5건, Decision Log, 버그 리포트 등)이 코드와 같은 저장소에서 버전 관리된다.

## 회고

직접 구현해 본 결론은 역설적이다. JWT 발급과 검증 자체는 구현 가능했지만, **키 관리·Refresh Token 보안·표준 준수까지 고려하면 인증 서버의 책임이 빠르게 복잡해졌다.** 검증된 인증 솔루션을 써야 하는 이유와 도입 시 확인할 지점(키 순환, 토큰 폐기, 경계별 재검증)을 몸으로 이해한 것이 이 실험의 가장 큰 수확이다.

**한계** — 상용 인증 서버 수준의 보안성을 검증한 것은 아니다. Auth 재시작 시 RSA 키가 새로 생성돼 기존 JWT가 무효화되며 키 교체·폐기 시나리오는 검증하지 못했다. Refresh Token 탈취 대응, 그리고 Admin → Matching 호출이 사용자 JWT를 전달해 서비스 자체의 신원을 증명하지 못하는 문제(client credentials·토큰 교환·mTLS)가 다음 과제다.

기획부터 데모 배포까지 단독 수행. 확정된 계획의 수정 차단 규칙을 **프론트 → 서버 가드(409) → 도구 노출 권한**으로 옮기며, 규칙을 어디에 두느냐가 곧 강제력임을 확인했다. 20~30초 AI 응답을 **SSE 스트리밍 + patch 교환**으로 전환하고 폴백을 실제로 끊어보며 검증했으며, JUnit 5 **317건**을 단위·MockMvc·Testcontainers 통합으로 분리했다. 에이전트 도구 선택 정확도를 평가 하네스로 **676회 실측**해 "모델이 금지된 도구 대신 인접 도구로 우회"하는 문제를 발견하고, 릴리스 스모크 **57회 통과율 100%** 확인 후 배포했다.
