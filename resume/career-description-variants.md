# A. 주요 프로젝트 3. AdminCore — 운영 관리자 콘솔 백엔드 (개인)

| | |
| :--- | :--- |
| **역할** | 요구사항 정의 · 도메인 경계 설계 · API 구현 · 관리자 기능(회원·QnA·알림·통계) · 인가 설계 (단독) |
| **기간** | 2026.06 ~ 진행 중 · phase마다 계획서와 완료 보고서를 쌍으로 |
| **핵심 성과** | 정지 계정의 **유효 토큰 통과 문제**를 인증 필터에서 차단 · 상태 변경과 통지를 **한 트랜잭션**으로 묶어 "통지 없는 정지" 제거 · 통계에 **TTL 캐시 + 쓰기 시점 무효화**를 함께 적용 |
| **기술** | Java 21, Spring Boot 4.1, JPA, Flyway, Spring Security/JWT, Gradle 9 |

[github.com/hello-pebble/AdminCore](https://github.com/hello-pebble/AdminCore) · [관리자 모드 명세](https://github.com/hello-pebble/AdminCore/blob/main/docs/admin_mode.md)

기존 매칭 서비스의 사용자 모드를 제거하고 **계정과 매칭을 통제·관측하는 운영 관리자 전용 백엔드**로 재정의했다. 관리자는 가입을 승인하고 문제 계정을 정지시키며, 문의에 답하고 공지를 보내고, 매칭이 어떻게 흘러가는지 본다. 관리자 API는 전부 `/api/admin/**` → `hasRole('ADMIN')` 한 규칙으로 묶여 있다.

## 핵심 문제

**관리 도구는 "버튼이 있다"와 "그 버튼이 실제로 듣는다"가 다르다.** 정지 버튼을 눌러도 대상이 계속 서비스를 쓰고 있으면 기능이 없는 것과 같고, 통계 화면이 방금 한 조작을 반영하지 못하면 관측 도구로 신뢰받지 못한다. 관리자 기능을 만들면서 실제로 부딪힌 것이 이 두 가지였다.

## 핵심 의사결정

**1. 발급된 토큰을 믿지 않고 요청마다 계정 상태를 다시 본다.** JWT는 서버가 세션 상태를 들고 있지 않아, 로그인 시점에만 정지 여부를 검사하면 **정지 이전에 발급된 토큰이 만료될 때까지 그대로 통과한다.** 정지가 "앞으로 로그인 불가"까지만 뜻하고 이미 들어온 사람은 막지 못하는 상태가 된다.

인증 필터가 서명을 검증한 뒤 사용자를 조회해 정지 상태면 **인증 자체를 부여하지 않도록** 했다. 서명이 멀쩡해도 통과하지 못한다. 계획서에 "위조 서명 / 만료 토큰 / **정지 계정의 유효 토큰**"을 먼저 적었는데, 앞의 둘은 라이브러리가 잡아주고 실제로 놓치기 쉬운 것은 세 번째였다.

**감수한 것** — 요청마다 사용자 조회가 한 번 늘어 JWT의 stateless 이점을 일부 되돌린다. 그리고 이 차단은 **진입점마다 잊지 않고 검사할 때만 성립한다.** 규칙이 아니라 규율에 기대는 구조라, 토큰 수명을 짧게 두고 갱신 시점에 거르는 방식이 더 안전한 대안이었다.

**2. 상태 변경과 통지를 한 트랜잭션으로 묶었다.** 회원을 승인·정지하면 대상에게 알림이 생성되는데, 이 둘을 `@Transactional` 하나로 묶어 알림 저장이 실패하면 상태 변경도 롤백되게 했다 — **계정은 정지됐는데 당사자는 이유를 모르는 상태**를 만들지 않기 위해서다. 같은 상태로 재저장하는 요청에는 `before != status` 가드로 중복 통지를 막았다.

**다르게 볼 수 있는 지점** — 알림을 비동기 이벤트로 뺐다면 상태 변경이 알림 실패에 발목 잡히지 않는다. 이 규모에서는 "통지 없는 정지"를 막는 쪽이 중요하다고 봤지만, 알림 채널이 외부(메일·푸시)로 늘어나면 뒤집어야 할 판단이다.

**3. 통계는 DB가 집계하고 배치가 바꾸면 캐시를 버린다.** 상태·성별·일별 분포는 PostgreSQL의 `GROUP BY` 3개 쿼리로 계산하고, 전체·성사 건수와 성사율은 상태별 결과에서 파생한다. `@Cacheable` 60초 TTL을 걸되 7일 무응답 만료 배치가 실행되면 `@CacheEvict`로 비운다. 사용자 매칭 쓰기 API는 제거했기 때문에, 캐시 무효화 경계도 현재 남아 있는 유일한 매칭 상태 변경인 배치에 맞췄다.

## 대표 구현 — 관측과 자동 정리

집계는 전체·성사 건수와 성사율, 일별 추이, 성별(요청자 기준) 분포, 상태별 분포(`REQUESTED`·`ACCEPTED`·`REJECTED`·`EXPIRED`)로 구성했다. 7일 무응답 매칭은 스케줄러가 `EXPIRED`로 전이시켜, 관리자가 손대지 않아도 `REQUESTED`가 무한정 쌓이지 않고 **성사율 분모가 오염되지 않는다.**

회원·문의 목록은 관리자 화면이라도 파라미터를 신뢰하지 않는다 — `size`를 최대 100으로 강제하고, 존재하지 않는 정렬 필드는 400으로 막는다.

**성사율의 성격** — 규칙 기반 추천(지역·나이·직군)이라 품질을 직접 잴 수단이 없어 성사율을 대리 지표로 뒀다. 시드 데이터 위의 숫자라 실제 선호를 설명하지는 못한다.

## 검증 결과

| 검증 항목 | 확인 결과 |
| :--- | :--- |
| 정지 계정 차단 | 유효 서명을 가진 정지 계정 토큰이 인증 단계에서 차단됨 |
| 권한 분리 | ADMIN이 아닌 토큰의 `/api/admin/**` 접근이 403으로 거부됨 |
| 트랜잭션 경계 | 알림 저장 실패 시 회원 상태 변경도 롤백 |
| 매칭 동시성 | 동시 수락·거절 시 `@Version` 낙관적 락으로 1건만 성공(409) |
| 자동 만료 | 스케줄러 실행 후 대상 매칭이 `EXPIRED`로 전이되고 통계에 반영 |
| API 회귀 | JUnit 5 `@SpringBootTest` 기반 회귀를 phase마다 green 유지 |

phase마다 **계획 문서**로 배경·설계·엣지케이스·테스트 계획을 고정하고 **완료 보고서**에 회귀 결과와 curl 실측을 기록했다.

## 회고

**관리 기능은 "동작한다"보다 "우회되지 않는다"로 판단해야 한다.** 정지 버튼은 처음부터 동작했지만, 대상이 이미 들고 있던 토큰으로 계속 접근할 수 있다는 것은 엣지케이스를 따로 적어보고서야 드러났다. 인증(토큰이 진짜인가)과 인가(지금도 유효한 사용자인가)는 다른 질문이고, **JWT를 쓰면 후자는 자동으로 따라오지 않는다.**

**한계** — 관리자 조작 이력(누가 언제 누구를 정지시켰는가)을 남기지 않는다. 운영 시스템이라면 감사 로그가 이 기능들보다 먼저 필요하다. 통계 캐시가 인메모리라 다중 인스턴스에서는 무효화가 자기 노드에만 적용되고, H2 인메모리 기반이라 대규모 트래픽은 검증 범위 밖이다.

# B. 주요 프로젝트 3. Gateway 기반 인증·인가 검증 (개인)

| | |
| :--- | :--- |
| **역할** | 인증 구조 설계 · JWT/Refresh Token 발급 · JWKS 기반 검증 · Gateway 라우팅 · 동시성 락 설계 · Compose 통합 구성 |
| **기간** | 2026.01 ~ 2026.03 · 기술 검증 프로젝트 |
| **핵심 성과** | 접근 제어 **4개 시나리오 실요청 검증** · 다중 모듈 **Compose 통합 기동** · 선택하지 않은 대안까지 TDR·Decision Log로 기록 |
| **기술** | Kotlin, Spring Boot, Spring Security, OAuth2/JWT, Spring Cloud Gateway(WebFlux), PostgreSQL, Docker Compose |

[github.com/hello-pebble/oauth2-authorization](https://github.com/hello-pebble/oauth2-authorization)

인증 서버가 JWT를 중앙 발급하고 Gateway·Resource Server가 각자 검증하는 구조를 다중 모듈(Auth·Gateway·Matching·Task·Preview·Admin)로 구성한 실험이다. 각 모듈의 업무 기능이 아니라 "공개 라우트를 가진 서비스 · 보호 API를 가진 서비스 · 내부 API만 가진 서비스"라는 역할 구분이 핵심이다.

## 핵심 문제

Gateway를 단일 진입점으로 구성했을 때 공개·보호·내부 경로의 접근 제어가 의도대로 동작하는지 확인할 방법이 필요했다. **인증은 설정 한 줄이 통째로 방어를 무력화할 수 있는 영역이라**, 동작한다는 느낌이 아니라 실제 요청과 응답 코드로 확인해야 한다고 봤다.

## 핵심 의사결정

**1. 인증 상태는 Stateless JWT로.** Redis 세션은 즉시 무효화가 가능하지만 **Redis가 단일 장애점**이 되고, Opaque Token은 매 요청 introspection으로 레이턴시가 늘어난다. Auth가 RSA 개인키로 서명하고 공개키를 JWKS로 제공해, 각 서비스가 공개키로 서명·만료를 직접 검증하도록 했다. **감수한 것도 같은 문서에 적었다** — 발급된 토큰의 중앙 회수 어려움, 권한 변경의 즉시 미반영, 키 보관·순환이 새로운 핵심 과제가 된다는 점. 선택하지 않은 것은 코드에서도 걷어냈다(미사용 Redis 의존성 −60줄).

**2. Gateway는 통과, 서비스는 재검증.** 호스트에 공개한 포트는 Gateway의 8000 하나이고, Gateway는 라우팅과 Cookie→Bearer 변환만 담당한다. JWT 서명과 역할 정책은 각 Resource Server가 자신의 규칙으로 다시 판단한다 — **Gateway만 검사하고 내부를 신뢰하는 구조는 진입점이 뚫리는 순간 전부 뚫리기 때문이다.**

## 대표 구현 — 경계별 책임을 실제 요청으로 검증

| 시나리오 | 보장해야 하는 동작 | 확인 결과 |
| :--- | :--- | :--- |
| 1. 공개 경로 | 로그인 화면·JWKS·OIDC metadata는 토큰 없이 접근 | Gateway 경유 접근 확인 |
| 2. 보호 경로 · 토큰 없음 | 보호 API 호출 시 401 | Task·Admin API에서 확인 |
| 3. Admin 경유 인가 | Admin → Matching 호출에서 **양쪽 서비스가 각각** JWT와 관리자 권한 검증 | 양측 검증 확인 |
| 4. 내부 경로 직접 접근 | Gateway에 `/internal/**` 라우트가 없어 외부에서는 404 | `/internal/admin/users` 404 확인 |

이 과정에서 **버그 하나가 비대칭 키 모델을 이해시켰다.** 초기 스모크 테스트에서 정상 JWT가 보호 API에서 401을 받았는데, 추적하니 `JwtProvider`가 토큰 **검증에도 RSA 개인키**를 쓰고 있었다 — 발급자와 검증자가 같은 코드였을 때는 드러나지 않다가 검증을 각 서비스로 분산하자 바로 깨진 것이다. "개인키는 발급 주체만, 공개키는 검증 주체 누구나"가 설정 문법이 아니라 실제 요청 흐름으로 이해된 순간이었다.

## 검증 결과

| 검증 항목 | 확인 결과 |
| :--- | :--- |
| 시나리오 1~4 | 실제 요청으로 전부 확인 |
| 모듈별 빌드 | 애플리케이션 모듈 빌드와 전체 테스트 통과 |
| 통합 실행 | 전체 애플리케이션 + PostgreSQL을 Compose로 기동하고 health 확인 |

기능 하나를 만드는 순서를 **문제 정의 → 접근법 A/B/C 비교 → 설계 문서 → TDD → 버그 리포트 → 시나리오 정리**로 고정했고, 이 사이클이 남긴 TDR·Decision Log·버그 리포트가 코드와 같은 저장소에서 버전 관리된다.

## 회고

직접 구현해 본 결론은 역설적이다. JWT 발급과 검증 자체는 구현 가능했지만, **키 관리·Refresh Token 보안·표준 준수까지 고려하면 인증 서버의 책임이 빠르게 복잡해졌다.** 검증된 인증 솔루션을 써야 하는 이유와 도입 시 확인할 지점(키 순환, 토큰 폐기, 경계별 재검증)을 몸으로 이해한 것이 이 실험의 가장 큰 수확이다.

**한계** — 상용 인증 서버 수준의 보안성을 검증한 것은 아니다. Auth 재시작 시 RSA 키가 새로 생성돼 기존 JWT가 무효화되며 키 교체·폐기 시나리오는 검증하지 못했다. Refresh Token 탈취 대응, 그리고 Admin → Matching 호출이 사용자 JWT를 전달해 서비스 자체의 신원을 증명하지 못하는 문제(client credentials·토큰 교환·mTLS)가 다음 과제다.

기획부터 데모 배포까지 단독 수행. 확정된 계획의 수정 차단 규칙을 **프론트 → 서버 가드(409) → 도구 노출 권한**으로 옮기며, 규칙을 어디에 두느냐가 곧 강제력임을 확인했다. 20~30초 AI 응답을 **SSE 스트리밍 + patch 교환**으로 전환하고 폴백을 실제로 끊어보며 검증했으며, 회귀를 단위·MockMvc·Testcontainers 3층으로 고정한 상태에서 리팩터링했다. 육안 판단을 대신할 평가 하네스를 만들어 도구 선택을 반복 측정했고, **"모델이 금지된 도구 대신 허용된 인접 도구로 우회"**하는 문제를 발견했다 — 1회 실행으로는 보이지 않고 구조로도 막을 수 없는 층이었다.
