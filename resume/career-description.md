## 핵심 의사결정

**1. 실행 환경을 이미지로 고정했다.** 장애 원인 대부분이 애플리케이션 버그가 아니라 서버마다 다른 포트·경로·런타임이었다. 같은 WAR가 개발 서버에서는 뜨고 운영 서버에서는 뜨지 않는 문제는 코드로 해결할 수 없다. Docker Compose로 실행 환경을 이미지화해 서버 간 환경 차이를 제거하고, **DB는 컨테이너 밖으로 분리**해 배포 실수가 데이터 손실로 이어지지 않게 했다.

**2. 빌드는 자동, 배포는 수동 승인.** 소스가 이미 GitLab에 있어 관리 지점을 늘리지 않도록 GitLab CI로 이미지 빌드까지 자동화했다. 배포 실행은 수동으로 남겼다 — 작업자들의 작업 종료 확인 후에만 배포가 가능하고 배포 직후 동작 확인을 사람이 해야 하는 운영 조건에서, 자동 배포로 시점이 심야에 잡히면 그 확인을 할 사람이 없기 때문이다. 대신 배포 전 확인 항목(포트 포워딩·방화벽·컨테이너 포트 연결)을 체크리스트로 고정해 누가 해도 같은 결과가 나오게 했다.

**3. 권한을 결과물 보호 기준으로 나눴다.** 라벨링 결과가 그대로 납품 데이터가 되므로, 작업자–검수 경로 밖에서 값이 바뀌면 납품물의 추적성을 보증할 수 없다. 매니저는 배분·현황 조회·문의 답변까지 가능하되 **라벨링 결과는 열람만**, 수정·삭제는 관리자로 한정했다.

## 대표 구현 — 저장 실패 원인 분석과 조치

가장 많은 문의가 나온 저장 장애는 **하나의 증상 뒤에 원인이 셋**이었다.

| # | 원인 |
| :--- | :--- |
| 1 | 자동 라벨링(한 프레임 지정 → 폴더 전체 추적 생성)으로 불어난 결과가, **로드된 전체 프레임의 모든 객체를 요청 하나로 전송**하는 오픈소스 저장 구조와 맞물려 요청이 서버 저장 처리에 도달하기 전에 끊김 |
| 2 | 객체 단위 INSERT를 **요청 전체 트랜잭션 없이 건별 커밋** — 중간에 끊기면 앞부분만 남음. "앞은 저장, 뒤는 유실"은 부분 저장이 아니라 **부분 커밋**이었다 |
| 3 | 3D 저장의 유니크 키에 객체 클래스·순서 번호까지 묶여 값이 바뀌면 신규 행이 되는데, 2D 경로에 있던 **기존 행 정리 호출이 3D 경로에는 누락**돼 이전 행이 잔존 |

조치는 **저장 단위를 프레임 단위로 분할**해 요청 하나의 크기가 폴더 전체에 비례하지 않게 한 것이다. 요청 전체를 한 트랜잭션으로 묶는 근본 조치도 검토했으나, 운영 중인 툴이라 저장 경로 전체를 건드리면 회귀 범위가 라벨링 작업 전체가 된다 — 매일 발생하는 유실을 먼저 멈추고 구조 변경을 뒤로 미뤘다. 함께 파일 이동 시점 자동 저장과 창 닫기 시 확인 안내를 넣어 미저장 종료 경로를 막았고, 조치 후 대량 자동 라벨링 상태에서 저장 성공과 중복 미발생을 확인했다.

**그 외 구현** — 신규 프로젝트마다 요구되는 라벨링 툴 기능 개발과 프로젝트별 커스터마이징 / 작업·검수 모드 분리(최종 승인 건만 규격 JSON 다운로드가 열려 미검수 데이터가 납품 경로로 나갈 수 없음) / 엑셀 기반 대량 사용자 등록 / 출퇴근·유급무급 휴가 승인 간이 HR / 동작·에러·접근 로그 분류 수집과 에러 패턴 기반 장애 대응 매뉴얼

## 핵심 문제

| 문제 | 비즈니스 비용 |
| :--- | :--- |
| 신규 조회 요구사항마다 Controller·Service·ServiceImpl·DAO·SQL XML **5개 파일**(관리 화면 동반 시 6개) 추가. 파라미터는 VO 없이 Map으로 오가 컴파일 검증도 안 됨 | 요구사항 1건 = 개발·리뷰·배포 1사이클 |

| 파라미터 검증·바인드 처리를 빠뜨릴 수 있는 자리가 API마다 존재 | 외부 공개 API에서 누락 하나가 **SQL 인젝션 통로** |

## 핵심 의사결정

**1. 반복을 코드가 아니라 데이터로 옮겼다.** 조회 기능의 공통 부분을 메타데이터와 SQL 변환 엔진으로 모으고 업무별 차이는 설정으로 표현했다. 코드 제너레이터도 검토했지만 파일 수가 그대로 늘어난다. 이 선택은 온보딩 문제와 뿌리가 같다 — 신규 인력이 헤맨 이유는 코드가 많아서가 아니라 **어디를 봐야 하는지 알 수 없어서**였고, 엔진 하나로 모으면 학습 대상이 "엔진 1개 + 메타데이터 규칙"으로 고정된다.

**2. 동적 영역의 경계를 먼저 그었다.** 런타임 조립 SQL은 컬럼·조건 조합마다 DB 방언 차이가 드러나고, 운영 DB는 개발 단계에서 접근할 수 없었다. **동적 영역을 넓힐수록 검증 경로가 `DB 종류 × 조건 조합`만큼 곱으로 늘어나므로** 층을 나눠 처리했다.

| 층 | 대상 | 처리 |
| :--- | :--- | :--- |
| 바깥 | 페이징 | 공통 래퍼를 XML에 고정, 값은 바인드 변수 |
| 중간 | DB 방언 | SQL 맵 세트를 디렉터리 단위로 분리해 설정으로 교체 |
| 안쪽 | 조회 컬럼·조건 | 메타데이터 기반 동적 조립 |

**3. 권한은 되돌릴 수 있는 동작인지로 나눴다.** 신규 데이터 등록과 API 버전 생성은 일반 사용자에게 열었다 — 잘못돼도 내부에서 수정 가능하고, 여기를 막으면 병목이 생겨 시스템을 안 쓰게 된다. 반면 **데이터 개방 여부 설정은 팀장 권한으로 한정**했다. 외부 공개는 되돌릴 수 없고 사업·법적 검토가 필요하기 때문이다. 함께 동일 데이터셋에 **API 버전(v1, v2) 체계**를 도입해, 기존 사용자를 깨지 않으면서 새 요구를 수용하고 두 버전의 관계가 시스템에 기록되게 했다.

## 대표 구현 — 메타데이터 기반 조회 엔진

API 엔드포인트 하나가 메타데이터 테이블의 행 하나다. 데이터셋이 조회 대상 테이블과 URL 키를, 컬럼 정의가 노출 컬럼·허용 필터·정렬 여부를 담고 **여기 등록된 컬럼만** 쓸 수 있다.

| sourceColumn | filterType | sortable | 요청 예시 |
| :--- | :--- | :--- | :--- |
| BILL_ID | EQUALS (=) | ✓ | `?BILL_ID=2200001` |
| COMMITTEE | CHECK (IN) | ✓ | `?COMMITTEE=행정안전위원회,정무위원회` |
| PROPOSE_DT | DATE (BETWEEN) | ✓ | `?PROPOSE_DT=2026-01-01,2026-06-30` |

**인젝션 방어 지점은 엔진 한 곳이다.** SQL에 들어가는 식별자는 요청 파라미터명이 아니라 메타데이터에 저장된 컬럼명이고, 요청 파라미터명은 조회 키로만 쓰이고 버려진다. 연산자도 클라이언트가 아닌 컬럼의 `filterType`이 결정하며, 값은 전부 바인드 파라미터다. 차단 목록이 아닌 화이트리스트라 방어 범위가 규칙 목록의 완전성에 의존하지 않는다.

그 외 데이터 타입 검증, 등록 직후 샘플 URL 호출로 설정 오류를 배포 전에 잡는 장치, Chart.js 기반 호출 통계·인기 데이터셋 대시보드, 레거시 모듈화와 API 명세서·설계 문서 작성, iBatis → MyBatis 전환을 수행했다.

## 검증 — 미완의 검증을 재구현으로

로컬·개발 서버에서 메타데이터 등록만으로 신규 API가 동작하는지, 미등록 컬럼·미허용 정렬이 차단되는지 확인했으나 **운영 반영 전 이직해 실트래픽 검증은 수행하지 못했다.**

그 검증을 대신하기 위해 핵심 구조를 비식별화해 현대 스택으로 재구현한 것이 **[api-forge](https://github.com/hello-pebble/api-forge)**(개인 프로젝트 · 2026.07 ~ · Java 21 · Spring Boot 3.5 · jOOQ · Testcontainers)다. 회사 코드를 가져오지 않고 설계 의도만 옮긴 클린룸 재구현이다.

**무엇을 확인하려 했나** — 화이트리스트 방어가 실제 공격 입력에서 성립하는지, 그리고 그 방어가 DB 방언에 의존하지 않는지. **어떻게 확인했나** — 세 가지 공격 시나리오를 매 커밋 CI에서 돌리고, 같은 시나리오를 H2와 PostgreSQL(Testcontainers) 양쪽에 두었다.

| 공격 입력 | 결과 |
| :--- | :--- |
| 미등록 컬럼으로 필터 요청 | `400` 거부 |
| `BILL_ID; DROP TABLE …` 파라미터명 위장 | `400` 거부 |
| `' OR '1'='1` 값 주입 | 문자열 리터럴로 바인드 |

**그래서 무엇을 확인했나** — 요청 파라미터명이 SQL에 진입하지 않으므로 방어가 규칙 목록의 완전성에 의존하지 않고, 두 방언에서 동일하게 성립한다. 재구현에서는 **jOOQ 타입 세이프 DSL + 식별자 화이트리스트**를 방어의 단일 지점으로 두고, 파라미터는 DTO + Bean Validation으로 받으며, 인증키는 해시로 저장해 저장소가 유출돼도 키 자체는 복원되지 않게 했다.

## 회고

**추상화의 이득은 검증 비용과 함께 계산해야 한다.** "모든 것을 설정으로" 밀어붙였다면 공수는 더 줄었겠지만, 접근할 수 없는 운영 DB를 상대로 조합 폭발한 검증 경로를 감당할 수 없었을 것이다. 페이징을 고정 래퍼로 남긴 판단이 가장 실용적이었다.

**설정으로 옮긴 문제는 사라지지 않고 위치를 바꾼다.** 코드 오류가 메타데이터 오류가 됐을 뿐이라, 재구현에서 식별자 규칙 검증과 발행 전 소스 테이블 실존 확인을 넣었지만 발행 후 스키마 변경 감지는 과제로 남았다. 다만 회사 코드를 가져올 수 없다는 제약 때문에 검증을 포기하는 대신, 구조만 재구현해 테스트로 증명하는 방법이 있다는 것을 확인했다.

| | |
| :--- | :--- |
| **역할** | 기획 · 데이터 모델링 · API 설계 · 프론트/백엔드 구현 · 평가 하네스 · 데모 배포 (단독) |
| **기간** | 2026.04 ~ 2026.06 · v0.1.0 ~ v0.17.0, 버전마다 문제 하나를 정해 해결 |
| **핵심 성과** | "확정 후 수정 불가" 규칙을 프론트 → 서버 가드 → **도구 권한**으로 이관해 구조적으로 불가능하게 만듦 · 육안 판단을 평가 하네스로 바꿔 **모델의 권한 우회 경로 발견** · 회귀를 3층으로 고정한 상태에서 리팩터링 |
| **기술** | Java, Spring Boot, React, PostgreSQL, OpenRouter, Docker, GitHub Actions, Oracle Cloud |

[github.com/hello-pebble/DelayNoMore_Release](https://github.com/hello-pebble/DelayNoMore_Release) · [데모](https://delaynomoreapp.duckdns.org/)

AI와 대화해 하루 단위 계획을 만들고, **확정 후에는 완료 체크와 이월만 허용**하는 서비스. 각 버전이 직전 버전이 드러낸 문제 하나를 해결하는 방식으로 진행했다.

## 핵심 의사결정

**1. 규칙의 소유권을 프론트에서 서버로, 다시 도구 권한으로.** "확정된 계획은 수정할 수 없다"는 규칙이 세 번 자리를 옮겼다.

| 단계 | 위치 | 결과 |
| :--- | :--- | :--- |
| v0.4.1 | 프론트 버튼 차단 | **curl로 API를 직접 호출하면 그대로 뚫림** — 화면의 규칙은 UX일 뿐 강제가 아니다 |
| v0.8.0 | 서버 가드 `409 PLAN_LOCKED` | 프론트는 안내, 강제는 서버. 이후 진행률·이월·날짜 검증까지 프론트의 규칙을 서버로 이관 |
| v0.14~15 | 선언적 전이표 → **도구 노출 권한** | AI 코치를 도구 호출 에이전트로 전환할 때 전이표가 그대로 도구 권한이 되면서, 수정 차단이 **애초에 수정 도구를 주지 않는 구조적 불가능**이 됨 |

전이는 `SELECT … FOR UPDATE` 행 잠금 안에서 원자적으로 실행되어 동시 완료 요청 시 첫 요청만 성공한다. 전이 매트릭스는 전수 검증 테스트로, 생성 한도 같은 동시 요청 경쟁은 20스레드가 `CountDownLatch` 이중 배리어로 동시에 진입하는 TOCTOU 테스트로 고정했다.

**2. 20~30초 AI 응답 — 모델을 낮추는 대신 대기를 진행 경험으로.** 응답 품질이 서비스의 핵심 가치라 모델을 낮추면 기능 자체가 의미를 잃는다. `SseEmitter` 기반 SSE 스트리밍으로 생성 과정을 그대로 보여주고, 계획 전체를 매번 재전송하던 방식을 **변경분(patch) 교환**으로 바꿔 토큰을 줄였다. 에이전트 루프와 SSE 전송 사이에는 `AgentEventSink`를 두어 루프를 SSE 없이 단위 테스트할 수 있게 분리했고, 스트림 실패 시 비스트리밍 → mock 폴백을 실제로 끊어보며 확인했다.

**3. 숫자는 서버 규칙이, 이유는 AI가.** 회고 기록으로 다음 계획 분량을 추천할 때 계산을 LLM에 맡기지 않았다 — 같은 기록에 추천이 달라지면 신뢰를 줄 수 없고, 외부 API 장애가 곧 기능 장애가 되기 때문이다. AI가 실패해도 서버 템플릿으로 초안은 나온다.

## 대표 구현 — 육안 확인을 평가 하네스로

AI 코치를 도구 호출 에이전트로 전환하자 **프롬프트나 모델을 바꿨을 때 좋아졌는지 판단할 수단이 없었다.** 기능 추가를 멈추고 실제 모델로 도구 선택 정확도를 재는 평가 하네스를 먼저 만들었다(케이스 데이터셋, 순수 함수 채점기, 정확도·토큰 비용 리포트).

**무엇을 확인하려 했나** — 프롬프트나 모델을 바꿨을 때 좋아졌는지. 그리고 "고정된 계획에는 수정 도구를 주지 않는다"는 권한 모델이 실제 모델에서도 지켜지는지.

**어떻게 확인했나** — 채점 대상을 도구 선택 하나로 좁혔다. 답변 문장의 품질은 사람 판단이나 심판 모델이 필요해 비싸고 흔들리는데, 그걸 넣는 순간 하네스가 "가끔 빨간불이 켜지는 물건"이 되어 아무도 안 보게 된다. 정답이 이산적인 축만 남겨 회귀 신호를 날카롭게 했다.

**결과가 세 번 바뀌었다** — 처음에는 특정 케이스가 실패한다고 봤지만 반복하니 실패가 케이스를 옮겨 다녔다. 반복을 늘리자 기저 실패율이 예상의 절반으로 수렴했다. 마지막으로, **모델이 금지된 도구 대신 허용된 인접 도구로 우회**하고 있다는 것이 드러났다 — 고정된 계획에 항목 추가를 요청하자 수정 도구가 없는 모델이 **이월 도구로 계획을 실제로 바꿨다.**

**그래서 무엇을 결정했나** — 이월은 그 상태에서 정상 노출되는 도구라 금지 목록에 넣을 수 없었다. 넣으면 정상적인 이월 요청까지 사고로 보고되고 빌드가 깨진다. 그래서 채점 범주를 갈랐다 — **막혀서 못 하는 것과, 할 수 있는데 하지 말아야 하는 것은 다르다.** 후자는 통과율에는 실패로 반영하되 빌드는 깨뜨리지 않는다. 둘을 같은 칸에 넣으면 진짜 사고가 모델 잡음에 묻히기 때문이다.

## 검증과 배포

테스트를 순수 단위 / standalone MockMvc / `*IT` 통합(Testcontainers PostgreSQL) 세 층으로 나누고, 실제 모델 호출 평가는 `@Tag("eval")`로 일반 빌드에서 제외했다 — 외부 API에 의존하는 검증이 일반 빌드를 막으면 아무도 테스트를 돌리지 않게 되기 때문이다. 매 push마다 GitHub Actions CI가 실행된다. 잠금 상태 수정 요청 409, 동시 완료 요청 시 첫 요청만 성공, 재시작 후 상태 복원, 스트리밍 폴백을 각각 시나리오로 확인했다.

배포는 프론트·백엔드·AI 프록시를 단일 Docker 컨테이너로 묶어 GitHub Actions가 빌드해 GHCR에 올리고, **Oracle Cloud 무료 VM(1GB)은 Pull만 해서 실행**한다 — 저사양 VM에서 빌드가 자원을 점유하면 서비스가 멈추기 때문이고, JVM 힙 상한으로 OOM을 방어했다.

## 회고

**규칙을 어디에 두느냐가 곧 그 규칙의 강제력이다.** 프론트 차단 → 서버 가드 → 도구 권한으로 옮겨온 과정이 가장 값진 학습이었다. 그리고 **출력이 흔들리는 대상은 한 번의 실행으로 판단하면 안 된다** — 반복 측정 없이는 우회 경로처럼 구조로 막을 수 없는 문제를 아예 발견하지 못한다.

**한계** — 데모 배포라 운영 트래픽과 장애 대응은 검증하지 못했고 실사용자 효과 지표가 없다. 생성 한도 가드가 `synchronized` 기반이라 다중 서버에서는 한도가 최대 1건 초과될 수 있다.
