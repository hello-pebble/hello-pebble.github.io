# 개방DB 관리 시스템 설계 및 프로토타입 개발

<span class="badge outline">회사 프로젝트</span>

> 데이터 스키마 추상화 기반의 **Generic API 엔진**을 설계하여, 개별 API를 빨리 만드는 것이 아니라 "API를 만들 필요가 없는 구조" 자체를 목표로 한 프로젝트입니다.

---

## Project Overview

- **구분**: 회사 프로젝트
- **기간**: 2024.09 ~ 2025.01 (5개월)
- **기술 스택**: Java, JSP, Spring MVC, MyBatis, MariaDB, Apache Tomcat
- **핵심 역할**: 설계 기획, Generic SQL 변환 엔진 설계 및 버전 관리 로직 구현

---

## Intent (설계 의도)

반복되는 조회성 API 개발은 개발자의 시간을 소모할 뿐 팀의 자산으로 남지 않는다고 판단했습니다. 요구사항이 올 때마다 유사한 코드를 찍어내는 방식을 유지하는 한, 인력이 늘어도 생산성은 늘지 않습니다.

그래서 이 프로젝트의 목표를 "N번째 API를 빠르게 만드는 것"이 아니라, **데이터 구조를 메타데이터로 추상화하여 조회 요구사항이 코드 변경 없이 흡수되는 구조**를 만드는 것으로 설정했습니다.

---

## Problem (문제 정의 및 원인 분석)

- **문제**: 신규 인력 온보딩이 빈번히 지연되었고, 새로운 요구사항이 있을 때마다 유사한 조회 API를 반복 개발하여 개발 생산성이 지속적으로 저하되었습니다.
- **원인**: 데이터 테이블 스키마에 결합된 **하드코딩 방식의 API 개발이 고착화**되어 있었으며, 비구조화된 레거시 코드가 누적되어 유지보수 비용이 기하급수적으로 상승했습니다.

---

## Solution (해결 과정)

![Generic API 엔진 - 개발 방식의 구조적 전환](/assets/images/portfolio/dbms-generic-engine.svg)

1. **데이터 스키마 추상화 관리 체계 수립**
   - 하드코딩된 API 엔드포인트 개발 방식을 탈피하기 위해, 데이터 구조를 유연하게 메타데이터화하는 **스키마 추상화 레이어**를 도입했습니다.
2. **Generic API 엔진 설계 및 리플렉션 응용**
   - MyBatis의 동적 쿼리 생성과 Java Reflection API 개념을 응용했습니다.
   - 사용자가 UI에서 선택한 메타데이터(컬럼·조건) 조합을 실시간으로 파싱하여 실행 가능한 SQL로 자동 변환하는 **Generic API 엔진**을 구축했습니다.
3. **API 버전 관리 체계 구축**
   - 무중단 기능 확장을 위해 라우팅 버저닝 시스템을 도입하여, 운영 중인 서비스에 영향(Side Effect) 없이 기능을 개편·추가할 수 있도록 보장했습니다.

---

## Results (최종 성과)

- **생산성 극대화**: 신규 조회성 API 추가에 따른 코드 작성이 불필요해져, **신규 API 개발 공수를 0건화(완전 자동화)**했습니다.
- **온보딩 비용 감소**: 하드코딩된 소스코드를 모듈식 아키텍처로 개편하여, 신규 인력의 코드 분석·적응 기간을 **기존 대비 50% 단축**했습니다.
