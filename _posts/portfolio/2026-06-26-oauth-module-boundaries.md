# 컨테이너 분리에서 변경 경계 분리로

- 실행 위치만 나뉜 구조에서 코드와 변경 책임이 계속 섞이는 문제를 경험
- 함께 변경되는 기능과 정책을 기준으로 6개 실행 모듈의 경계를 정의

{% include oauth-project-nav.html %}

## 배경

PMS의 신규 기능은 별도 Docker 컨테이너로 실행했지만 기존 프로젝트 구조와 코드를 폭넓게 공유했습니다. 기능 하나를 배포하기 위해 담당 기능과 무관한 코드와 의존성까지 함께 가져가는 경우가 생겼습니다.

여러 팀원이 같은 코드 영역을 병렬로 수정하면서 Merge Conflict가 반복됐고, 장애가 발생하면 어느 기능의 변경만 되돌리면 되는지보다 함께 수정된 범위 중 어디까지 원복해야 하는지를 먼저 판단해야 했습니다.

## 문제를 어떻게 해석했는가

원인은 Docker가 아니라 **실행 단위와 변경 단위가 일치하지 않는 구조**라고 판단했습니다.

- 컨테이너는 분리됐지만 기능별 소스 경계가 모호했습니다.
- 공통 프로젝트를 공유해 담당자별 수정 범위가 겹쳤습니다.
- 한 기능의 변경이 다른 기능의 빌드와 실행 파일에도 포함됐습니다.

따라서 컨테이너 수를 늘리는 대신 함께 변경되는 코드와 정책을 기준으로 모듈을 나눴습니다.

## 모듈 경계

| 모듈 | 소유하는 책임 | 경계 밖 책임 |
| :--- | :--- | :--- |
| **Auth** | 로그인, 계정, JWT 발급, JWKS 제공 | 리소스 서비스의 업무 정책 |
| **Gateway** | 외부 진입점, 라우팅, Cookie→Bearer 변환 | JWT와 역할 정책 판단 |
| **Matching** | 매칭 프로필, 노출·차단 상태, 관리자용 내부 API | 계정과 작업 기능 |
| **Task** | 사용자 작업 API | 매칭과 관리자 정책 |
| **Preview** | 로그인·인가 흐름 확인 화면 | 업무 데이터 처리 |
| **Admin** | 관리자 API, Matching 연계 | Matching 상태 직접 소유 |

각 애플리케이션은 별도의 소스 디렉터리와 빌드·실행 설정을 가집니다. 변경 파일, 테스트 실패, 실행 대상을 기능 모듈 단위로 추적할 수 있는 구조를 만들었습니다.

## 확인한 점

- 한 기능의 코드와 정책을 해당 모듈에서 찾아 수정할 수 있습니다.
- 6개 애플리케이션을 각각 빌드한 뒤 Compose에서 함께 실행할 수 있습니다.
- Admin이 Matching의 상태를 직접 소유하지 않고 내부 API를 통해 요청합니다.
- 사용하지 않는 Redis·Redisson 의존성과 테스트 대역을 제거해 실제 책임과 빌드 구성을 맞췄습니다.

## 이 구조가 해결하지 않는 것

현재는 하나의 저장소를 사용하는 모노레포입니다. 따라서 모듈 경계가 개발자의 소스 열람 권한까지 제한하지는 않습니다. 소스 접근을 분리하려면 저장소 분리, CODEOWNERS 또는 별도의 권한 정책이 필요합니다.

또한 모듈별 독립 CI/CD와 버전 정책은 구성하지 않았습니다. 이 프로젝트에서 검증한 범위는 **코드·빌드·실행 경계를 기능별로 나눌 수 있는가**까지입니다.
