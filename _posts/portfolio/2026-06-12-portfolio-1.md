# DelayNoMore <span class="badge">개인 프로젝트</span>

> "계획을 고칠 수 있다는 여지"가 미루기를 만든다고 보고, 계획을 확정하는 순간 수정·삭제 권한을 박탈하는 **잠금(Immutable Lock) 모델**을 검증한 서비스입니다.
> **Spring Boot(Java 21) + React + PostgreSQL** 풀스택으로 직접 설계·구현하고, **단일 컨테이너로 배포**하며 **AI 호출 비용까지 튜닝**한 백엔드 중심 프로젝트입니다.

## 콘셉트 — "계획은 신중하게, 실행은 강제로"

AI 코치가 목표·기간·가용 시간을 대화로 수집해 **하루 단위 실행 계획**을 만들고, 사용자가 확정하면 그 계획은 **완료 체크만 허용**되는 잠금 상태로 들어갑니다. 수정·삭제라는 도피로를 구조적으로 없애 미루기를 차단하는 것이 서비스의 핵심 가설입니다.

![DelayNoMore 사용자 워크 프로세스](/assets/images/portfolio/delaynomore-flow.svg)

시스템은 프론트엔드·백엔드·AI 프록시를 **하나의 Docker 컨테이너**로 묶어 배포됩니다. Spring Boot가 빌드된 React 정적 파일과 `/api/v1` REST·SSE를 함께 서빙하고, OpenRouter 키는 서버에만 보관하며, 상태는 PostgreSQL(Supabase)에 영속화됩니다.

![시스템 아키텍처](/assets/images/portfolio/delaynomore-architecture.svg)

## A. 백엔드 설계 — 어떻게, 왜 {#backend}

> 규칙과 검증의 **단일 진실 공급원(source of truth)을 서버**에 두는 것을 원칙으로 삼았습니다. 프론트가 아무리 막아도 API는 `curl`로 직접 호출될 수 있으므로, **서버가 최종 방어선**이 되도록 계층과 계약을 설계했습니다.

![백엔드 계층 구조 — 요청 생애주기](/assets/images/portfolio/delaynomore-backend.svg)

**계층 분리 — 왜 나눴나.** 초기에는 한 컨트롤러(약 1,000줄)에 프롬프트 조립·응답 정제·HTTP 호출·검증이 뒤섞여 있었습니다. 책임별로 분리해 테스트 가능성과 변경 용이성을 확보했습니다.

- **`domain/{ai, plan}` + `global/{response, error, config}`** 로 도메인과 공통 관심사를 분리.
- **Controller** 는 `@Valid` 검증과 서비스 호출만(얇게 유지), **Service** 가 도메인 규칙·프롬프트 조립(`AiPromptBuilder`)·응답 정제(`AiResponseParser`)·SSE 릴레이를 소유.
- **`OpenRouterClient`** 로 외부 LLM 호출을 격리하고, Boot 4 규칙에 맞춰 `RestTemplate` → **`RestClient`** 전환. 서비스 계층 단위 테스트로 회귀 방어.

**API 계약 — 예측 가능한 응답.**

- 모든 응답을 `/api/v1` 아래 `{ success, data, error }`(`ApiResponse`)로 통일. 검증 실패는 `error.fieldErrors`, 오류 분기는 `error.code`(`ErrorCode`)로 판별해 클라이언트 분기를 단순화.
- 수동 `Map` 파싱을 **Bean Validation**(`@NotBlank`/`@Min`/`@Max`)으로 교체, 예외는 `BusinessException(ErrorCode)` + `GlobalExceptionHandler` 한 곳으로 일원화, springdoc(Swagger)로 문서화.

**서버가 지키는 규칙 — 최종 방어선.**

- 커스텀 제약 `@ValidPlanTasks`(날짜 키 `YYYY-MM-DD`, 항목 `{id, content, completed?}` 형태)와 status `@Pattern(DRAFT|CONFIRMED)`.
- LLM이 출력 계약을 어겨도(최상위 배열, "Day N" 키, `{plan:[...]}` 래퍼) 서버가 실제 날짜 키로 매핑(`normalizeDraftPlan`)해 원인 지점에서 정규화.
- 진행률과 회고 완료 개수가 같은 도메인 메서드(`Plan.countTasksOn`/`countAllTasks`)를 공유해 화면마다 값이 어긋나지 않게 함.

**Immutable Lock — 원자적 잠금 가드.** 확정(CONFIRMED)된 계획은 완료 토글과 no-op만 허용하고 구조·내용 변경은 거부합니다.

![Immutable Lock — 서버 원자 가드](/assets/images/portfolio/delaynomore-lock.svg)

- 가드를 `computeIfPresent` 람다(키 단위 원자 구간)에서 실행해 **조회·검사·교체 사이에 다른 쓰기가 끼어들 수 없습니다**(check-then-act 레이스 제거). 거부 시 저장소·감사 이벤트 모두 변화 없음.
- 생성 시 소유자당 한도 검사는 `synchronized`로 원자화해 TOCTOU를 막습니다(단일 서버 데모 범위의 의도된 선택, 다중 서버 확장은 별도 마일스톤).

> **💬 면접 포인트** — 왜 규칙의 단일 진실 공급원을 서버에 두었나 · `computeIfPresent`와 DB `SELECT … FOR UPDATE`가 같은 보장을 주는 방식 · LLM처럼 계약을 어기는 외부 응답의 서버측 검증·정규화 · 단일 서버 `synchronized`의 한계와 다중 서버 대안

## B. 배포 & 인프라 {#deploy}

> 풀스택을 **하나의 컨테이너**로 묶고, **빌드는 CI에서 한 번만** 수행해 VM은 이미지를 받아 실행만 하도록 설계했습니다. 저사양 무료 VM(Oracle Cloud Always Free)에서도 흔들리지 않게 하는 것이 목표였습니다.

![배포 파이프라인](/assets/images/portfolio/delaynomore-deploy.svg)

- **단일 서빙**: 루트 `Dockerfile` 하나로 Spring Boot가 React 정적 파일과 `/api/*`를 함께 서빙 — 프론트/백엔드를 따로 배포·정렬할 필요 없음.
- **Pull 방식 배포**: `main` 푸시/`v*` 태그마다 GitHub Actions가 이미지를 빌드해 `ghcr.io`에 push, VM은 **빌드 없이 이미지를 받아 실행**만. 저사양 VM이 빌드로 마비되던 문제를 근본 해결.
- **런타임 방어**: JVM 힙 상한(`-XX:MaxRAMPercentage=50`)으로 작은 VM의 OOM 방지.
- **프로필 전환**: 같은 이미지가 `DB_URL` 유무만으로 **PostgreSQL(영속)** ↔ **인메모리(휘발성)** 로 기동 — 데모·롤백 경로 유지.
- **키 관리**: 배포 스크립트가 `~/.delaynomore.env`(chmod 600)를 자동 로드해 셸 히스토리에 키가 남지 않음. Supabase는 세션 풀러(5432, `sslmode=require`) 사용(6543은 Flyway 세션 기능 미지원이라 배제).
- **KST 결함 해결**: 컨테이너 JVM(UTC)에서 자정~오전 9시 요청이 하루 이르게 처리되던 문제를 `KstDates`로 `Asia/Seoul` 기준 통일.

> **💬 면접 포인트** — 프론트·백엔드를 단일 컨테이너로 묶어 얻은 것/잃은 것 · VM에서 빌드하지 않고 Pull하도록 바꾼 이유 · 프로필 전환으로 휘발/영속 두 모드를 운영하는 이점 · 무료 VM에서 JVM 메모리 방어

## C. 데이터 & 동시성 설계 {#data}

> 누적된 회고를 다음 계획에 되먹이려면 **재시작에도 살아남는 저장소**가 필요했습니다. **PostgreSQL(Supabase 관리형)** 을 택하고 스키마·인덱스·격리·원자성을 각각의 이유를 가지고 설계했습니다.

![데이터 스키마 — 3 테이블](/assets/images/portfolio/delaynomore-schema.svg)

**스키마 설계.**

- **유연한 본문, 평탄한 매핑**: `Plan.tasks`는 형태가 바뀌기 쉬워 **`JSONB`**로 보관, 나머지는 레코드와 컬럼을 1:1 매핑. 날짜·시각은 프론트 ISO 문자열 왕복을 위해 `TEXT`, 정렬 키 `saved_at`은 epoch ms `BIGINT`.
- **조회 패턴 인덱스**: `(owner, saved_at DESC, id DESC)`, `(plan_id, date DESC)` 등을 실제 쿼리에 맞춰 설계.
- **이력은 삭제를 견딘다**: `reflections`는 `plans`에 `ON DELETE CASCADE`, `audit_events`는 **FK 없이** 두어 계획 삭제 뒤에도 "언제 삭제됐는가"를 답함.
- **접근 통제**: Supabase 자동 REST 노출을 막기 위해 세 테이블에 **정책 없는 RLS를 켜고** 앱은 특권 역할로 직접 접속. 스키마는 Flyway(`V1__init.sql`)로 버전 관리.

**소유자 격리 — 인증 이전의 접근 키.** 브라우저가 만든 안정 UUID를 `X-Guest-Id`로 실어 계획·회고·이력을 소유자별로 격리했습니다. `Plan.owner`를 키로 목록은 `findAllByOwner`로만 조회하고, **다른 소유자의 계획은 조회·수정·삭제 모두 404**로 존재 자체를 은닉. 저장 한도는 소유자당 10개 / 전역 200개로 분리, 개인 데이터엔 `Cache-Control: no-store`.

**동시성 · 원자성 보장.** 여러 방문자가 같은 데이터를 동시에 건드려도 깨지지 않도록, 조회·검사·교체를 한 트랜잭션의 행 잠금 안에서 수행합니다.

![동시성 · 원자성 보장](/assets/images/portfolio/delaynomore-concurrency.svg)

| 무엇을 지키나 | 어떻게 (PostgreSQL) |
| :--- | :--- |
| 생성 한도 TOCTOU 방지 | `@Transactional` + 검사·저장을 한 커밋에 |
| 고정 계획 잠금 레이스 방지 | `SELECT … FOR UPDATE` 행 잠금 안에서 가드 |
| 1일 1 회고 업서트 | 업서트, `createdAt` 보존 |
| 계획 변경과 감사 이력 | 한 트랜잭션 원자 커밋(실패 시 함께 롤백) |

- **저장 계층 추상화**: 저장소를 인터페이스로 두고 구현을 프로필로 선택(`postgres`=JDBC, 기본=인메모리). **서비스 코드 무변경**으로 어느 저장소에서도 같은 원자 보장.
- **재시작 복원 검증**: Testcontainers로 실제 PG17에 Flyway를 적용, 원자 가드·업서트 보존·캐스케이드·감사 생존을 검증하고 **새 인스턴스로 다시 읽어 복원**을 증명(`PersistenceRestartIT`).
- **정직한 한계**: 데이터 접근 키가 여전히 브라우저 게스트 ID라, 다른 기기/브라우저에선 재연결 불가. **로그인 도입(owner를 guestId→memberId로 재-key)** 전까지 남는 구조적 한계로 로드맵에 명시.

> **💬 면접 포인트** — `tasks`를 `JSONB`로 둔 이유와 정규화 컬럼 대비 트레이드오프 · 인덱스 조합의 근거 · `audit_events`를 FK 없이 둔 의도 · RLS를 켜고도 앱이 우회 접속하는 이유 · 재시작 복원을 테스트로 증명한 방법

## D. AI 통합 & 토큰 절약 {#ai}

> 대형 LLM을 쓰면서도 **비용과 체감 대기**를 잡아야 했습니다. 모델 품질은 유지한 채 **전송량(토큰)만 줄여** 요청당 비용을 낮추고, SSE 스트리밍으로 긴 대기를 조립 과정으로 바꿨습니다.

![AI 토큰 절약](/assets/images/portfolio/delaynomore-token.svg)

**토큰 절약 — 요청당 대부분 $0.001 미만.**

- **patch 전송**: 계획 전체 재전송을 **변경된 날짜만 담는 patch**로 전환(수정=해당 날짜, 연장=새 날짜, 단축=`null`).
- **compact 포맷**: `id`·`completed` 보일러플레이트를 제거하고 "날짜 → 문자열 배열"로 통일, 프론트가 상태 복원.
- **이력 축소** 12턴 → 6턴, **추론 모드 OFF**(요청당 약 95초·4천 토큰 절감), **`max_tokens` 상한**으로 폭주 방어.
- **결과(증빙)**: 요청당 입력 364–1,645 토큰, 비용 **$0.0002–$0.0022**로 대부분 $0.001 미만. 부수적으로 한국어 출력 순도도 백엔드 후처리로 확정 보장(한자/가나 제거, 한글·영문·숫자·기호 보존).

**실시간 스트리밍 — 대기를 "조립 과정"으로.** 하루 단위 설계에 20~30초 이상 걸려 이탈이 발생하던 병목을 스트리밍으로 해소했습니다.

![실시간 스트리밍(SSE)](/assets/images/portfolio/delaynomore-streaming.svg)

- **SSE 토큰 스트리밍**으로 응답을 도착하는 대로 흘려 체감 대기 단축, 초안은 "하루=한 줄(NDJSON)"로 생성해 **Day1부터 순차**로 채움.
- 응답을 "산문 → `===PLAN===` → 계획 JSON"으로 분리해 사람이 읽는 텍스트만 스트리밍하고 JSON은 끝에서 반영(깨진 JSON 방어), 실패 시 비스트리밍 → mock 폴백.

**초기 로딩 — 번들 최적화.** `rollupOptions`로 `node_modules`를 `vendor.js`로 격리 분할해 메인 앱 소스를 **44.53kB로 축소**, Vite 경고 해소.

![Vite 번들 최적화](/assets/images/portfolio/delaynomore-bundle.svg)

**AI 분량 추천 — 회고를 다음 계획으로.** 쌓인 회고를 되먹여 다음 분량을 추천하는 피드백 루프입니다.

![AI 분량 추천 피드백 루프](/assets/images/portfolio/delaynomore-recommendation.svg)

- **서버가 계산·규칙 소유**: 완료율은 관찰 창에서만 계산, 규칙(50% 미만 −1 · 85%+·여유 회고 다수 +1 등)으로 다음 분량 결정(1~5개, ±1 클램프).
- **AI는 이유만 설명**(숫자는 못 바꿈, 폴백 템플릿), **사용자 승인 필수**, 표본이 작으면 **같은 목표 최근 3건 합산**으로 안정화.

> **💬 면접 포인트** — 토큰 사용량을 어떻게 측정·절감했나(patch·compact·이력·추론) · 스트리밍 중 JSON 깨짐을 구조적으로 막은 방법 · AI를 신뢰하지 않기 위한 서버측 검증·정규화·폴백 배치 · LLM에 계산이 아닌 "이유 설명"만 맡긴 판단
