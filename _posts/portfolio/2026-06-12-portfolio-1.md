# DelayNoMore — AI 계획 실행 서비스 <span class="badge">개인 프로젝트</span>

> 기능 구현에 그치지 않고, **서버가 어디까지 책임져야 하는지**, 실패와 동시 요청에서도 **어떤 상태를 보장할지**를 중심으로 설계했습니다.
> 무료 VM·게스트 기반 접근·외부 LLM이라는 제약 안에서 **Spring Boot·React 풀스택을 단독 개발**하고, 서버 잠금 규칙·PostgreSQL 영속화·장애 폴백·Docker 배포까지 운영 가능한 흐름으로 완성했습니다.
> AI와 대화해 하루 단위 계획을 만들고, 확정된 계획은 수정·삭제를 제한해 실행에 집중하도록 만든 서비스입니다.

**[▶ 실행해 보기](http://delaynomoreapp.duckdns.org/)** · **[GitHub 저장소](https://github.com/hello-pebble/DelayNoMore_Release)**

![DelayNoMore 실제 서비스 화면 — 왼쪽 AI 코치와의 대화로 계획을 만들고, 가운데에 오늘 할 일이 모이며, 오른쪽 체크리스트에서 실행을 추적한다](/assets/images/portfolio/delaynomore-app.png)

<span class="section-note">실제 서비스 화면 — **대화(계획 생성) → 오늘 할 일(집계) → 체크리스트(실행 추적)** 3단 구성. 계획 확정 후에는 완료 체크만 허용되고, 미완료 항목은 버튼 하나로 내일로 이월됩니다.</span>

## 이 프로젝트에서 내린 핵심 설계 판단

- **왜 20~30초 걸리는 AI 응답에 SSE와 patch를 함께 적용했는가**
- **왜 확정된 계획을 화면이 아니라 트랜잭션 내부에서 잠가야 했는가**
- **왜 저장소를 PostgreSQL로 바꾸면서도 서비스 코드는 유지했는가**
- **왜 1GB VM에서 단일 컨테이너와 Pull 배포를 선택했는가**
- **왜 다중 서버 정합성은 지금 구현하지 않고 명시적인 한계로 남겼는가**

<span class="section-note">각 판단의 근거와 트레이드오프가 아래 본문 순서대로 이어집니다 — 선택 기준 · 보장 범위 · 검증 방법 · 의도적으로 포기한 것.</span>

## 핵심 성과

**1. 화면 규칙을 서버·트랜잭션이 보장하는 불변식으로 전환**
확정된 계획의 구조·내용 변경은 서버가 `409 PLAN_LOCKED`로 거부하고, 트랜잭션과 행 잠금 안에서 검사해 클라이언트 우회 호출과 동시 요청에도 같은 규칙을 적용했습니다.

**2. 인메모리에서 PostgreSQL로 이전하고 재시작 복원을 검증**
저장소 인터페이스를 유지한 채 PostgreSQL 구현체를 추가하고, Testcontainers 기반 통합 테스트에서 새 인스턴스로 데이터를 다시 읽어 계획·회고·감사 이력의 복원을 증명했습니다.

**3. 20~30초의 AI 무응답 구간 제거와 요청 비용 최적화**
SSE와 Day별 순차 생성으로 진행 상태를 즉시 노출하고, patch 전송·포맷 압축·대화 이력 축소로 동일한 모델을 유지하면서 요청 비용을 대부분 $0.001 미만(실사용 $0.0002–$0.0022)으로 낮췄습니다.

**제품 확장 — 실행 기록 → 다음 계획으로 이어지는 피드백 루프**
일일 회고의 완료율·체감 난이도를 서버가 집계해 다음 계획의 하루 분량을 추천합니다. 추천 숫자는 재현 가능해야 하므로 서버의 결정적 규칙이 계산하고, AI에는 계산 결과를 바꿀 권한 없이 사용자가 이해할 수 있는 이유 설명만 맡겼습니다.

![AI 분량 추천 피드백 루프](/assets/images/portfolio/delaynomore-recommendation.svg)

<span class="section-note">회고 UI — 하루를 닫으며 자동 계산된 완료율에 체감 난이도·이유를 남기면, 다음 계획 분량 추천의 입력이 됩니다.</span>

## 대표 문제 해결

### 1. 20~30초 걸리는 AI를 어떻게 '멈춤'이 아닌 '진행'으로 바꿨나

- **문제**: 고품질 계획 생성에 20~30초가 걸려 사용자가 처리 진행을 알 수 없는 무응답 구간이 생겼고, 대화마다 계획 전체를 주고받아 토큰 비용이 불필요하게 컸습니다.
- **해결**: 응답을 "산문 → 구분자 → 계획 JSON"으로 분리해 사람이 읽는 텍스트만 SSE로 스트리밍하고(깨진 JSON 방어), 계획은 변경된 날짜만 담는 patch로 교환했습니다. `id`·`completed` 보일러플레이트 제거, 이력 12→6턴 축소, 추론 모드 OFF(요청당 약 95초·4천 토큰 절감), `max_tokens` 상한까지 겹쳐 적용했습니다.
- **결과**: 요청당 입력 364–1,645 토큰, 비용 $0.0002–$0.0022. 스트림 실패 시 비스트리밍 → mock 순으로 폴백해 외부 LLM 장애에서도 핵심 흐름을 확인할 수 있게 했습니다.
- **트레이드오프**: SSE는 생성 시간 자체를 줄인 것이 아니라, 사용자가 진행 상태를 인지하지 못하는 무응답 구간을 제거한 선택입니다.

![AI 토큰 절약](/assets/images/portfolio/delaynomore-token.svg)

![실시간 스트리밍(SSE)](/assets/images/portfolio/delaynomore-streaming.svg)

### 2. 확정된 계획을 왜 UI가 아닌 서버와 DB에서 잠갔나

- **문제**: "확정된 계획은 수정 불가"라는 핵심 규칙을 프론트 화면만 지키고 있어, API를 직접 호출하면 우회할 수 있었습니다.
- **해결**: 규칙의 단일 진실 공급원을 서버로 옮겼습니다. 확정(CONFIRMED) 계획의 구조·내용 변경은 서버가 **409 `PLAN_LOCKED`**로 거부하고 완료 토글만 허용합니다. 이 검사를 저장소의 원자 구간(키 단위 `computeIfPresent`, DB 전환 후엔 트랜잭션+`SELECT … FOR UPDATE`) 안에서 실행해 조회·검사·교체 사이에 다른 쓰기가 끼어들 수 없게 했습니다. 입력 형식(`@ValidPlanTasks`)과 LLM의 계약 위반 응답 정규화도 서버가 담당합니다.
- **결과**: 클라이언트 우회 호출에서도 동일한 잠금 규칙이 유지됩니다. 거부 시 저장소·감사 이력 모두 무변화로 남아 상태가 항상 일관되고, 모든 변경은 "누가(세션)·언제·무엇을" 감사 이력으로 기록됩니다.
- **트레이드오프**: 행 잠금은 일관성을 얻는 대신 동시 처리량을 제한하므로, 잠금 범위를 계획 한 건으로 한정했습니다.

![Immutable Lock — 서버 원자 가드](/assets/images/portfolio/delaynomore-lock.svg)

### 3. 저장소를 PostgreSQL로 바꾸면서 서비스 코드를 어떻게 유지했나

- **문제**: 인메모리 저장은 서버 재시작마다 데이터가 사라져, 회고를 누적해 다음 계획에 되먹이는 피드백 루프를 만들 수 없었습니다.
- **해결**: PostgreSQL(Supabase)로 옮기며 스키마를 목적에 맞게 설계했습니다 — 형태가 변하는 `tasks`는 `JSONB`, 인덱스는 실제 조회 패턴 기준, 회고는 `ON DELETE CASCADE`, 감사 이력은 FK 없이 두어 계획 삭제 후에도 생존. 저장소를 인터페이스로 추상화해 인메모리 시절의 원자 보장(한도 TOCTOU 가드, 1일 1회고 업서트)을 트랜잭션+행 잠금으로 동일하게 이식했고, **서비스 코드는 변경 없이** 프로필 전환만으로 두 저장소를 오갑니다.
- **결과**: Testcontainers로 실제 PG17에서 원자 가드·업서트 보존·캐스케이드를 검증하고, 새 인스턴스로 다시 읽어 **재시작 후 복원을 테스트로 증명**했습니다.
- **트레이드오프**: 감사 이력에 FK를 두지 않아 참조 무결성 검사는 포기했지만, 계획이 삭제된 뒤에도 "무슨 일이 있었는지"는 남는 쪽을 택했습니다.

## 1GB 무료 VM에서 왜 단일 컨테이너와 Pull 배포를 선택했나

프론트엔드·백엔드·AI 프록시를 **하나의 Docker 컨테이너**로 묶었습니다. Spring Boot가 빌드된 React 정적 파일과 `/api/v1` REST·SSE를 함께 서빙하고, OpenRouter 키는 서버에만 보관합니다.

![시스템 아키텍처](/assets/images/portfolio/delaynomore-architecture.svg)

백엔드는 Controller(검증)–Service(규칙 소유)–Repository(프로필 전환) 계층으로 분리하고, 응답은 `{ success, data, error }` 공통 래퍼와 `ErrorCode`로 통일했습니다.

![백엔드 계층 구조](/assets/images/portfolio/delaynomore-backend.svg)

배포는 GitHub Actions가 이미지를 빌드해 `ghcr.io`에 올리고, Oracle Cloud 무료 VM은 **빌드 없이 Pull·실행만** 합니다(저사양 VM이 빌드로 마비되던 문제 해결). JVM 힙 상한으로 OOM을 방어하고, 같은 이미지가 환경변수만으로 영속/인메모리 모드를 오갑니다.

![배포 파이프라인](/assets/images/portfolio/delaynomore-deploy.svg)

**트레이드오프**: 단일 컨테이너는 독립 확장에는 불리하지만, 현재 트래픽과 1GB VM에서는 배포 복잡도를 줄이는 편이 더 중요했습니다.

### 구현하지 않은 것과 그 이유

- **게스트 ID 기반 접근**: 데이터 접근 키가 브라우저 localStorage의 게스트 ID라, 브라우저를 바꾸면 DB에 데이터가 남아 있어도 재연결되지 않습니다. 로그인 도입(owner를 guestId→memberId로 재-key) 전까지 남는 구조적 한계로 로드맵에 명시했습니다.
- **단일 서버 전제**: 생성 한도 가드에 `synchronized`를 사용해 다중 서버로 늘리면 한도가 최대 1 초과될 수 있습니다. 단일 서버 데모 범위의 의도된 선택이며, 강화는 다중 서버 마일스톤으로 분리했습니다.
- **자유 텍스트 그룹핑**: 분량 추천이 같은 목표를 `goalName` 문자열로 묶어, 목표명을 바꾸면 추천 계보가 갈라집니다. 구조적 계보(`source_plan_id`)는 다음 버전에서 다룹니다.

다중 서버까지 추상적으로 대비하기보다, **현재 운영 범위에서 필요한 보장을 먼저 명확히** 했습니다. 위 항목들은 숨긴 것이 아니라 로드맵에 명시한 의도적 선택입니다.
