## Overview {#overview}

계획을 세우는 것보다 계획을 계속 수정하는 과정이 실행을 늦춘다는 가설에서 시작했습니다. 사용자는 AI와 계획을 만든 뒤 확정하고, 확정된 계획에서는 완료 체크와 미완료 항목의 다음 날 이월만 수행합니다.

일일 회고에서 완료율과 체감 난이도를 저장하면 서버가 다음 계획의 하루 분량을 추천합니다. 추천 숫자는 동일 입력에서 재현돼야 하므로 서버 규칙이 계산하고, AI에는 결과를 변경할 권한 없이 사용자가 이해할 수 있는 이유 설명만 맡겼습니다.

## 01. 결정적 규칙에서 AI 맞춤 추천으로 {#adaptive-recommendation}

### 왜 처음부터 AI가 숫자를 정하지 않았는가

회고 데이터가 적은 초기 단계에서 LLM에 분량 결정을 전부 맡기면 같은 기록에도 추천이 달라질 수 있고, 외부 API 장애가 곧 핵심 기능 장애가 됩니다. 먼저 **재현 가능한 기준선과 실패해도 동작하는 피드백 루프**를 만드는 것이 우선이라고 판단했습니다.

- 미래 일정은 완료율에서 제외하고, 완료했거나 3일 이상 실행한 계획만 추천 대상으로 삼았습니다.
- 같은 목표의 최근 계획을 최대 3건 합산해 짧은 계획 한 건의 완료율이 과도하게 반영되는 문제를 줄였습니다.
- 관찰 3일 미만은 유지, 완료율 50% 미만은 1개 감소, 완료율 85% 이상이면서 여유 회고가 다수면 1개 증가하도록 했습니다.
- 하루 1~5개, 한 번에 최대 ±1개로 제한하고 벅참과 분량 과다 회고가 반복되면 감소를 우선했습니다.

### 역할을 분리해 안전한 승인 경계를 만들었다

`WorkloadRecommendation`은 통계와 숫자를 계산하고, AI는 이미 정해진 숫자의 이유를 설명합니다. 사용자가 `[추천대로]·[기존처럼]·[직접 설정]` 중 하나를 고르면 AI가 정확한 일일 개수로 새 계획 내용을 만들지만, 이 결과는 미리보기에만 존재합니다. `confirm` 요청이 들어와야 별도 계획으로 저장되며 원본 계획과 회고는 변경하지 않습니다.

AI가 날짜별 개수를 지키지 못하거나 호출에 실패하면 서버 템플릿으로 전환합니다. 추천 조회, 채택·변경, 추천 기반 생성은 감사 이력에 남겨 “어떤 판단으로 다음 계획이 만들어졌는가”를 추적할 수 있게 했습니다.

### 동작 검증

| 검증 대상 | 확인한 내용 |
| :--- | :--- |
| **결정 규칙** | 관찰 기간 부족, 완료율 경계, 벅참 우선 감소, 미래 일정 제외, 1~5개·±1 제한을 단위 테스트로 검증 |
| **표본 합산** | 같은 목표의 최근 3건만 합산하고 다른 목표와 다른 사용자의 데이터는 제외 |
| **승인 경계** | 초안 단계에서는 계획 수가 늘지 않고, 승인 후 새 계획만 생성되며 원본은 불변 |
| **장애 폴백** | AI 실패 시에도 날짜마다 선택한 개수의 서버 템플릿 초안을 생성 |
| **추적성** | 추천 조회, 추천 채택·변경, 추천 기반 계획 생성 이벤트 기록 |

규칙 분기와 `recommend → draft → confirm`, AI 실패 폴백을 자동 테스트로 확인하고 실제 화면에서 분량 선택·미리보기·승인 저장 흐름을 확인했습니다. 이 단계에서 **데이터 수집, 사용자 선택, 안전한 저장 경계**가 연결됐고 다음 고도화를 비교할 기준선도 확보했습니다.

### 다음 단계 — 호출을 늘리지 않고 AI가 숫자까지 제안

현재 구조는 재현성과 장애 대응에는 강하지만, 고정 임계값만으로는 최근 수행 추세·투자 시간·수준·회고 조합을 세밀하게 해석하기 어렵습니다. 다음 단계에서는 기존의 “AI 이유 설명” 호출 한 번이 아래 구조화된 결과를 함께 반환하도록 확장할 예정입니다.

```json
{
  "recommendedTasksPerDay": 2,
  "reason": "최근 완료율과 반복된 과부하 회고를 함께 보면 하루 2개가 적절합니다.",
  "confidence": 0.82,
  "signals": ["완료율 하락", "벅찼어요 3회", "분량 과다 2회"]
}
```

- 서버가 최근 기록을 `RecommendationContext`로 구조화하고 AI는 숫자·이유·신뢰도·근거를 한 번에 반환합니다.
- 서버는 1~5 범위, 현재 대비 최대 ±1, 관찰 데이터 충분 여부를 다시 검증합니다.
- JSON 오류·범위 위반·타임아웃이면 현재의 결정적 규칙으로 즉시 폴백합니다.
- 추천 결과에 `recommendationId`를 발급해 저장하고, 확정 시 클라이언트가 보낸 숫자가 아니라 서버 기록으로 채택·변경 여부를 판정합니다.
- 동일한 AI 호출 안에서 숫자와 이유를 함께 받으므로 외부 호출 횟수는 늘리지 않습니다.

![다음 계획 추천 고도화 — 현재 규칙 기반 기준선 위에 AI 맞춤 판단과 서버 검증을 추가한다](/assets/images/portfolio/delaynomore-recommendation-evolution.svg){:.portfolio-diagram}

고도화 후에는 단순히 “AI를 붙였다”가 아니라 다음 지표로 효과를 확인할 계획입니다.

| 관찰 지표 | 확인하려는 것 |
| :--- | :--- |
| **추천 응답 p95** | AI가 숫자를 함께 생성해도 사용 대기시간이 허용 범위인지 |
| **AI 폴백률** | JSON 오류·타임아웃·검증 실패가 얼마나 발생하는지 |
| **추천 채택·변경률** | 맞춤 추천이 사용자의 판단과 얼마나 일치하는지 |
| **다음 계획 완료율 변화** | AI 추천을 채택한 뒤 실제 실행 결과가 개선되는지 |

먼저 AI 추천과 규칙 추천을 함께 기록해 비교하고, 충분한 표본이 쌓인 뒤 계획별 최근 추세와 사용자의 과거 선택 패턴을 컨텍스트에 추가합니다. 문제가 생기면 AI 숫자 결정을 끄고 현재 규칙 결과로 즉시 돌아갈 수 있도록 폴백 경로를 그대로 유지합니다.

## 02. AI 응답 대기를 진행 경험으로 바꾸기 {#ai-streaming}

### 문제

고품질 계획 생성에 20~30초가 걸려 사용자가 처리 여부를 알 수 없는 무응답 구간이 생겼습니다. 대화마다 계획 전체를 다시 주고받아 토큰도 불필요하게 사용했습니다.

### 설계

- 응답을 `산문 → 구분자 → 계획 JSON`으로 분리하고 사람이 읽는 텍스트만 SSE로 전송했습니다.
- 계획은 전체 문서 대신 변경된 날짜만 담은 patch로 교환했습니다.
- `id`·`completed` 보일러플레이트를 제거하고 대화 이력을 12턴에서 6턴으로 줄였습니다.
- 추론 모드를 끄고 `max_tokens` 상한을 적용했습니다.
- 스트림 실패 시 비스트리밍, 다시 실패하면 mock으로 전환했습니다.

![AI 응답 최적화 — patch와 SSE로 전송량과 체감 대기를 줄임](/assets/images/portfolio/delaynomore-ai.svg){:.portfolio-diagram}

### 결과와 Trade-off

- 요청당 입력은 364–1,645 토큰, 비용은 $0.0002–$0.0022 범위로 확인했습니다.
- 외부 LLM이 실패해도 계획 생성의 핵심 흐름을 확인할 수 있습니다.
- SSE는 생성 시간 자체를 줄인 것이 아니라 사용자가 진행을 알 수 없는 구간을 제거한 선택입니다.

## 03. 계획 상태의 무결성과 영속화 {#state-integrity}

### 상태 수명주기와 운영 동시성

상태 문자열과 분산된 `if` 정책을 `PlanStatus` 전이표로 모으고, 고정·완료·중단을 명시적 API로 분리했습니다. 운영 서버에서는 현재 상태 확인과 갱신을 PostgreSQL 트랜잭션 안에서 처리합니다.

![계획 상태 전이 — 운영 PostgreSQL의 트랜잭션·행 잠금과 로컬 테스트용 인메모리 구현을 분리](/assets/images/portfolio/delaynomore-state-transition.svg){:.portfolio-diagram}

- 두 세션이 동시에 완료를 요청하면 첫 요청만 `CONFIRMED → COMPLETED`로 전이하고 이력을 저장합니다. 뒤 요청은 잠금 해제 후 최신 상태를 읽어 409를 받고, 프론트는 계획을 다시 조회합니다.
- 허용되지 않은 전이는 애플리케이션의 `PlanStatus`가 차단하고, `confirmedAt·completedAt`은 서버가 발급합니다.
- `ConcurrentHashMap.computeIfPresent` 구현은 DB 없이 빠르게 도메인 규칙을 확인하는 **로컬·단위 테스트용**입니다. 실서버의 영속성과 동시성 보장은 PostgreSQL 경로를 기준으로 합니다.

4×4 전이 매트릭스와 PostgreSQL 통합 테스트로 허용 간선, 종결 잠금, 상태·완료 시각 저장을 확인했습니다.

### 확정 이후 허용 동작을 서버가 결정한다

- `CONFIRMED`에서는 완료 체크와 서버가 통제하는 오늘→내일 이월만 허용합니다.
- 지난 날짜의 완료 상태는 소급 변경할 수 없고, `COMPLETED·CANCELLED`에서는 모든 실행 변경을 막습니다.
- 프론트는 허용된 동작만 노출하며, 회고 저장 시 종료일 도달 또는 전체 완료라면 계획 종결을 제안합니다.

### 저장소를 교체해도 서비스 규칙은 유지했다

초기 인메모리 저장은 재시작마다 데이터가 사라져 운영 저장소를 PostgreSQL로 전환했습니다. Repository 인터페이스는 유지하되 인메모리 구현은 로컬·단위 테스트 범위로 제한했습니다.

- 형태가 변하는 계획 항목은 `JSONB`로 저장했습니다.
- 회고는 계획 삭제 시 함께 정리되도록 `ON DELETE CASCADE`를 사용했습니다.
- 감사 이력은 계획 삭제 후에도 남기기 위해 FK를 두지 않았습니다.
- 상태 전이와 1일 1회고 업서트를 트랜잭션과 행 잠금으로 보호했습니다.
- Testcontainers의 PostgreSQL 17에서 원자성·업서트·캐스케이드·재시작 복원을 검증했습니다.

## 04. 1GB 무료 VM 제약 안에서 배포하기 {#deployment}

프론트엔드·백엔드·AI 프록시를 하나의 Docker 컨테이너로 묶었습니다. Spring Boot가 React 정적 파일과 `/api/v1` REST·SSE를 함께 제공하고 OpenRouter 키는 서버에만 보관합니다.

![시스템 아키텍처 — 단일 컨테이너 안의 Controller·Service·Repository](/assets/images/portfolio/delaynomore-architecture.svg){:.portfolio-diagram}

GitHub Actions가 이미지를 빌드해 GHCR에 올리고, Oracle Cloud 무료 VM은 빌드하지 않고 이미지를 Pull해 실행합니다. 저사양 VM에서 빌드가 자원을 점유하는 문제를 피하고 JVM 힙 상한으로 OOM을 방어했습니다.

![배포 파이프라인 — VM은 빌드하지 않고 이미지를 Pull한다](/assets/images/portfolio/delaynomore-deploy.svg){:.portfolio-diagram}

단일 컨테이너는 구성 요소별 독립 확장에 불리합니다. 하지만 현재 트래픽과 1GB VM에서는 확장성보다 배포 단순성과 장애 지점 축소를 우선했습니다.

### 의도적으로 남긴 한계

- **게스트 기반 접근**: 브라우저의 게스트 ID가 데이터 접근 키이므로 다른 브라우저에서 기존 데이터에 다시 연결할 수 없습니다.
- **단일 서버 전제**: 생성 한도 가드에 `synchronized`를 사용해 다중 서버에서는 한도가 최대 1건 초과될 수 있습니다.
- **문자열 기반 목표 계보**: 같은 목표를 `goalName`으로 묶어 이름을 바꾸면 추천 이력이 나뉩니다.

추상적인 다중 서버 확장보다 현재 운영 범위에서 보장할 규칙을 먼저 명확히 했습니다. 로그인, 분산 동시성, 구조적 목표 계보는 다음 마일스톤으로 분리했습니다.
