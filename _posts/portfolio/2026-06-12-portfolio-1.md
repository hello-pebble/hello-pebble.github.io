# DelayNoMore — AI 기반 계획 실행 서비스 <span class="badge">개인 프로젝트</span>

> AI와 대화해 하루 단위 계획을 만들고, 확정된 계획은 수정·삭제를 제한해 실행에 집중하도록 설계했습니다.
> **Spring Boot·React 풀스택을 단독 개발**하고, SSE 스트리밍·서버 잠금 규칙·PostgreSQL 영속화·Docker 배포까지 구현했습니다.
> AI 요청 비용을 **대부분 $0.001 미만**으로 낮추고, 실행 기록을 다음 계획 분량 추천에 반영하는 **피드백 루프**를 구축했습니다.

## 핵심 성과

**1. AI 요청당 비용 대부분 $0.001 미만 (실사용 $0.0002–$0.0022)**
계획 전체 재전송을 변경분(patch)만 보내도록 바꾸고, 전송 포맷 압축·대화 이력 축소·추론 모드 비활성화로 모델 품질은 유지한 채 전송 토큰만 줄였습니다.

**2. 20~30초 AI 대기를 "계획이 조립되는 과정"으로 전환**
SSE 토큰 스트리밍과 Day별 순차 생성으로, 응답을 기다리는 화면 대신 체크리스트가 Day 1부터 실시간으로 채워지는 경험을 만들어 이탈 병목을 해소했습니다.

**3. 실행 기록 → 다음 계획으로 이어지는 피드백 루프 완성**
일일 회고(완료율·체감 난이도)를 서버가 집계하고, 규칙 기반으로 다음 계획의 하루 분량을 추천합니다. AI는 이유 설명만 담당하고 숫자는 서버 규칙이 결정합니다.

## 대표 문제 해결

### 1. 느리고 비싼 대형 모델 — 스트리밍과 토큰 다이어트

- **문제**: 고품질 계획 생성에 20~30초가 걸려 유저가 먹통으로 오인했고, 대화마다 계획 전체를 주고받아 토큰 비용이 불필요하게 컸습니다.
- **해결**: 응답을 "산문 → 구분자 → 계획 JSON"으로 분리해 사람이 읽는 텍스트만 SSE로 스트리밍하고(깨진 JSON 방어), 계획은 변경된 날짜만 담는 patch로 교환했습니다. `id`·`completed` 보일러플레이트 제거, 이력 12→6턴 축소, 추론 모드 OFF(요청당 약 95초·4천 토큰 절감), `max_tokens` 상한까지 겹쳐 적용했습니다.
- **결과**: 요청당 입력 364–1,645 토큰, 비용 $0.0002–$0.0022. 스트림 실패 시 비스트리밍 → mock 순 폴백으로 데모가 끊기지 않습니다.

![AI 토큰 절약](/assets/images/portfolio/delaynomore-token.svg)

![실시간 스트리밍(SSE)](/assets/images/portfolio/delaynomore-streaming.svg)

### 2. 우회 가능한 잠금 규칙 — 서버가 강제하는 Immutable Lock

- **문제**: "확정된 계획은 수정 불가"라는 핵심 규칙을 프론트 화면만 지키고 있어, API를 직접 호출하면 우회할 수 있었습니다.
- **해결**: 규칙의 단일 진실 공급원을 서버로 옮겼습니다. 확정(CONFIRMED) 계획의 구조·내용 변경은 서버가 **409 `PLAN_LOCKED`**로 거부하고 완료 토글만 허용합니다. 이 검사를 저장소의 원자 구간(키 단위 `computeIfPresent`, DB 전환 후엔 트랜잭션+`SELECT … FOR UPDATE`) 안에서 실행해 조회·검사·교체 사이에 다른 쓰기가 끼어들 수 없게 했습니다. 입력 형식(`@ValidPlanTasks`)과 LLM의 계약 위반 응답 정규화도 서버가 담당합니다.
- **결과**: curl로도 우회할 수 없는 잠금. 거부 시 저장소·감사 이력 모두 무변화로 남아 상태가 항상 일관됩니다. 모든 변경은 "누가(세션)·언제·무엇을" 감사 이력으로 남습니다.

![Immutable Lock — 서버 원자 가드](/assets/images/portfolio/delaynomore-lock.svg)

### 3. 휘발성 데이터 — 재시작을 견디는 PostgreSQL 설계

- **문제**: 인메모리 저장은 서버 재시작마다 데이터가 사라져, 회고를 누적해 다음 계획에 되먹이는 피드백 루프를 만들 수 없었습니다.
- **해결**: PostgreSQL(Supabase)로 옮기며 스키마를 목적에 맞게 설계했습니다 — 형태가 변하는 `tasks`는 `JSONB`, 인덱스는 실제 조회 패턴 기준, 회고는 `ON DELETE CASCADE`, 감사 이력은 FK 없이 두어 계획 삭제 후에도 생존. 저장소를 인터페이스로 추상화해 인메모리 시절의 원자 보장(한도 TOCTOU 가드, 1일 1회고 업서트)을 트랜잭션+행 잠금으로 동일하게 이식했고, **서비스 코드는 변경 없이** 프로필 전환만으로 두 저장소를 오갑니다.
- **결과**: Testcontainers로 실제 PG17에서 원자 가드·업서트 보존·캐스케이드를 검증하고, 새 인스턴스로 다시 읽어 **재시작 후 복원을 테스트로 증명**했습니다.

## 아키텍처

프론트엔드·백엔드·AI 프록시를 **하나의 Docker 컨테이너**로 묶었습니다. Spring Boot가 빌드된 React 정적 파일과 `/api/v1` REST·SSE를 함께 서빙하고, OpenRouter 키는 서버에만 보관합니다.

![시스템 아키텍처](/assets/images/portfolio/delaynomore-architecture.svg)

백엔드는 Controller(검증)–Service(규칙 소유)–Repository(프로필 전환) 계층으로 분리하고, 응답은 `{ success, data, error }` 공통 래퍼와 `ErrorCode`로 통일했습니다.

![백엔드 계층 구조](/assets/images/portfolio/delaynomore-backend.svg)

배포는 GitHub Actions가 이미지를 빌드해 `ghcr.io`에 올리고, Oracle Cloud 무료 VM은 **빌드 없이 Pull·실행만** 합니다(저사양 VM이 빌드로 마비되던 문제 해결). JVM 힙 상한으로 OOM을 방어하고, 같은 이미지가 환경변수만으로 영속/인메모리 모드를 오갑니다.

![배포 파이프라인](/assets/images/portfolio/delaynomore-deploy.svg)

### 기술적 한계 (정직하게)

- **게스트 ID 기반 접근**: 데이터 접근 키가 브라우저 localStorage의 게스트 ID라, 브라우저를 바꾸면 DB에 데이터가 남아 있어도 재연결되지 않습니다. 로그인 도입(owner를 guestId→memberId로 재-key) 전까지 남는 구조적 한계로 로드맵에 명시했습니다.
- **단일 서버 전제**: 생성 한도 가드에 `synchronized`를 사용해 다중 서버로 늘리면 한도가 최대 1 초과될 수 있습니다. 단일 서버 데모 범위의 의도된 선택이며, 강화는 다중 서버 마일스톤으로 분리했습니다.
- **자유 텍스트 그룹핑**: 분량 추천이 같은 목표를 `goalName` 문자열로 묶어, 목표명을 바꾸면 추천 계보가 갈라집니다. 구조적 계보(`source_plan_id`)는 다음 버전에서 다룹니다.
