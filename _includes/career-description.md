# 1. 사내 공정 관리 솔루션(PMS) 개발 및 운영

| | |
| :--- | :--- |
| 역할·기간 | 백엔드 개발·운영(툴 통합, 배포 환경 구성, 장애 대응, 사용자 교육) |
| | 2022.11 ~ 2024.12 (2년 2개월) · 사용자 최대 100명 |
| 기술 | Java · Spring Boot · MyBatis · MariaDB · Docker Compose · GitLab CI · Nginx |

**핵심 성과**

- 사용 문의 **월 20건 → 1~2건** (약 90%↓)
- 저장한 작업물이 사라지던 장애의 **원인 3가지**를 찾아 조치
- 저장 요청 페이로드 **폴더 전체 비례 → 프레임 1개 비례**
- 설정 누락으로 인한 접속 장애를 배포 전 체크리스트로 차단

AI 학습데이터 라벨링 공정을 관리하는 웹 시스템이다. 3D(PCD 큐보이드)·2D 이미지·PDF 세 종류의 라벨링 툴을 시스템 안에 포함한다.

도입 전에는 매니저가 작업자 PC에 프로그램을 설치하고 엑셀 파일명으로 작업물을 배분·회수했다. 이를 웹 툴로 옮기고 배분–라벨링–검수–납품을 하나의 공정으로 묶었다.

## 핵심 의사결정

### 1) 실행 환경은 이미지로 고정하고, 배포 실행은 수동으로 남겼다

장애 원인의 대부분은 애플리케이션 버그가 아니었다. 서버마다 다른 포트·경로·런타임이 원인이었고, 그 설정은 문서가 아니라 담당자 기억에 있었다. 설정 하나가 어긋나면 전원 접속 불가, 곧 공정 전체 정지였다.

Docker Compose로 환경을 이미지화하고 **DB는 컨테이너 밖으로 분리**했다. 배포 실수가 데이터 손실로 이어지지 않게 하기 위해서다. 배포 전에 확인할 항목(포트 포워딩·방화벽·컨테이너 포트)은 체크리스트로 남겼다.

> **배포까지 자동화하지는 않았다**
> 작업자 종료를 확인한 뒤에만 배포할 수 있고, 배포 직후 확인도 사람이 해야 한다. 자동 배포 시점이 심야에 잡히면 확인할 사람이 없다. CI는 이미지 빌드까지만 자동화했다.
{: .tradeoff}

> **DB는 컨테이너에 넣지 않았다**
> 환경 재현성은 올라가지만, 컨테이너를 잘못 내리는 순간 운영 데이터가 함께 사라진다.
{: .tradeoff}

### 2) 권한을 결과물 보호 기준으로 나눴다

라벨링 결과가 그대로 납품 데이터가 된다. 매니저는 배분·조회·문의 답변까지 가능하되 **결과는 열람만** 할 수 있고, 수정·삭제는 관리자로 한정했다.

같은 이유로 최종 승인 건에만 규격 JSON 다운로드를 열었다. 미검수 데이터가 납품 경로로 나갈 수 없다.

### 3) 기존 SQL 자산 위에서 움직였다

> **JPA로 갈아타지 않았다**
> 라벨링 툴이 다루는 조회는 프레임·객체·클래스가 얽힌 비정형 질의가 많았다. 운영 중인 시스템에서 영속성 계층을 갈아끼우는 비용이, 얻을 이득보다 컸다. MyBatis로 기존 SQL을 유지했다.
{: .tradeoff}

## 대표 구현 — 저장 실패 원인 분석과 조치

가장 많은 문의가 나온 저장 장애(중복 저장, 뒷부분 유실, 미저장 종료)는 **하나의 증상 뒤에 원인이 셋**이었다.

| | 원인 | 증상과의 관계 |
| :--- | :--- | :--- |
| ① | 자동 라벨링으로 불어난 결과가, 로드된 전체 프레임을 요청 하나로 전송하는 오픈소스 저장 구조와 맞물림 | 서버 저장 처리에 도달하기 전에 끊김 |
| ② | 객체 단위 INSERT가 요청 전체 트랜잭션 없이 건별 커밋 | "앞은 저장, 뒤는 유실"은 부분 저장이 아니라 **부분 커밋**이었다 |
| ③ | 3D 유니크 키에 클래스·순서가 묶여 있는데, 2D 경로에 있던 기존 행 정리 호출이 3D 경로에 빠져 있음 | 이전 행이 남아 중복으로 보임 |

**저장 단위를 프레임 단위로 나눴다.** 요청 하나가 실어 나르는 양이 폴더 전체에 비례하던 것에서 프레임 1개에 비례하는 것으로 떨어진다. 자동 라벨링으로 결과가 불어나도 요청 크기는 따라 커지지 않는다. 유실을 막으면서 전송량도 함께 잡은 셈이다.

파일 이동 시 자동 저장과 창 닫기 확인 안내로 미저장 종료 경로도 막았다.

> **요청 전체를 한 트랜잭션으로 묶지는 않았다**
> 근본 조치는 이쪽이다. 다만 운영 중인 툴이라 저장 경로 전체를 건드리면 회귀 범위가 라벨링 작업 전체가 된다. 매일 발생하는 유실을 먼저 멈추고 구조 변경을 뒤로 미뤘다.
{: .tradeoff}

## 결과 — 문의 90% 감소

문서를 한 번 쓴 결과가 아니다.

- 화면별 조작을 번호로 설명한 **PDF 매뉴얼** 작성
- 기능이 몰린 화면에는 **서비스 안에 매뉴얼 버튼** 배치
- 문의를 받으면 그 항목을 매뉴얼에 추가

배분은 로컬 설치 + 엑셀에서 웹 원격 배분·회수로 바뀌었고, 인계는 구두 설명에서 매뉴얼 + 분기별 시연으로 바뀌었다.

## 회고

**부분 실패는 전면 실패보다 늦게 발견된다.** 실패를 드물게 만들었을 뿐 트랜잭션 경계는 끝내 도입하지 못했다. 다시 한다면 되돌아가는 경계를 먼저 만들고 그 위에서 전송량을 줄였을 것이다.

문의 건수는 세고 있었기에 90% 감소를 말할 수 있다. 반면 배포 소요·장애 대응 시간은 세지 않았다. **측정한 것만 개선을 말할 수 있다.** 이후로는 시작하기 전에 무엇을 잴지부터 정한다. DelayNoMore에서 눈으로 보던 판단을 평가 하네스로 바꾼 것이 이 경험에서 나왔다.

# 2. 개방DB API관리 시스템 설계 및 프로토타입 개발

| | |
| :--- | :--- |
| 역할·기간 | 화면·API 설계 · 메타데이터 구조 설계 · 동적 쿼리 엔진 구현 · 권한 분리 · 대시보드 |
| | 3인 팀 · 2024.09 ~ 2025.01 (5개월) |
| 기술 | Java · Spring · MyBatis · MariaDB · JSP · JavaScript · Chart.js |
| 후속 | 클린룸 재구현 [api-forge](https://github.com/hello-pebble/api-forge) · 2026.07 ~ · Java 21 · Spring Boot 3.5 · jOOQ · Testcontainers |

**핵심 성과**

- 조회 API 추가 공수 **파일 5~6개 + 재배포 → 메타데이터 등록 1건**
- 검증 누락 가능 지점 **API 개수만큼 → 엔진 1곳**
- 신규 인력 학습 대상 **흩어진 조회 로직 → 엔진 1개 + 메타데이터 규칙**
- 개발 서버까지 적용. **운영에 올리기 전에 이직해 실제 트래픽으로는 확인하지 못함**
- 그 검증을 대신하는 재구현에서 인젝션 차단 **3개 시나리오 × 2개 DB 방언 = 6조합**을 매 커밋 CI로 검증

신규 조회 요구사항마다 Controller·Service·ServiceImpl·DAO·SQL XML **5개 파일**이 늘었다. 파라미터는 VO 없이 Map으로 오가 컴파일 검증도 되지 않았고, 검증·바인드를 빠뜨릴 수 있는 자리가 API마다 있었다. 외부 공개 API에서 누락 하나는 곧 **SQL 인젝션 통로**다.

구조화되지 않은 레거시 탓에 신규 인력이 어떤 모듈을 써야 하는지 파악하는 데 시간이 걸렸고, 프로젝트 초반 딜레이가 반복됐다.

## 핵심 의사결정

### 1) 반복을 코드가 아니라 데이터로 옮겼다

조회 기능의 공통 부분을 메타데이터와 SQL 변환 엔진으로 모으고, 업무별 차이는 설정으로 표현했다.

이 선택은 온보딩 문제와 뿌리가 같다. 신규 인력이 헤맨 이유는 코드가 많아서가 아니라 **어디를 봐야 하는지 알 수 없어서**였다. 엔진 하나로 모으면 학습 대상이 "엔진 1개 + 메타데이터 규칙"으로 고정된다.

> **코드 제너레이터는 쓰지 않았다**
> 손으로 안 쓸 뿐 파일 수는 그대로 늘어난다. 온보딩 문제도, 검증 지점이 API마다 흩어지는 문제도 그대로 남는다.
{: .tradeoff}

### 2) 동적 영역의 경계를 먼저 그었다

런타임 조립 SQL은 조합마다 DB 방언 차이가 드러난다. 그런데 운영 DB는 개발 단계에서 접근할 수 없었다. 동적 영역을 넓힐수록 검증 경로가 `DB 종류 × 조건 조합`만큼 곱으로 늘어난다.

그래서 층을 나눴다.

| 층 | 처리 방식 |
| :--- | :--- |
| 페이징 | 공통 래퍼를 XML에 고정 (값은 바인드 변수) |
| DB 방언 | SQL 맵 세트를 디렉터리로 분리해 설정 교체 |
| 조회 컬럼·조건 | 메타데이터 기반 동적 조립 |

> **전부를 설정으로 빼지는 않았다**
> 공수는 더 줄었겠지만, 확인할 경로가 조합만큼 불어난다. 접근할 수 없는 운영 DB를 상대로는 감당할 수 없는 양이다.
{: .tradeoff}

> **페이징까지 런타임에 조립하지는 않았다**
> 조합마다 DB 방언 차이가 드러나 검증 불가능한 영역이 생긴다.
{: .tradeoff}

### 3) 권한은 되돌릴 수 있는 동작인지로 나눴다

데이터 등록과 API 버전 생성은 일반 사용자에게 열었다. 잘못돼도 내부에서 수정할 수 있고, 막으면 병목이 생겨 시스템을 안 쓰게 된다.

반면 **개방 여부 설정은 팀장 권한으로 한정**했다. 외부 공개는 되돌릴 수 없고 사업·법적 검토가 필요하다.

함께 **API 버전(v1, v2) 체계**를 두어, 기존 사용자를 깨지 않으면서 새 요구를 받아들일 수 있게 했다.

> **직급으로 일괄 제한하지 않았다**
> 등록·버전 생성까지 막으면 병목이 생겨 시스템 자체를 안 쓰게 된다. 기준은 직급이 아니라 되돌릴 수 있는지다.
{: .tradeoff}

### 4) iBatis를 MyBatis로 전환했다

취향이 아니라 전제 조건이었다. 엔진이 DB 방언별 SQL 맵 세트를 디렉터리 단위로 갈아끼우려면, 지원이 끊긴 iBatis 위에서는 설정 분리 자체가 성립하지 않는다.

## 대표 구현 — 메타데이터 기반 조회 엔진

API 엔드포인트 하나가 메타데이터 테이블의 행 하나다. 데이터셋이 조회 대상 테이블과 URL 키를, 컬럼 정의가 노출 컬럼·허용 필터·정렬 여부를 담는다. **여기 등록된 컬럼만** 쓸 수 있다.

| 컬럼 | filterType | 생성되는 조건 |
| :--- | :--- | :--- |
| `BILL_ID` | EQUALS | `=` |
| `COMMITTEE` | CHECK | `IN` |
| `PROPOSE_DT` | DATE | `BETWEEN` |

**인젝션 방어 지점은 엔진 한 곳이다.**

- SQL에 들어가는 식별자는 요청 파라미터명이 아니라 **메타데이터에 저장된 컬럼명**이다
- 요청 파라미터명은 조회 키로만 쓰이고 버려진다
- 연산자는 클라이언트가 아니라 컬럼의 `filterType`이 결정한다
- 값은 전부 바인드 파라미터다

차단 목록이 아니라 화이트리스트라, 방어 범위가 규칙 목록의 완전성에 의존하지 않는다.

그 밖에 등록 직후 샘플 URL을 호출해 설정 오류를 배포 전에 잡는 장치, 호출 통계 대시보드, 레거시 모듈화와 명세서 작성을 맡았다.

## 검증 — 못 한 확인을 재구현으로 대신하다

개발 서버까지는 확인했지만, **운영에 올리기 전에 이직해 실제 트래픽으로는 확인하지 못했다.** 그 검증을 대신해 핵심 구조를 비식별화하고 현대 스택으로 재구현한 것이 [api-forge](https://github.com/hello-pebble/api-forge)다. 회사 코드를 가져오지 않고 설계 의도만 옮긴 클린룸 재구현이다.

| 공격 시나리오 | 기대 결과 |
| :--- | :--- |
| 미등록 컬럼으로 필터 요청 | `400` |
| `BILL_ID; DROP TABLE …` 파라미터명 위장 | `400` |
| `' OR '1'='1` 값 주입 | 문자열 리터럴로 바인드 |

매 커밋 CI에서 H2와 PostgreSQL 양쪽으로 돌린다. 요청 파라미터명이 SQL에 진입하지 않으므로, **방어가 규칙 목록의 완전성에 의존하지 않고 두 방언에서 동일하게 성립한다**는 것을 확인했다.

## 회고

**추상화의 이득은 검증 비용과 함께 계산해야 한다.** "모든 것을 설정으로" 밀어붙였다면 공수는 더 줄었겠지만, 감당할 수 없는 양의 확인을 떠안았을 것이다.

그리고 **설정으로 옮긴 문제는 사라지지 않고 위치를 바꾼다.** 코드 오류가 메타데이터 오류가 됐을 뿐이다. 재구현에 식별자 규칙 검증을 넣었지만 발행 후 스키마 변경 감지는 과제로 남았다.

# 3. DelayNoMore — AI 계획 실행 지원 서비스 (개인)

| | |
| :--- | :--- |
| 역할·기간 | 기획 · 데이터 모델링 · API 설계 · 프론트/백엔드 · 평가 하네스 · 데모 배포 (단독) |
| | 2026.04 ~ 진행 중 (v0.1.0 ~ v0.22.0) |
| 기술 | Java · Spring Boot · React · PostgreSQL · OpenRouter · SSE · Docker · GitHub Actions · Oracle Cloud |
| 링크 | [저장소](https://github.com/hello-pebble/DelayNoMore_Release) · [데모](https://delaynomoreapp.duckdns.org/) |

**핵심 성과**

- "확정 후 수정 불가" 규칙을 프론트 → 서버 가드 → 도구 권한 순으로 옮겨, **curl로 직접 호출하면 뚫리던 경로 1건 → 0건**
- 눈으로 보고 판단하던 것을 **반복해서 돌릴 수 있는 평가 하네스**로 바꿔, 모델이 권한을 **돌아가는 경로 1건 발견**
- AI 컨텍스트 전송 **계획 전문 재전송 → 변경분(patch) 교환**{% comment %} TODO: patch 전환 전/후 요청당 평균 토큰을 1회 측정해 "N토큰 → M토큰 (X%↓)"로 채울 것 {% endcomment %}
- 마이너 릴리스 **22회** · 상태 전이 전수 검증 · **20스레드** TOCTOU 테스트

AI와 대화해 하루 단위 계획을 만들고, **확정 후에는 완료 체크와 이월만 허용**하는 서비스다. 각 버전이 직전 버전이 드러낸 문제 하나를 해결하는 방식으로 진행했다.

## 핵심 의사결정

### 1) 규칙의 소유권을 프론트에서 서버로, 다시 도구 권한으로

| 단계 | 위치 | 결과 |
| :--- | :--- | :--- |
| v0.4.1 | 프론트 버튼 차단 | **curl로 API를 직접 호출하면 그대로 뚫림.** 화면의 규칙은 UX일 뿐 강제가 아니다 |
| v0.8.0 | 서버 가드 `409 PLAN_LOCKED` | 프론트는 안내, 강제는 서버. 이후 진행률·이월·날짜 검증까지 서버로 옮김 |
| v0.14~15 | 선언적 전이표 → **도구 노출 권한** | 전이표가 그대로 도구 권한이 되면서, 수정을 막는 일이 **애초에 수정 도구를 쥐여주지 않는 것**으로 바뀜 |

상태 전이는 `SELECT … FOR UPDATE` 행 잠금 안에서 원자적으로 실행된다. 동시 완료 요청이 들어와도 첫 요청만 성공한다. 전이 매트릭스는 모든 조합을 도는 테스트로 묶어뒀고, 생성 한도 경쟁은 20스레드가 `CountDownLatch` 이중 배리어로 동시에 들어가는 TOCTOU 테스트로 묶어뒀다.

### 2) 경합이 생기자 판정을 쓰기 안으로 옮겼다

정원이 한정된 챌린지 참가(v0.21.0)에서 `SELECT`로 세어 자바에서 `if`로 판정하면, 두 문장 사이가 열려 정원을 넘긴다(TOCTOU).

조건 자체를 `UPDATE … WHERE participant_count < capacity`로 옮기고, 갱신 행 수 0을 마감으로 읽었다. 등록·참가비 차감·자리 예약은 한 트랜잭션으로 묶었다.

> **`SELECT`로 세어 자바에서 판정하지 않았다**
> 두 문장 사이가 열려 정원을 넘긴다. **틀린 구현을 대조군 테스트로 남겨** 실제 PostgreSQL에서 정원 초과가 재현되는 것을 assert한다.
{: .tradeoff}

### 3) 20~30초 AI 응답 — 모델을 낮추는 대신 대기를 진행 경험으로

`SseEmitter` 스트리밍으로 생성 과정을 보여주고, 계획 전체를 매번 재전송하던 방식을 **변경분(patch) 교환**으로 바꿨다. 전문 재전송은 요청당 전송량이 계획 크기에 비례해 대화가 길어질수록 비용과 지연이 같이 늘지만, patch는 그 회차에 바뀐 항목에만 비례한다.

> **더 가벼운 모델로 바꾸지 않았다**
> 응답 품질이 곧 서비스의 가치다. 모델을 낮추면 대기 시간은 줄지만 기능 자체가 의미를 잃는다.
{: .tradeoff}

### 4) 숫자는 서버 규칙이, 이유는 AI가

분량 추천 계산을 LLM에 맡기지 않았다. 같은 기록에 추천이 흔들리지 않고, 외부 API 장애에도 서버 템플릿으로 초안은 나온다.

> **숫자까지 LLM에 맡기지 않았다**
> 같은 기록에 추천이 흔들리고, 외부 API가 죽으면 초안조차 못 낸다.
{: .tradeoff}

## 대표 구현 — 눈으로 보던 것을 평가 하네스로

AI 코치를 도구 호출 에이전트로 전환하자 **프롬프트나 모델을 바꿨을 때 좋아졌는지 판단할 수단이 없었다.** 기능 추가를 멈추고, 실제 모델로 도구 선택 정확도를 재는 평가 하네스를 먼저 만들었다. 케이스 데이터셋, 순수 함수 채점기, 정확도·토큰 비용 리포트로 구성했다.

> **답변 문장의 품질까지 채점하지는 않았다**
> 비싸고 흔들린다. 그걸 넣는 순간 하네스가 "가끔 빨간불이 켜지는 물건"이 되어 아무도 보지 않게 된다. 채점 대상을 도구 선택 하나로 좁혔다.
{: .tradeoff}

**결과가 세 번 바뀌었다.**

1. 특정 케이스가 실패한다고 봤다.
2. 반복하니 실패가 케이스를 옮겨 다녔다. 반복을 늘리자 기저 실패율이 예상의 절반 수준으로 수렴했다.{% comment %} TODO: 평가 하네스 리포트에서 케이스 수와 수렴 기저 실패율(%)을 확인해 "N개 케이스, 기저 실패율 X%"로 채울 것 {% endcomment %}
3. 마지막으로 **모델이 금지된 도구 대신 허용된 인접 도구로 우회**한다는 것이 드러났다.

고정된 계획에 항목 추가를 요청하자, 수정 도구가 없는 모델이 **이월 도구로 계획을 실제로 바꿨다.** 이월은 그 상태에서 정상 노출되는 도구라 금지 목록에 넣으면 정상 요청까지 사고로 보고된다.

그래서 채점 범주를 갈랐다. **막혀서 못 하는 것과, 할 수 있는데 하지 말아야 하는 것은 다르다.** 후자는 통과율에는 실패로 반영하되 빌드는 깨뜨리지 않는다.

## 검증과 배포

테스트는 세 층으로 나눴다.

| 층 | 대상 |
| :--- | :--- |
| 순수 단위 | 도메인 규칙, 채점기 |

배포는 GitHub Actions가 단일 이미지를 빌드해 GHCR에 올리고, **Oracle Cloud 무료 VM(1GB)은 Pull만 해서 실행**한다.

# 기타 경력

## 정부 오픈API 개방 관리 시스템

(주)미디어그룹사람과숲 · 2023.08 ~ 2024.01 · Java, Spring MVC, Python, WildFly, MariaDB

행정안전부 개방데이터 시범 사업이다. 4인 팀에 Java를 다룰 사람이 적어 백엔드와 서버 세팅을 맡아 이끌었다.

**문제** — 개방 대상 원문이 HWP였고, 등록은 담당자가 문서를 열어 텍스트를 옮기고 개인정보를 지우는 수작업이었다. 파싱에 쓸 수 있는 코드는 Python인데 **외부 통신이 차단된 폐쇄망**이라 라이브러리를 그대로 끌어올 수 없었다.

**해결** — 서버 안에 Python 가상환경을 만들어 필요한 라이브러리를 직접 옮겨 넣고, Java가 `ProcessBuilder`로 스크립트를 호출하는 **서브프로세스 연동**을 택했다. 네트워크 구성을 건드리지 않으면서 텍스트 추출 → 마스킹 → DB 저장을 한 흐름으로 묶기 위해서다.

자료 등록은 담당자가 문서를 열어 옮겨 적던 수작업에서 **파일을 올리면 끝나는 절차**가 됐다. 그 위에 공공데이터포털 연계 **오픈API 5종**, 발주처가 JSON 응답을 직접 확인하는 미리보기 페이지, 호출 로그 통계 화면을 올려 시범 사업을 완료했다. ([공공데이터포털 공개](https://www.data.go.kr/data/15125451/openapi.do))

> **파싱 서버를 따로 두지 않았다**
> 폐쇄망에서 방화벽 규칙을 추가하는 절차 자체가 비용이다. 서버 하나를 더 띄우는 비용도 시범 사업 규모에 맞지 않았다.
{: .tradeoff}

## 사내 교육 플랫폼(LMS) 백엔드

(주)에이아이넷 · 2020.12 ~ 2021.03 · Java, Spring Boot, JPA, Oracle, SSO

6인 팀 파견으로 강의 등록·수강생 관리·자료 등록 백엔드를 전담했다.

**문제** — 권한 처리가 화면 단위 분기로만 되어 있었다. 메뉴를 감추는 것은 화면의 일이라, API 주소를 알면 강사용 기능이 수강생 계정으로도 호출됐다.

**해결** — SSO 세션 정보를 **RBAC**으로 구조화하고, Spring Security 계층의 공통 인터셉터에서 **엔드포인트 레벨로 차단**했다. 권한 확인 지점을 기능 개수만큼에서 인터셉터 1곳으로 모은 것이다. 이후 기능이 추가돼도 권한 규칙은 한 곳에만 등록하면 됐다.

첨부파일 **Oracle BLOB** 저장은 사내 정보 보관 요건상 정해진 요구사항이었고, 내 몫은 그 위에서 파일 변경이 비즈니스 데이터와 **같은 트랜잭션에 묶이게** 하는 것이었다. 처음 접한 JPA는 선임의 코드 리뷰와 페어 프로그래밍으로 학습하며 적용했다.

> **권한 검증을 기능마다 두지 않았다**
> 검증을 각 기능에 흩어놓으면 누락된 한 곳이 곧 구멍이 된다. 확인할 자리를 하나로 모아야 누락을 구조적으로 막을 수 있다.
{: .tradeoff}

## 항만 시설 사용료 관리 시스템

(주)엘에프아이티 · 2019.05 ~ 2020.07 · Java, Spring MVC, MyBatis, Oracle

여수광양항만공사 GIS 기반 시스템에서 사용료 산정과 업체 관리를 담당했다.

**문제** — 사용료는 해마다 고시되는 세율로 전 업체에 **일괄 자동 계산**되는 구조였다. 그런데 코로나 시기에 비상 감면이 들어오면서 세율을 업체 사정에 맞춰 **건별로 다르게** 적용해야 했다. 일괄 적용을 전제로 만들어진 계산에는 그 예외를 넣을 자리가 없었다.

**해결** — 세율을 "그해에 하나"가 아니라 **업체별로, 적용 종료 시점과 함께 지정하는 값**으로 바꿨다. 산정 로직은 계산식 대신 *적용할 세율을 고르는 규칙*(임시 세율이 있으면 그것, 없으면 연도 고시 세율)만 갖게 했다.

임시 세율 등록·관리 화면을 담당자에게 열어 **감면 1건당 개발 요청·배포에서 담당자 화면 조작**으로 바꿨다. 예외 업체가 늘어도 개발 공수는 0이고, 예외가 없는 업체는 기존 일괄 자동 계산이 그대로 돌았다.

폐쇄 환경이라 원격 접속이 되지 않아 **월 1회 정기 현장 방문**으로 서버를 점검하며 요청을 반영했다.

> **계산식에 감면 분기를 넣지 않았다**
> 예외가 늘어날수록 계산식이 부풀고, 감면 1건마다 개발·배포가 필요하다. 예외가 생길 수 있는 값은 코드가 아니라 담당자가 쥐고 있어야 한다.
{: .tradeoff}

## AdminCore — 운영 관리자 콘솔 백엔드

2026.06 ~ 진행 중 · Java 21, Spring Boot 4.1, PostgreSQL, JPA, Flyway, Spring Security/JWT

**JWT는 서버가 상태를 들고 있지 않아, 계정을 정지시켜도 이미 발급된 토큰이 만료 전까지 유효하다.** 인증 필터가 서명 검증 후 계정 상태까지 확인하게 해, 유효한 서명을 가진 정지 계정을 차단했다.

**인증과 인가는 다른 질문이고, JWT를 쓴다고 인가가 따라오지는 않는다**는 것을 여기서 배웠다. [github.com/hello-pebble/AdminCore](https://github.com/hello-pebble/AdminCore)

> 전자는 정지가 토큰 만료까지 듣지 않는다. 후자는 TTL만큼 같은 문제가 규모만 줄어든 채 재발한다. 지연을 없애려고 도입한 구조에 지연을 다시 넣지 않기로 하고, **요청당 DB 조회 1회**를 감수했다.
{: .tradeoff}
