# 1. 사내 공정 관리 솔루션(PMS) 개발 및 운영

AI 학습데이터 라벨링 공정을 관리하는 웹 시스템으로, **3D(PCD 큐보이드)·2D 이미지·PDF 세 종류의 라벨링 툴을 시스템 안에 포함**한다. 도입 전에는 매니저가 작업자 PC에 프로그램을 설치하고 엑셀 파일명으로 작업물을 배분·회수했는데, 이를 웹 툴로 옮기고 배분–라벨링–검수–납품을 하나의 공정으로 묶었다.

## 핵심 의사결정

**1. 실행 환경을 이미지로 고정하고, 배포 실행은 수동으로 남겼다.** 장애 원인 대부분이 애플리케이션 버그가 아니라 서버마다 다른 포트·경로·런타임이었고 그 설정이 문서가 아니라 담당자 기억에 있었다(설정 하나가 어긋나면 전원 접속 불가 = 공정 전체 정지). Docker Compose로 환경을 이미지화하고 **DB는 컨테이너 밖으로 분리**해 배포 실수가 데이터 손실로 이어지지 않게 했다. GitLab CI는 이미지 빌드까지만 자동화했다 — 작업자 종료 확인 후에만 배포할 수 있고 배포 직후 확인을 사람이 해야 하는 조건에서 자동 배포 시점이 심야에 잡히면 확인할 사람이 없기 때문이고, 대신 배포 전 확인 항목(포트 포워딩·방화벽·컨테이너 포트)을 체크리스트로 고정했다.

**2. 권한을 결과물 보호 기준으로 나눴다.** 라벨링 결과가 그대로 납품 데이터가 되므로 매니저는 배분·조회·문의 답변까지 가능하되 **결과는 열람만**, 수정·삭제는 관리자로 한정했다. 같은 이유로 최종 승인 건만 규격 JSON 다운로드가 열려 미검수 데이터가 납품 경로로 나갈 수 없다.

## 대표 구현 — 저장 실패 원인 분석과 조치

가장 많은 문의가 나온 저장 장애(중복 저장, 뒷부분 유실, 미저장 종료)는 **하나의 증상 뒤에 원인이 셋**이었다. ① 자동 라벨링으로 불어난 결과가 **로드된 전체 프레임을 요청 하나로 전송**하는 오픈소스 저장 구조와 맞물려 서버 저장 처리 도달 전에 끊김 ② 객체 단위 INSERT를 **요청 전체 트랜잭션 없이 건별 커밋** — "앞은 저장, 뒤는 유실"은 부분 저장이 아니라 **부분 커밋**이었다 ③ 3D 유니크 키에 클래스·순서가 묶여 있는데 2D 경로에 있던 **기존 행 정리 호출이 3D 경로에 누락**돼 이전 행이 잔존.

조치는 **저장 단위를 프레임 단위로 분할**한 것이다. 요청 하나가 실어 나르는 양이 **로드된 폴더 전체 비례 → 프레임 1개 비례**로 떨어지면서, 자동 라벨링으로 결과가 불어나도 요청 크기가 같이 커지지 않는다 — 유실을 막는 조치인 동시에 전송량을 상수로 묶는 조치였다. 요청 전체를 한 트랜잭션으로 묶는 근본 조치도 검토했으나 운영 중인 툴이라 저장 경로 전체를 건드리면 회귀 범위가 라벨링 작업 전체가 된다 — 매일 발생하는 유실을 먼저 멈추고 구조 변경을 뒤로 미뤘다. 파일 이동 시 자동 저장과 창 닫기 확인 안내로 미저장 종료 경로도 막았다.

**결과** — 문의 90% 감소는 문서를 한 번 쓴 결과가 아니다. 화면별 조작을 번호로 설명한 PDF 매뉴얼을 만들고 기능이 몰린 화면에는 **서비스 안에 매뉴얼 버튼**을 두었으며, 문의를 받으면 그 항목을 매뉴얼에 추가했다. 배분은 로컬 설치 + 엑셀에서 웹 원격 배분·회수로, 인계는 구두 설명에서 매뉴얼 + 분기별 시연으로 바뀌었다.

**회고** — **부분 실패는 전면 실패보다 늦게 발견된다.** 실패를 드물게 만들었을 뿐 트랜잭션 경계는 끝내 도입하지 못했다. 다시 한다면 되돌아가는 경계를 먼저 만들고 그 위에서 전송량을 줄였을 것이다. 그리고 문의 건수는 세고 있었기에 90% 감소를 말할 수 있지만 배포 소요·장애 대응 시간은 세지 않았다 — **측정한 것만 개선을 말할 수 있다.** 이후로는 착수 전에 잴 지표부터 정한다. DelayNoMore에서 육안 판단을 평가 하네스로 바꾼 것이 이 경험의 직접적인 결과다.

# 2. 개방DB API관리 시스템 설계 및 프로토타입 개발

| | |
| :--- | :--- |
| **역할·기간** | 화면·API 설계 · 메타데이터 구조 설계 · 동적 쿼리 엔진 구현 · 권한 분리 · 대시보드 (3인 팀) · 2024.09 ~ 2025.01 (5개월) |
| **핵심 성과** | 조회 API 추가 공수 **파일 5~6개 + 재배포 → 메타데이터 등록 1건** · 검증 누락 가능 지점 **API 개수만큼 → 엔진 1곳** · 신규 인력 학습 대상 **흩어진 조회 로직 → 엔진 1개 + 메타데이터 규칙** — 개발 서버까지 적용, **운영 반영 전 이직으로 실트래픽 검증은 미완** |
| **후속 (개인)** | 그 미완의 검증을 대신하는 클린룸 재구현 **[api-forge](https://github.com/hello-pebble/api-forge)** · 2026.07 ~ · 인젝션 차단 **3개 시나리오 × 2개 DB 방언 = 6조합**을 매 커밋 CI에서 검증 |
| **기술** | Java · Spring · **MyBatis**(SQL 맵 세트를 디렉터리로 분리해 DB 방언을 설정 교체로 처리) · **MariaDB**(운영 DB는 개발 단계에서 접근 불가 → 방언 차이를 검증 대상으로 격리) · JSP · JavaScript · Chart.js(호출 통계 대시보드) |

신규 조회 요구사항마다 Controller·Service·ServiceImpl·DAO·SQL XML **5개 파일**이 늘고, 파라미터는 VO 없이 Map으로 오가 컴파일 검증도 되지 않았으며, 검증·바인드를 빠뜨릴 수 있는 자리가 API마다 있었다 — 외부 공개 API에서 누락 하나가 **SQL 인젝션 통로**다. 구조화되지 않은 레거시 탓에 **신규 인력이 어떤 모듈을 써야 하는지 파악하는 데 시간이 걸려 프로젝트 초반 딜레이도 반복**됐다.

## 핵심 의사결정

**1. 반복을 코드가 아니라 데이터로 옮겼다.** 조회 기능의 공통 부분을 메타데이터와 SQL 변환 엔진으로 모으고 업무별 차이는 설정으로 표현했다. 코드 제너레이터도 검토했지만 파일 수는 그대로 늘어난다. 이 선택은 온보딩 문제와 뿌리가 같다 — 신규 인력이 헤맨 이유는 코드가 많아서가 아니라 **어디를 봐야 하는지 알 수 없어서**였고, 엔진 하나로 모으면 학습 대상이 "엔진 1개 + 메타데이터 규칙"으로 고정된다.

**2. 동적 영역의 경계를 먼저 그었다.** 런타임 조립 SQL은 조합마다 DB 방언 차이가 드러나는데 운영 DB는 개발 단계에서 접근할 수 없었다. **동적 영역을 넓힐수록 검증 경로가 `DB 종류 × 조건 조합`만큼 곱으로 늘어나므로** 층을 나눴다 — 페이징은 공통 래퍼를 XML에 고정(값은 바인드 변수), DB 방언은 SQL 맵 세트를 디렉터리로 분리해 설정 교체, 조회 컬럼·조건만 메타데이터 기반 동적 조립.

**3. 권한은 되돌릴 수 있는 동작인지로 나눴다.** 데이터 등록과 API 버전 생성은 일반 사용자에게 열었다 — 잘못돼도 내부에서 수정 가능하고, 막으면 병목이 생겨 시스템을 안 쓰게 된다. 반면 **개방 여부 설정은 팀장 권한으로 한정**했다. 외부 공개는 되돌릴 수 없고 사업·법적 검토가 필요하다. 함께 **API 버전(v1, v2) 체계**를 도입해 기존 사용자를 깨지 않으면서 새 요구를 수용했다.

## 대표 구현 — 메타데이터 기반 조회 엔진

API 엔드포인트 하나가 메타데이터 테이블의 행 하나다. 데이터셋이 조회 대상 테이블과 URL 키를, 컬럼 정의가 노출 컬럼·허용 필터·정렬 여부를 담고 **여기 등록된 컬럼만** 쓸 수 있다(`BILL_ID`=EQUALS, `COMMITTEE`=CHECK(IN), `PROPOSE_DT`=DATE(BETWEEN) 식). 신규 조회 기능 추가는 파일 5~6개 + 재배포에서 **메타데이터 등록 1건**으로, 신규 인력의 학습 대상은 흩어진 조회 로직에서 **엔진 1개 + 메타데이터 규칙 + 설계 문서**로 바뀌었다.

**인젝션 방어 지점은 엔진 한 곳이다.** SQL에 들어가는 식별자는 요청 파라미터명이 아니라 메타데이터에 저장된 컬럼명이고, 요청 파라미터명은 조회 키로만 쓰이고 버려진다. 연산자도 클라이언트가 아닌 컬럼의 `filterType`이 결정하며 값은 전부 바인드 파라미터다. 차단 목록이 아닌 화이트리스트라 방어 범위가 규칙 목록의 완전성에 의존하지 않는다. 그 외 등록 직후 샘플 URL 호출로 설정 오류를 배포 전에 잡는 장치, 호출 통계 대시보드, 레거시 모듈화와 명세서 작성을 수행했다. **iBatis → MyBatis 전환**은 취향이 아니라 전제 조건이었다 — 엔진이 DB 방언별 SQL 맵 세트를 디렉터리 단위로 갈아끼우려면 지원이 끊긴 iBatis 위에서는 설정 분리 자체가 성립하지 않았다.

**검증 — 미완의 검증을 재구현으로.** 개발 서버까지는 확인했으나 **운영 반영 전 이직해 실트래픽 검증은 하지 못했다.** 그 검증을 대신해 핵심 구조를 비식별화하고 현대 스택으로 재구현한 것이 **[api-forge](https://github.com/hello-pebble/api-forge)**(Java 21 · Spring Boot 3.5 · jOOQ · Testcontainers)다. 회사 코드를 가져오지 않고 설계 의도만 옮긴 클린룸 재구현으로, 미등록 컬럼 필터 요청(`400`)·`BILL_ID; DROP TABLE …` 파라미터명 위장(`400`)·`' OR '1'='1` 값 주입(문자열 리터럴로 바인드) 세 시나리오를 매 커밋 CI에서 H2와 PostgreSQL 양쪽으로 돌린다. **요청 파라미터명이 SQL에 진입하지 않으므로 방어가 규칙 목록의 완전성에 의존하지 않고 두 방언에서 동일하게 성립한다**는 것을 확인했다.

**회고** — **추상화의 이득은 검증 비용과 함께 계산해야 한다.** "모든 것을 설정으로" 밀어붙였다면 공수는 더 줄었겠지만 접근할 수 없는 운영 DB를 상대로 조합 폭발한 검증 경로를 감당할 수 없었을 것이다. 그리고 **설정으로 옮긴 문제는 사라지지 않고 위치를 바꾼다** — 코드 오류가 메타데이터 오류가 됐을 뿐이라 재구현에 식별자 규칙 검증을 넣었지만 발행 후 스키마 변경 감지는 과제로 남았다.

# 3. DelayNoMore — AI 계획 실행 지원 서비스 (개인)

| | |
| :--- | :--- |
| **역할·기간** | 기획 · 데이터 모델링 · API 설계 · 프론트/백엔드 · 평가 하네스 · 데모 배포 (단독) · 2026.04 ~ 진행 중 (v0.1.0 ~ v0.22.0) |
| **핵심 성과** | "확정 후 수정 불가" 규칙을 프론트 → 서버 가드 → **도구 권한**으로 이관 — **curl 직접 호출로 뚫리던 경로 1건 → 0건** · 육안 판단 → **반복 실행 가능한 평가 하네스**로 바꿔 모델의 **권한 우회 경로 1건 발견** · AI 컨텍스트 전송을 **계획 전문 재전송 → 변경분(patch) 교환**으로 축소 {% comment %} TODO: patch 전환 전/후 요청당 평균 토큰을 1회 측정해 "N토큰 → M토큰 (X%↓)"로 채울 것 {% endcomment %} · 마이너 릴리스 **22회**, 상태 전이 전수 검증 + **20스레드** TOCTOU 테스트 |
| **기술** | Java · Spring Boot · React · **PostgreSQL**(`SELECT … FOR UPDATE` 행 잠금과 조건부 `UPDATE`로 경합 판정을 DB 안에서 처리) · **OpenRouter**(모델 교체 지점을 한 곳으로) · **SSE**(20~30초 응답에서 모델 다운그레이드 대신 대기를 진행 경험으로) · Docker · GitHub Actions · **Oracle Cloud 무료 VM 1GB**(빌드는 CI, VM은 Pull만) |

[github.com/hello-pebble/DelayNoMore_Release](https://github.com/hello-pebble/DelayNoMore_Release) · [데모](https://delaynomoreapp.duckdns.org/) — AI와 대화해 하루 단위 계획을 만들고 **확정 후에는 완료 체크와 이월만 허용**하는 서비스. 각 버전이 직전 버전이 드러낸 문제 하나를 해결하는 방식으로 진행했다.

## 핵심 의사결정

**1. 규칙의 소유권을 프론트에서 서버로, 다시 도구 권한으로.**

| 단계 | 위치 | 결과 |
| :--- | :--- | :--- |
| v0.4.1 | 프론트 버튼 차단 | **curl로 API를 직접 호출하면 그대로 뚫림** — 화면의 규칙은 UX일 뿐 강제가 아니다 |
| v0.8.0 | 서버 가드 `409 PLAN_LOCKED` | 프론트는 안내, 강제는 서버. 이후 진행률·이월·날짜 검증까지 서버로 이관 |
| v0.14~15 | 선언적 전이표 → **도구 노출 권한** | AI 코치를 도구 호출 에이전트로 전환할 때 전이표가 그대로 도구 권한이 되면서, 수정 차단이 **애초에 수정 도구를 주지 않는 구조적 불가능**이 됨 |

상태 전이는 `SELECT … FOR UPDATE` 행 잠금 안에서 원자적으로 실행되어 동시 완료 요청 시 첫 요청만 성공한다. 전이 매트릭스는 전수 검증 테스트로, 생성 한도 경쟁은 20스레드가 `CountDownLatch` 이중 배리어로 동시 진입하는 TOCTOU 테스트로 고정했다.

**2. 경합이 생기자 판정을 쓰기 안으로 옮겼다.** 정원이 한정된 챌린지 참가(v0.21.0)에서 `SELECT`로 세어 자바에서 `if`로 판정하면 두 문장 사이가 열려 정원을 넘긴다(TOCTOU). 조건 자체를 `UPDATE … WHERE participant_count < capacity`로 옮겨 갱신 행 수 0을 마감으로 읽었고, 등록·참가비 차감·자리 예약을 한 트랜잭션으로 묶었다. **틀린 구현을 대조군 테스트로 남겨** 실제 PostgreSQL에서 정원 초과가 재현되는 것을 assert한다.

**3. 20~30초 AI 응답 — 모델을 낮추는 대신 대기를 진행 경험으로.** 응답 품질이 서비스의 핵심 가치라 모델을 낮추면 기능이 의미를 잃는다. `SseEmitter` 스트리밍으로 생성 과정을 보여주고, 계획 전체를 매번 재전송하던 방식을 **변경분(patch) 교환**으로 바꿨다. 전문 재전송은 요청당 전송량이 계획 크기에 비례해 대화가 길어질수록 비용과 지연이 같이 늘지만, patch는 그 회차에 바뀐 항목에만 비례한다. 한편 **숫자는 서버 규칙이, 이유는 AI가** — 분량 추천 계산을 LLM에 맡기지 않아 같은 기록에 추천이 흔들리지 않고, 외부 API 장애에도 서버 템플릿으로 초안은 나온다.

## 대표 구현 — 육안 확인을 평가 하네스로

AI 코치를 도구 호출 에이전트로 전환하자 **프롬프트나 모델을 바꿨을 때 좋아졌는지 판단할 수단이 없었다.** 기능 추가를 멈추고 실제 모델로 도구 선택 정확도를 재는 평가 하네스를 먼저 만들었다(케이스 데이터셋, 순수 함수 채점기, 정확도·토큰 비용 리포트). 채점 대상은 도구 선택 하나로 좁혔다 — 답변 문장의 품질은 심판 모델이 필요해 비싸고 흔들리는데, 그걸 넣는 순간 하네스가 "가끔 빨간불이 켜지는 물건"이 되어 아무도 안 보게 된다.

**결과가 세 번 바뀌었다** — 특정 케이스가 실패한다고 봤지만 반복하니 실패가 케이스를 옮겨 다녔고, 반복을 늘리자 기저 실패율이 예상의 절반 수준으로 수렴했으며,{% comment %} TODO: 평가 하네스 리포트에서 케이스 수와 수렴 기저 실패율(%)을 확인해 "N개 케이스, 기저 실패율 X%"로 채울 것 {% endcomment %} 마지막으로 **모델이 금지된 도구 대신 허용된 인접 도구로 우회**한다는 것이 드러났다 — 고정된 계획에 항목 추가를 요청하자 수정 도구가 없는 모델이 **이월 도구로 계획을 실제로 바꿨다.** 이월은 그 상태에서 정상 노출되는 도구라 금지 목록에 넣으면 정상 요청까지 사고로 보고된다. 그래서 채점 범주를 갈랐다 — **막혀서 못 하는 것과, 할 수 있는데 하지 말아야 하는 것은 다르다.** 후자는 통과율에는 실패로 반영하되 빌드는 깨뜨리지 않는다.

**검증과 배포** — 테스트는 순수 단위 / standalone MockMvc / `*IT` 통합(Testcontainers PostgreSQL) 세 층으로 나누고, 실제 모델 호출 평가는 `@Tag("eval")`로 일반 빌드에서 제외했다 — 외부 API에 의존하는 검증이 일반 빌드를 막으면 아무도 테스트를 돌리지 않는다. 배포는 GitHub Actions가 단일 이미지를 빌드해 GHCR에 올리고 **Oracle Cloud 무료 VM(1GB)은 Pull만 해서 실행**한다.

**회고** — **규칙을 어디에 두느냐가 곧 그 규칙의 강제력이다.** 그리고 **출력이 흔들리는 대상은 한 번의 실행으로 판단하면 안 된다.** **한계** — 데모 배포라 운영 트래픽과 실사용자 효과 지표가 없고, 생성 한도 가드가 `synchronized` 기반이라 다중 서버에서는 한도가 최대 1건 초과될 수 있다.

# 기술 선택 근거 — 채택안과 기각안
{: #tech-decisions}

각 판단의 배경은 해당 프로젝트 본문에 있고, 여기서는 비교 대상만 모았다.

| 상황 | 채택 | 기각 | 기각 이유 |
| :--- | :--- | :--- | :--- |
| 조회 API 반복 개발 (개방DB) | 메타데이터 + 변환 엔진 | 코드 제너레이터 | 손으로 안 쓸 뿐 파일 수는 그대로 늘어남 — 온보딩·검증 지점 문제가 남음 |
| 동적 SQL 범위 (개방DB) | 컬럼·조건만 동적 | 전면 설정화 | 검증 경로가 `DB 종류 × 조건 조합`으로 곱 증가, 운영 DB는 접근 불가 |
| 페이징 처리 (개방DB) | 공통 래퍼를 XML에 고정 | 런타임 조립 | 조합마다 DB 방언 차이가 드러나 검증 불가능한 영역이 생김 |
| 배포 자동화 (PMS) | 이미지 빌드까지만 CI | 전자동 배포 | 배포 직후 사람 확인이 필수인데 자동 시점이 심야면 확인자가 없음 |
| 저장 유실 조치 (PMS) | 프레임 단위 분할 | 요청 전체 단일 트랜잭션 | 운영 중인 툴이라 저장 경로 전체를 건드리면 회귀 범위가 라벨링 작업 전체 |
| 권한 분리 기준 (개방DB) | 되돌릴 수 있는지로 구분 | 직급으로 일괄 제한 | 등록·버전 생성까지 막으면 병목이 생겨 시스템을 안 쓰게 됨 |
| AI 응답 지연 (DelayNoMore) | SSE 스트리밍 + patch 교환 | 경량 모델로 교체 | 응답 품질이 곧 서비스의 가치 — 낮추면 기능 자체가 의미를 잃음 |
| 분량 추천 계산 (DelayNoMore) | 서버 규칙이 숫자, AI가 이유 | LLM이 숫자까지 산출 | 같은 기록에 추천이 흔들리고, 외부 API 장애 시 초안조차 못 냄 |
| 평가 하네스 채점 범위 (DelayNoMore) | 도구 선택 정확도만 | 답변 문장 품질까지 (심판 모델) | 비싸고 흔들려 "가끔 빨간불이 켜지는 물건"이 되면 아무도 안 봄 |
| 정원 초과 방지 (DelayNoMore) | 조건부 `UPDATE … WHERE` | `SELECT` 후 자바 `if` | 두 문장 사이가 열려 정원을 넘김(TOCTOU) — 대조군 테스트로 재현 |
| HWP 파싱 (정부 오픈API) | `ProcessBuilder` 서브프로세스 | 별도 파싱 서버 + HTTP | 폐쇄망 방화벽 규칙 추가 절차 자체가 비용 |
| JWT 정지 계정 (AdminCore) | 필터에서 계정 상태 조회 | 순수 stateless 유지 / 상태 캐싱 | 전자는 정지가 만료까지 안 먹히고, 후자는 TTL만큼 같은 문제가 축소 재발 |
| 토큰 검증 위치 (Auth Gateway) | Resource Server가 JWKS로 독립 검증 | Gateway 검증 결과를 신뢰 헤더로 전달 | Gateway 우회 경로 하나가 인가 전체의 단일 실패점 |

# 기타 경력

**정부 오픈API 개방 관리 시스템** · (주)미디어그룹사람과숲 · 2023.08 ~ 2024.01 · Java, Spring MVC, Python, WildFly, MariaDB
행정안전부 개방데이터 시범 사업. 4인 팀 중 Java 인력이 제한적이어서 백엔드와 서버 세팅을 주도했다.
**문제** — 개방 대상 원문이 HWP였고 등록은 담당자가 문서를 열어 텍스트를 옮기고 개인정보를 지우는 수작업이었다. 파싱에 쓸 수 있는 코드는 Python인데 **외부 통신이 차단된 폐쇄망**이라 라이브러리를 그대로 끌어올 수 없었고, 별도 파싱 서버를 두고 HTTP로 부르는 방법은 방화벽 규칙 추가 절차 자체가 비용이었다.
**해결** — 별도 파싱 서버 + HTTP 호출은 방화벽 규칙 추가 절차 자체가 비용이라 기각하고, 서버 로컬에 Python 가상환경을 만들어 필요한 라이브러리를 반입한 뒤 Java가 `ProcessBuilder`로 스크립트를 호출하는 **서브프로세스 연동**을 택했다. 네트워크 구성을 건드리지 않으면서 텍스트 추출 → 마스킹 → DB 저장을 한 흐름으로 묶기 위해서다. **자료 등록은 담당자가 HWP를 열어 텍스트를 옮기고 개인정보를 지우던 수작업에서, 파일을 올리면 추출 → 마스킹 → 저장이 한 흐름으로 끝나는 절차로 바뀌었다.** 그 위에 공공데이터포털 연계 **오픈API 5종**과 발주처가 JSON 응답을 직접 확인하는 미리보기 페이지, 호출 로그 통계 화면을 올려 시범 사업을 완료했다. ([공공데이터포털 공개](https://www.data.go.kr/data/15125451/openapi.do))

**사내 교육 플랫폼(LMS) 백엔드** · (주)에이아이넷 · 2020.12 ~ 2021.03 · Java, Spring Boot, JPA, Oracle, SSO
6인 팀 파견으로 강의 등록·수강생 관리·자료 등록 백엔드를 전담했다.
**문제** — 권한 처리가 화면 단위 분기로만 되어 있었다. 메뉴를 감추는 것은 화면의 일이라, API 주소를 알면 강사용 기능이 수강생 계정으로도 호출됐다.
**해결** — SSO 세션 정보를 **RBAC**으로 구조화하고 Spring Security 계층의 공통 인터셉터에서 **엔드포인트 레벨로 차단**했다. 검증을 각 기능에 흩어놓으면 누락된 한 곳이 곧 구멍이 되므로, **권한 확인 지점을 기능 개수만큼 → 인터셉터 1곳**으로 모은 것이다. 이후 기능이 추가돼도 권한 규칙은 한 곳에만 등록하면 됐다. 첨부파일 **Oracle BLOB** 저장은 사내 정보 보관 요건상 정해진 요구사항이었고, 내 몫은 그 위에서 파일 변경이 비즈니스 데이터와 **같은 트랜잭션에 묶이게** 하는 것이었다. 처음 접한 JPA는 선임의 코드 리뷰와 페어 프로그래밍으로 학습하며 적용했다.

**항만 시설 사용료 관리 시스템** · (주)엘에프아이티 · 2019.05 ~ 2020.07 · Java, Spring MVC, MyBatis, Oracle
여수광양항만공사 GIS 기반 시스템에서 사용료 산정과 업체 관리를 담당했다.
**문제** — 사용료는 해마다 고시되는 세율로 전 업체에 **일괄 자동 계산**되는 구조였다. 그런데 코로나 시기에 비상 감면이 들어오면서 세율을 업체 사정에 맞춰 **건별로 다르게** 적용해야 하는 상황이 생겼다. 일괄 적용을 전제로 만들어진 계산에는 그 예외를 넣을 자리가 없었다.
**해결** — 세율을 "그해에 하나"가 아니라 **업체별로, 적용 종료 시점과 함께 지정하는 값**으로 바꾸고, 산정 로직은 계산식 대신 *적용할 세율을 고르는 규칙*(임시 세율이 있으면 그것, 없으면 연도 고시 세율)만 갖게 했다. 임시 세율 등록·관리 화면을 담당자에게 열어 **감면 1건당 개발 요청·배포 → 담당자 화면 조작**으로 바꿨고(예외 업체가 늘어도 개발 공수는 0), 예외가 없는 업체는 기존 일괄 자동 계산이 그대로 돌았다. 폐쇄 환경이라 원격 접속이 되지 않아 **월 1회 정기 현장 방문**으로 서버를 점검하며 요청을 반영했다. 예외가 생길 수 있는 값은 코드가 아니라 담당자가 쥐고 있어야 한다는 것을 여기서 배웠다.

# 기타 개인 프로젝트

**AdminCore — 운영 관리자 콘솔 백엔드** · 2026.06 ~ 진행 중 · Java 21, Spring Boot 4.1, PostgreSQL, JPA, Flyway, Spring Security/JWT
**JWT는 서버가 상태를 들고 있지 않아 계정을 정지시켜도 이미 발급된 토큰이 만료 전까지 유효하다** — 인증 필터가 서명 검증 후 계정 상태까지 확인하게 해 유효 서명을 가진 정지 계정을 차단했다. **요청당 DB 조회 1회 추가**와 stateless 이점의 일부를 내주고 정지가 다음 요청부터 듣게 한 선택이다. 캐시로 그 조회를 없앨 수도 있지만, 캐시 TTL만큼 정지가 다시 늦게 듣게 되므로 애초에 해결하려던 문제가 규모만 줄어든 채 돌아온다 — 지연을 없애려고 도입한 구조에 지연을 다시 넣지 않기로 했다. **인증과 인가는 다른 질문이며 JWT에서 후자는 자동으로 따라오지 않는다**는 것이 수확이다. [github.com/hello-pebble/AdminCore](https://github.com/hello-pebble/AdminCore)

**Auth Gateway Platform — Gateway 기반 인증·인가 검증** · 2026.01 ~ 2026.03 · Kotlin, Spring Boot, Spring Security, OAuth2/JWT, Spring Cloud Gateway
Auth가 JWT를 중앙 발급하고 Gateway·Resource Server가 JWKS로 각자 검증하는 구조를 다중 모듈로 구성한 아키텍처 실험. 공개 경로 접근·무토큰 401·양측 권한 검증·내부 경로 404 **4개 시나리오를 실제 요청으로 검증**하고, 설계마다 대안 A/B/C 비교 근거를 코드와 함께 버전 관리했다. Gateway가 검증 결과를 신뢰 헤더로 넘기는 대안 대신 **Resource Server가 JWKS로 독립 검증**하게 한 것은, 전자가 Gateway 우회 경로 하나로 인가 전체가 무력화되는 단일 실패점이 되기 때문이다. [github.com/hello-pebble/auth-gateway-platform](https://github.com/hello-pebble/auth-gateway-platform)
